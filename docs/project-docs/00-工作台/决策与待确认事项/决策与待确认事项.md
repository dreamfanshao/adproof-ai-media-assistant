### D017｜达人检索改为每批 20 人并持久化续检进度

- **日期**：2026-08-29
- **结论**：D010 中单次 50 人目标调整为每批最多 20 名有效博主；同一项目、同一检索条件再次检索时复用持久化游标和筛选历史，排除已采用、项目已有及冷却期内已过滤对象。单批任务持续检索直至达到 20 人、数据源耗尽或安全调用预算不足；仍可继续时由用户点击“继续检索 20 人”从上次位置续跑。
- **理由**：50 人单批会显著放大 RedFox 调用量和等待时间，固定 100 人候选池又会在合格率低时过早停止；20 人批次更适合人工复核，同时持久化续检可避免重复消耗并消除固定候选上限。
- **影响范围**：FR-04/FR-05、检索 API、Worker 调度、Supabase 检索会话与筛选历史、找达人页面和验收口径；D010 的其他 API 契约仍有效。

### D018｜检索不足 20 人时改为任务内自动续批

- **日期**：2026-08-30
- **结论**：检索任务首次命中不足 20 人时，不再因单批调用窗口结束而立即要求用户手动续检；系统在同一任务、同一游标和同一去重历史上自动续批，直到补足 20 人、数据源耗尽、供应商真实限流/余额不足或达到整任务安全上限。只有整任务保护触发且仍有后续数据时，才展示“继续补足至 20 人”。
- **理由**：严格粉丝、时间、点赞和语义条件下首批命中率可能很低；把内部批次暴露为用户操作会造成“只返回 2 人就停”的错误体验。
- **影响范围**：FR-04/FR-05、Worker 调用预算、任务状态文案、找达人结果页操作按钮；D017 的 20 人目标与持久化去重规则保持不变。

### D019｜下一批统一从顶部“开始检索”发起

- **日期**：2026-08-30
- **结论**：移除结果区“继续补足至 20 人”按钮。顶部“开始检索”作为唯一入口，每次创建一批并尽力新增 20 人；本批结束后再次点击即可从同一条件的持久化游标获取下一批，直到数据源无更多符合项。去重范围扩大为当前项目全部历史任务已经发现或筛查过的达人，不再只限于同一检索会话或已写入候选列表的达人。
- **理由**：用户只需要理解“每点一次取下一批 20 人”，无需区分首次检索、任务内续页和手动续检三种系统概念；项目级历史排除也能避免跨条件重复消耗接口与人工复核时间。
- **影响范围**：FR-04/FR-05、找达人页面、检索任务防重窗口、Worker 项目级筛查历史；D017/D018 的独立续检按钮约定由本决策替代。

### D020｜模型不得覆盖 20 人目标，关键词计划只增不减

- **日期**：2026-08-31
- **结论**：达人检索批次目标由业务层强制为 20，忽略意图模型输出的其他 `limit`；关键词采用最多 32 路确定性基础、长尾与宽召回词，模型仅能补充语义信息，不能缩减关键词集合。历史会话只耗尽旧关键词时必须自动打开新增关键词并继续真实 RedFox 检索。
- **理由**：任务 `2398c2aa-9070-4e39-b5db-12e6c66c5325` 复用旧游标时，运行中的旧 Worker 将关键词从 24 路缩回已耗尽的 8 路，导致 `requestCount=0` 却误报数据源耗尽；DeepSeek 返回 `limit=50` 进一步暴露了模型输出和业务目标未隔离的问题。
- **兜底边界**：系统持续检索直至新增 20 个有效博主；只有 RedFox 真实数据耗尽、供应商余额/限流或整任务安全上限触发时才允许不足 20，并必须记录调用数、游标、漏斗和终止原因，不得用不合格或虚构数据补足。
- **影响范围**：意图 Skill 输出契约、Agent 结果截断、关键词生成、持久化游标恢复、Worker 自动续检、运行日志与验收测试。

### D021｜RedFox API Key 支持用户级安全替换并优先使用

- **日期**：2026-08-31
- **结论**：找达人页面展示 RedFox Key 来源状态，并允许登录用户配置或替换自己的 API Key；用户级 Key 以 AES-256-GCM 加密保存到 `private` schema，仅返回不可逆短指纹，运行时优先于系统默认 Key。余额不足时保留现有检索游标，替换 Key 后由用户再次点击“开始检索”继续，不重复筛查项目历史达人。
- **安全边界**：原始 Key 不写入浏览器持久化、URL、任务 payload、任务结果、项目文档或日志；API 不回显原始 Key；数据库表不向 `anon`/`authenticated` PostgREST 角色开放，仅可信 API 与 Worker 通过数据库直连访问。
- **运行边界**：Worker 在每个新达人任务开始时重新读取 `.env.local` 的系统 Key，解决修改系统 Key 后必须重启 Worker的问题；已经运行中的外部请求不热切换 Key，新 Key 从下一任务生效。用户级 Key 保存后不需要重启 API 或 Worker。
- **影响范围**：找达人页面、Fastify 凭据 API、Worker RedFox 客户端配置、Supabase 私有迁移与凭据安全测试。

### D022｜共享任务队列只允许一个当前 Worker 实例

- **日期**：2026-08-31
- **结论**：Worker 启动时必须取得 PostgreSQL connection-scoped advisory lock；未取得锁的重复实例立即正常退出，不得参与 `private.jobs` 轮询。每个达人任务结果记录 Worker 运行时版本、RedFox Key 来源、不可逆短指纹和实际搜索端点，禁止记录原始 Key。
- **理由**：本机同时存在 00:25 启动的旧 Worker 和 21:55 启动的新版 Worker。旧 Worker 不支持用户级 Key 且默认走旧 `xhsUser/searchArticle` 端点，却持续与新版 Worker 抢共享队列；用户替换 Key 后的最近任务被旧实例领取，实际使用余额为 0 的系统 Key，造成“个人 Key 已替换但仍提示余额不足”。
- **验证**：清理重复进程后仅保留新版 Worker；同一用户个人 Key 指纹直连实时 `xhs/ability/searchWork` 成功；第二个新版 Worker 实例实测因 advisory lock 立即退出；全量测试 59/59、类型检查、Lint 和生产构建通过。
- **影响范围**：Worker 进程管理、任务领取、RedFox Key 路由、运行日志、故障诊断和部署说明。

### D023｜只放宽淘汰人数最多的一个硬条件，再评分取 20 人

- **日期**：2026-09-01
- **结论**：每次检索先在首轮跨主题候选池统一统计粉丝、近期点赞、近 30 天发帖数、最近发帖时间四类已启用硬条件的淘汰人数，只放宽淘汰人数最多的一项；其他已启用硬条件与内容语义匹配继续严格淘汰。通过候选门槛的达人按综合评分降序取前 20，不用低相关或语义不匹配账号凑数。
- **质量约束**：首轮至少轮询 8 个不同主题页，关键词按项目/皮肤问题轮转，避免前置关键词过早占满名额；放宽项未达标会在匹配证据中明确标记并降低评分。硬条件淘汰数相同时优先放宽近期点赞条件，以保留粉丝范围对投放匹配度的约束。
- **续检边界**：首轮严格门槛通过者不足 20 时，沿同一游标继续检索并补足；语义不匹配、其他硬条件失败、项目历史重复和资料不可判断对象仍不入选。RedFox 数据耗尽、真实限流/余额不足或整任务安全上限仍是允许不足 20 的终止条件。
- **影响范围**：关键词轮转、RedFox 分页计划、候选门槛、综合评分、证据文案、检索会话版本与回归测试。

### Q001｜小红书实时数据链路的可行实现方式

- **日期**：2026-08-13
- **状态**：2026-08-17 首轮技术门已通过；连接服务产品化和稳定性仍在 T06 内继续验证。
