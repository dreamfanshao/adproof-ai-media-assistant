# 视觉模型连通性测试与验收手册

## 1. 文档信息

- 项目：媒介助手
- 测试对象：模型管理中的视觉模型连接
- 当前模型：`deepseek-v4-flash-vision-exp`
- 测试入口：`http://127.0.0.1:3081/models/creators`
- 测试接口：`POST /api/model-config/test`
- 最近验证日期：2026-09-02
- 测试性质：真实模型调用，会产生 API 用量

## 2. 测试目标

确认以下链路可以正常工作：

1. Eval 服务能读取视觉模型配置和对应的 API Key 环境变量。
2. 服务端能构造符合 OpenAI Chat Completions 格式的多模态请求。
3. 测试请求包含一张完整、受支持的图片，而不是损坏的占位数据。
4. DeepSeek 能成功处理图片并返回可解析的 JSON。
5. 模型管理页面能正确展示成功结果或具体错误原因。
6. 修复不会破坏 Eval 测试和 TypeScript 编译。

## 3. 本次故障记录

### 3.1 故障现象

在模型管理页面点击“测试视觉模型”后，页面显示：

```text
ERROR: 请求失败
```

本地测试接口返回 HTTP 502，内部模型结果为：

```json
{
  "status": "error",
  "model": "deepseek-v4-flash-vision-exp",
  "note": "deepseek HTTP 400",
  "provider": "deepseek",
  "fallbackUsed": false
}
```

DeepSeek 的实际错误响应为：

```text
You have uploaded an unsupported image. Please make sure your image is valid
and has one of the following formats: webp, png, jpeg, and gif.
```

### 3.2 根因

视觉连通性测试在没有上传图片时，使用了下面的默认值：

```text
data:image/png;base64,iVBORw0KGgo=
```

该 Base64 解码后只有 8 字节，仅包含 PNG 文件签名，不是一张完整图片，因此被模型接口拒绝。失败与 API Key 额度无关，也不是模型路由错误。

### 3.3 修复内容

1. 将残缺占位数据替换为完整、有效的 1×1 PNG。
2. 当模型调用失败时，接口在 `data.error` 中返回具体错误，不再只显示笼统的“请求失败”。
3. 增加自动化测试，校验默认测试图片：
   - MIME 类型是 `image/png`；
   - Base64 可解码；
   - 文件长度大于 PNG 文件签名；
   - 前 8 字节符合 PNG 标准签名。

相关代码：

- `eval/model-routes.ts`
- `eval/test/runtime-alignment.test.ts`

## 5. 标准测试流程

### 5.1 启动或重启 Eval 服务

在项目目录执行：

```powershell
npm run eval:server
```

如果端口已经被旧进程占用，应先确认占用 `3081` 的确实是本项目 Eval 进程，再停止旧进程并重新启动。不要结束来源不明的进程。

通过标准：

- `http://127.0.0.1:3081/models/creators` 可以打开；
- 页面能显示文本模型和视觉模型配置；
- 页面没有 `Bad Request` 或服务不可用提示。

### 5.2 运行静态检查

执行：

```powershell
npm run typecheck
```

通过标准：命令退出码为 `0`，无 TypeScript 错误。

### 5.3 运行 Eval 回归测试

执行：

```powershell
npm run test:eval
```

通过标准：

- 所有测试通过；
- `vision connectivity test uses a complete PNG fallback image` 测试通过；
- 不存在 `fail`、`cancelled` 或 `skipped`。

2026-09-02 实测结果：`7/7` 通过。

### 5.4 直接测试后端接口

此步骤绕过页面，用于判断问题在模型调用链路还是前端展示层。执行：

```powershell
node -e "fetch('http://127.0.0.1:3081/api/model-config/test',{method:'POST',headers:{'content-type':'application/json'},body:JSON.stringify({target:'vision',prompt:'Return JSON with ok true after viewing the image.'})}).then(async r=>console.log('STATUS='+r.status+'\n'+await r.text())).catch(e=>{console.error(e);process.exit(1)})"
```

通过标准：

- HTTP 状态码为 `200`；
- `result.status` 为 `scored`；
- `result.model` 为当前配置的视觉模型；
- `result.provider` 为 `deepseek`；
- `result.data.ok` 为 `true`；
- `fallbackUsed` 为 `false`。

参考成功响应：

```json
{
  "data": {
    "target": "vision",
    "result": {
      "status": "scored",
      "model": "deepseek-v4-flash-vision-exp",
      "data": {
        "ok": true,
        "message": "连接成功"
      },
      "provider": "deepseek",
      "fallbackUsed": false
    }
  }
}
```

### 5.5 页面端到端测试

1. 打开 `http://127.0.0.1:3081/models/creators`。
2. 找到“视觉模型”区域。
3. 确认连接状态显示环境变量已存在。
4. 点击“测试视觉模型”。
5. 等待“正在连接模型……”消失。
6. 检查结果区域。

通过标准：

- 页面不再显示 `ERROR: 请求失败`；
- 结果中包含 `status: scored`；
- 结果中包含 `ok: true`；
- 模型名称、Provider 与当前配置一致；
- `fallbackUsed` 为 `false`；
- 浏览器控制台没有 JavaScript 错误。

2026-09-02 页面实测返回：`ok: true`、`message: 连接成功`，浏览器控制台错误数为 `0`。

### 5.6 检查接口日志

在后台管理的接口数据页面筛选：

- 提供方：`deepseek`
- 状态：成功或错误

通过标准：

- 成功测试应产生一条 `/chat/completions` 成功日志；
- 请求应标记为多模态调用；
- 日志不得显示 API Key 明文；
- 如果失败，响应中应保留供应商返回的具体错误，便于区分图片、模型、鉴权、额度和网络问题。

## 6. 结果判定

只有同时满足以下条件，视觉模型测试才算通过：

| 检查项 | 通过条件 |
| --- | --- |
| 服务状态 | Eval 页面可访问 |
| 类型检查 | `npm run typecheck` 退出码为 0 |
| 回归测试 | `npm run test:eval` 全部通过 |
| 后端接口 | HTTP 200 |
| 模型结果 | `status=scored` 且 `data.ok=true` |
| 模型路由 | 模型和 Provider 与配置一致 |
| 降级状态 | `fallbackUsed=false` |
| 前端展示 | 页面显示成功结果，无泛化错误 |
| 浏览器状态 | 控制台无 JavaScript 错误 |
| 安全检查 | 页面和日志均不暴露 API Key |

任一关键项失败，都不能判定整体通过。

## 7. 常见失败与排查顺序

### 7.1 HTTP 400：unsupported image

优先检查：

1. 图片 Data URL 是否完整；
2. MIME 类型是否为 `image/png`、`image/jpeg`、`image/webp` 或 `image/gif`；
3. Base64 是否能正常解码；
4. 解码结果是否包含完整图片，而不只是文件头。

### 7.2 HTTP 401 或 403

优先检查：

1. `DEEPSEEK_API_KEY` 是否存在；
2. 修改 `.env.local` 后是否重启 Eval 服务；
3. API Key 是否有效、是否有权调用当前模型。

注意：`.env.local` 是进程启动时读取的。仅刷新浏览器不会让已经运行的 Node 进程重新读取新 Key。

### 7.3 HTTP 404 或模型不存在

检查模型名称和 Base URL 是否匹配当前供应商配置。不要通过猜测更换模型名称，应以供应商实际可调用结果为准。

### 7.4 HTTP 429

检查额度、限流和并发。等待限流窗口结束后只重试一次，避免页面连续点击造成重复扣费。

### 7.5 HTTP 502 且页面只显示“请求失败”

检查接口返回体是否包含：

```json
{
  "data": {
    "error": "具体错误",
    "result": {}
  }
}
```

如果服务端已有具体错误而页面仍显示泛化文本，应排查前端接口错误解析逻辑。

### 7.6 请求超时

检查：

1. `LLM_TIMEOUT_MS` 是否合理；
2. 当前网络能否访问模型 Base URL；
3. 接口日志中是否记录 `request timeout`；
4. 是否错误触发了文本降级。

连通性验收要求 `fallbackUsed=false`，通过文本降级得到结果不能算视觉模型通过。

## 8. 回归要求

发生以下变更后必须重新执行本手册第 5 节：

- 更换视觉模型；
- 更换 Provider 或 Base URL；
- 更换 API Key 环境变量；
- 修改多模态消息格式；
- 修改 `routeFor` 模型路由；
- 修改视觉降级逻辑；
- 修改模型管理页面的测试按钮或接口错误处理；
- 修改默认测试图片。

为控制成本，普通代码变更先运行静态检查和自动化测试；只有涉及模型、路由、图片或请求格式时，才执行真实接口和页面端到端测试。
