## 一、结论与上线门槛

**本地发布构建及预检工具已完成，暂不建议直接公开开放注册。** 先完成安全整改和受控预发布验收，再邀请少量真实用户。

本轮没有修改 `.env.local`、密钥、证书或 CI/CD；没有推送代码、迁移线上数据库、购买资源或重启当前业务任务；未调用 RedFox/模型业务接口。

### 仍未通过的上线条件

1. **安全依赖**：本次 `npm audit --omit=dev --json` 报告 8 high / 2 moderate，共 10 个依赖条目，包含依赖链重复计数，不等于 10 条独立可利用漏洞。涉及 Fastify、fast-uri 依赖链、mammoth/xmldom、xlsx。必须核实可达路径、升级修复版本或替换，再回归；不能直接 `npm audit fix --force`。本轮没有批量升级依赖。
2. **国内可用性**：浏览器仍直连 Supabase Auth，部分上传/签名 URL 链路也依赖 Supabase。前端放大陆不代表全部业务都在大陆，必须不用 VPN 实测。
3. **生产 Auth、SMTP、域名**：真实验证邮件和正式域名回跳未验收。
4. **数据迁移与备份还原**：生产项目、RLS/Storage 隔离、完整迁移和恢复演练待确认。
5. **公开运营安全**：现有检索可能长时间持续；本轮未改变用户选定的预算策略。开放注册前需明确用户额度、并发公平性、费用告警和应急取消，API 请求频控不等于单任务消费限制。
6. **业务质量**：本轮没有跑真实找达人全流程，不承诺稳定返回 20 个合格达人。人工验收粉丝硬门槛、语义证据、排重、实际新增数、耗时和费用后才开放。

xlsx 当前检索到的生产调用用于导出，不是解析任意 Excel；这影响漏洞可达性，但不能直接忽略告警。

## 三、部署范围

```text
国内用户 → HTTPS 443 → Nginx → dist 静态页面
                         └→ /api/v1 → 127.0.0.1:3001 API
浏览器 → Supabase Auth/必要的 Storage 请求（国内连通性待测）
API → Supabase 数据库/Storage
单 Worker → 同一数据库队列 → RedFox / 配置的文本与视觉模型
本地 Eval 3081：不上公网、不随发布包上线
```

安全组公众只开 80/443；22 仅你的固定出口 IP；不开放 3001、3081、3092、5173、5432、6543。

Supabase 必须使用 direct 或 **session pooler**。Worker advisory lock 是连接级锁，不适合 transaction pooler；不仅看端口，还要在 Connect 页面核实模式。参考[官方数据库连接说明](https://supabase.com/docs/guides/database/connecting-to-postgres)。

## 四、按顺序部署

以下是部署时供操作者执行的步骤，本轮未执行。账号、路径、域名先核对；上线、密钥/证书配置、数据库变更需你明确批准。

### 1. 准备服务器

安装系统安全更新、Nginx、Node.js 24。用 `node --version` 和 `command -v node` 确认模板中的 `/usr/bin/node` 与实际路径一致。不能用 Vite 开发服务器或 preview 代替 Nginx。

仅在新服务器创建专用账号和目录：

```bash
sudo useradd --system --home /var/lib/adproof --shell /usr/sbin/nologin adproof
sudo install -d -o root -g root -m 755 /opt/adproof/releases
sudo install -d -o root -g adproof -m 750 /etc/adproof
sudo install -d -o adproof -g adproof -m 700 /var/lib/adproof
sudo install -d -o adproof -g adproof -m 700 /var/lib/adproof/api-analytics /var/lib/adproof/worker-analytics
```

### 2. 准备数据库与认证

1. 建立生产 Supabase 项目。本地测试项目继续保留，避免本地/线上 Worker 争用同一把锁。
2. 在可信终端核对 Supabase 目标项目，执行 `npm run db:migrations`、`npm run db:push:dry`。确认备份与变更后，经批准执行 `npx supabase db push`。不运行 `db reset`，不在服务启动时自动迁移。特别检查反馈表、检索会话、筛查历史及 execution_timeout/loop_limit 枚举迁移。
3. Auth 配置正式 Site URL、实际回跳 Redirect URLs，清理无关开发地址和宽泛通配。
4. 配置自定义 SMTP、发信域名验证和限流，真实测试非项目成员邮箱。默认 SMTP 不是生产邮件服务，见[Supabase 官方说明](https://supabase.com/docs/guides/auth/auth-smtp)。不要关闭邮箱验证绕过故障。
5. 验证 RLS 与私有 Storage：用户 A 不能读取 B 的项目、反馈、私有知识库和审核数据。预检只检查部分表开启 RLS，不替代权限策略测试。
6. 新生产库单独初始化公共知识库并核对内容/版本；不要将本地所有业务历史整库混入。

### 3. 配置生产环境

服务模板从 `/etc/adproof/runtime.conf` 读取 `KEY=value`。用安全编辑器/密钥工具填写，文件 root 所有、adproof 组可读（640）。不直接复制开发 `.env.local`，不上传 GitHub，不发送内容给聊天。

| 变量 | 生产要求 |
| --- | --- |
| NODE_ENV | production |
| API_HOST / API_PORT | 127.0.0.1 / 3001 |
| WEB_ORIGINS | 真实 HTTPS origin，无路径、尾斜杠或通配 |
| SUPABASE_URL / SUPABASE_PUBLISHABLE_KEY | 生产项目地址和公开 Key |
| SUPABASE_SERVICE_ROLE_KEY | 仅服务端，禁止 VITE_ 前缀 |
| DATABASE_URL | direct/session 连接，要求 sslmode=verify-full；正确 URL 编码特殊字符密码 |
| XHS_SESSION_ENCRYPTION_KEY | 32 字节，64 hex 或合法 base64；迁移已有加密数据必须保留原密钥并安全备份 |
| REDFOX_API_KEY | 服务端系统默认 Key；个人 Key 按原规则优先 |
| 模型 Key | 按 agent/data/model-config.json 的 text.apiKeyEnv、vision.apiKeyEnv 配置，不凭标签猜测 |
| NODE_EXTRA_CA_CERTS | 仅证书链需额外可信根时设置官方 CA 的绝对路径；不要设 NODE_TLS_REJECT_UNAUTHORIZED=0 |

生产系统 Key 改动后重启 API/Worker 才读取新的进程环境。前台保存的个人 Key 仍在新任务读取。既有检索预算/轮数策略本轮没有改变。

构建时另提供 `VITE_SUPABASE_URL`、`VITE_SUPABASE_PUBLISHABLE_KEY`、`VITE_API_BASE_URL=/api/v1`。它们固化到前端，切换项目必须重新构建，不是刷新就生效。

### 4. 修复安全依赖、构建、上传

先解决第一节依赖告警并核实锁文件。在干净构建环境执行：

```bash
npm ci
npm run typecheck
npm run lint
npm run test:release
npm run test:server
node scripts/test/run-compiled-worker-tests.mjs
npm audit --omit=dev
npm run build:release
node scripts/test/smoke-release.mjs
```

`npm ci` 会重建依赖目录，只在干净构建环境执行。提供生产 VITE 变量，不修改开发密钥文件。编译 Worker 测试入口用于规避本机 tsx 启动时报 `uv_os_get_passwd ENOMEM`，这不是业务断言失败。

把 `.release/<时间>/` **目录内容**上传到新的 `/opt/adproof/releases/<release-id>/`。不传 Windows node_modules、整个源码目录、日志或 `.env.local`。在服务器该目录执行 `npm ci --omit=dev` 安装 Linux 依赖，并再次审计。默认 RedFox 链路不安装浏览器；若恢复浏览器采集须另做 Linux/Playwright 验收。

发布包 `release.json` 标记 UNVERIFIED_ON_TARGET，不是上线通过凭证。

### 5. 目标机器预检与权限

核对该发布目录的 agent/data 归 adproof 所有，目录 700、文件 600，可供 Worker 写运行记录；其余发布文件只读，dist 可供 Nginx 读取。目录不能位于公开静态根下。

进入新的发布目录执行：

```bash
sudo -u adproof /usr/bin/node --env-file=/etc/adproof/runtime.conf scripts/check-release.mjs --database
```

预检只读：验证文件、生产配置、模型 Key 变量、前后端 Supabase URL、前端密钥泄漏、已应用迁移、部分核心表 RLS，以及是否还有 queued/running 任务。runtime.conf 必须含 NODE_ENV=production，手动运行不享有 systemd 的额外变量。检查不代表模型余额/视觉能力、邮件或 Worker 活性验证通过。

首次建立 `/opt/adproof/current` 指向验证过的发布目录。升级先停止新提交、确认队列空、停止旧服务，再切换 current。保留旧发布，不覆盖或删除。长任务运行中不能直接换软链接。

### 6. 启动 API 与 Worker

核对并安装 deploy 目录两个 service 文件至 `/etc/systemd/system/`，再执行：

```bash
sudo systemd-analyze verify /etc/systemd/system/adproof-api.service /etc/systemd/system/adproof-worker.service
sudo systemctl daemon-reload
sudo systemctl enable --now adproof-api adproof-worker
sudo systemctl status adproof-api adproof-worker
curl --fail http://127.0.0.1:3001/api/v1/health
curl --fail http://127.0.0.1:3001/api/v1/ready
sudo journalctl -u adproof-worker -n 50 --no-pager
```

必须确认 Worker 已成功持有单实例锁。如果提示已有 Worker，查本地或旧服务器是否还连同一个库。API 返回 200 不能证明任务会被执行。

### 7. HTTPS 与 Nginx

1. 修改 deploy/nginx.conf.template 中域名、证书路径，安装有效证书并配置续期、失败提醒。
2. 未签发证书时先用受控 HTTP ACME 站点或 DNS 验证；不要加载指向不存在证书的 443 配置。
3. 人工启用站点后先 `sudo nginx -t`，成功才 reload。现有默认站点是否停用需核对，不自动删除。
4. HTTPS 打开 /login，直接访问并刷新 /creators 正常；/admin、/eval、/api/admin/feedback、/.env.local 均不可公开访问。
5. 只有 /api/v1/ 转发至 API；SSE 禁止缓存/缓冲。代理超时不等于检索总时长限制，页面刷新恢复要真实验证。

### 8. 真实预发布验收，再少量开放

| 验收 | 操作和通过标准 |
| --- | --- |
| 国内网络 | 至少两种国内运营商、不用 VPN，记录首页/注册/登录/上传/SSE 速度与失败率；慢在 Supabase 时不只优化 Nginx |
| 账号 | 两个非项目成员邮箱注册、收最新验证邮件、回跳正式域名、登录/刷新/退出；找回密码按实际支持功能验证 |
| 隔离 | A 创建项目、私有文档、反馈，B 通过界面和 API 都读不到；未登录受保护 API 返回 401 |
| 检索 | 一个真实任务：有日志、被领取、刷新恢复、不重复启动；粉丝严格、语义有证据、排重、实际新增数正确；不足 20 有真实终止原因，不能凑数 |
| Key | 前台保存个人 Key 后新任务使用它，只核对脱敏指纹，不打印原值 |
| 知识库/审核 | 小文档解析为 ready、内容可见，真实图文审核带来源与人工复核提示 |
| 反馈/导出 | 提交刷新后反馈保留；通过受控运维渠道查看；Excel 中文与范围正确、不含他人数据 |
| 恢复 | 无任务时先验证重启，再在隔离环境验证任务租约恢复/取消，不把页面恢复当任务已结束 |
| 异常 | 在隔离环境验证供应商超时/余额不足/数据库中断，用户提示明确、日志脱敏 |

## 五、运维、备份与回滚

- 监控 HTTPS、内部 ready、systemd、队列最长等待/心跳、错误率、磁盘、证书到期、供应商余额与费用。未接入外部告警前，不宣称自动告警已完成。
- API/Worker 的 ADPROOF_ANALYTICS_DIR 分开，避免两个进程读改写同一个 JSON 造成丢日志。当前 Eval 读日志依赖本地目录，生产统计整合需要单独处理，不能说公网后台已打通。
- Eval 不部署公网。要团队在线管理，先做独立管理员认证、角色和审计；不能把“本地免 token”直接搬到公网。本轮没有创建生产远程管理后台。
- 分别备份数据库、Storage 实际对象、加密密钥、模型/Skill 配置；做一次隔离环境恢复，确认文件可下载、密文可解密。数据库备份不含 Storage 二进制，见[官方备份说明](https://supabase.com/docs/guides/platform/backups)。
- 回滚：维护窗口停止新请求，处理当前任务，停 API/Worker，current 切回保留的旧发布，重新预检并启动。数据库迁移不随代码盲目回滚，先判断兼容；不可逆操作走恢复方案。
- Worker 正常退出等待当前任务；systemd 配置 900 秒后仍可能强杀。发布应安排在空闲时；强杀后需验租约和重复调用，不承诺零重复消费。
