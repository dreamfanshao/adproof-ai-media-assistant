## 本次增补 A｜产品壁垒与增长判断

### Q100｜大模型越来越强，你的 AI 应用还有什么价值？

考察点：能否区分模型能力与产品价值；关联旧题 Q21、Q24、Q61。题目角度参考 N1，答案按你的项目重新组织。

记忆提纲：承认能力会下放 → 看完整任务 → 积累有效反馈 → 用复用和成本验证。

主回答：如果我的产品只是把用户输入转发给模型，再换一个界面展示答案，那确实很容易被替代。以媒介助手为例，我更关注的是媒介能不能完成一次真实工作：把需求变成筛选条件，拿到有依据的候选名单，再完成内容初审和人工确认。这里除了模型理解能力，还涉及数据可用性、团队规则、候选状态和工作交接。后续真正值得积累的是用户为什么选或不选某个达人、哪些审核结论被纠正，以及这些反馈能不能持续改善下一次结果。但我不会把现在的小项目直接说成已经有壁垒。目前更准确的定位是验证一个细分工作流，先证明用户愿意重复使用，再谈数据和流程积累形成的优势。

追问1：通用大模型也接入搜索、文件和工具了，你凭什么让用户留下？

追问提纲：同任务对比 → 看补救工作 → 不满足就调整定位。

答：我会拿同一份真实需求做对照，不只比较回答看起来好不好，而是比较完成名单和审核需要多少人工操作、结果能否核实、下一位同事能否接手。如果通用产品已经能低成本完成这些事，我就需要缩小到它还没解决好的环节，或者放弃没有差异的功能，不会为了保住项目硬说自己有优势。

追问2：用户使用数据越多，就一定能形成数据壁垒吗？

追问提纲：有权使用 → 反馈有质量 → 能改善结果。

答：不一定。大量点击记录不等于有用的业务反馈，而且客户数据也不能默认跨客户复用。我更看重有授权、有明确任务背景的选择和纠正记录，能不能解释错误、进入评测，并证明下一版有改善。没有这一层验证，数据只是越存越多。

备考备注：不把工作流、知识库或历史数据本身说成已建立商业壁垒；本题是产品判断，不是融资路演。

### Q101｜AI 产品增长慢，你怎么选一个细分场景突破？

考察点：从总体增长问题转向可验证的垂类选择；关联 Q45、Q68、Q86。角度参考 N6。

记忆提纲：先拆增长环节 → 按任务分人群 → 看痛点与供给 → 小范围验证。

主回答：我不会一看到增长慢就马上换赛道。先看是合适的人没进来，还是进来后没完成任务，或者完成一次后没有再用。然后按用户任务分组，而不只是按年龄、城市分。放到媒介助手里，可以比较不同类型的媒介需求：哪类任务重复发生、人工筛选负担重，且现有数据和审核规则能支持。选突破口时，我会一起看痛点强度、触达难度、数据可获得性和交付成本。先选一个边界清楚的场景，跑通从需求到采用的链路，观察完成率、人工返工、下一次任务复用和付费意愿。只有这些表现比其他场景更扎实，才扩大投入，不能因为某一类注册数多就认定找到了方向。

追问1：样本少，几个用户都说好，可以集中资源了吗？

追问提纲：态度不等于行为 → 增加独立样本 → 分阶段投入。

答：可以作为继续验证的信号，但还不足以重押。我会看他们有没有带着真实任务回来、是否愿意花时间接入，以及使用时卡在哪里。也要补一些不是朋友介绍的目标用户，避免关系带来的好评。资源先小步增加，并提前约定继续和停止的条件。

追问2：客户提出很多定制需求，怎么判断是不是值得做的垂类？

追问提纲：共同问题与个性规则拆开 → 看复用 → 算交付负担。

答：我会把需求拆成共同流程和个性配置。如果多个客户只是规则不同，但核心任务一致，可以做配置化；如果每家都要改一套核心逻辑，可能更像项目交付生意。两种模式都可能成立，但要明确收入能不能覆盖持续交付和维护成本，不能用 SaaS 的规模化预期包装定制开发。

备考备注：本题不要求声称已做过增长实验；面试可用“如果进入推广阶段，我会……”开头。

### Q102｜多个 AI 功能共用入口，怎么判断各自带来的增量？

考察点：功能归因、替代效应和实验意识；关联 Q47、Q91、Q93。角度参考 N1。

记忆提纲：统一最终目标 → 补全功能路径 → 区分使用与增量 → 看组合效果。

主回答：我会先定义共同的业务结果，再看每个功能在链路里扮演什么角色。比如候选筛选和内容初审共用一个入口，功能点击次数不能直接相加当贡献，同一位用户也可能连续使用两个功能。埋点上需要串起用户、任务和版本，记录曝光、进入、完成以及最终采用。数据量足够时，可以用稳定分组的实验比较“只有筛选”和“筛选加初审”，同时观察任务完成、返工和整体成本。如果两个功能互相依赖，就测组合，不强行把价值拆成精确百分比。流量不足时先做分批试点和任务回访，但明确这只是方向性证据，不把相关性说成因果。

追问1：新增功能使用率很高，但总留存没提升，要下线吗？

追问提纲：看是否替代 → 看目标人群 → 看其他价值。

答：先看它是不是替代了原来的操作，以及它解决的任务本来多久发生一次。如果让用户更快完成同样的任务，访问次数减少不一定是坏事。但如果没有改善完成质量、耗时或付费，反而增加干扰和成本，就需要缩减入口或重新设计。不能只拿一个留存数字直接判生死。

追问2：老板一定要你报“这个功能贡献了多少增长”呢？

追问提纲：区分可算指标 → 给不确定范围 → 说明补证方案。

答：我会把能直接观测的任务数、采用数先报清楚，再说明这些不等于净增量。有对照实验就报估计增量和不确定性，没有就给关联表现及影响判断的因素。我可以承诺补验证，但不会为了让报告完整，给一个看似精确、其实没有依据的贡献比例。

备考备注：讨论的是功能增量，不是把最后一次点击当成真实因果归因。

### Q103｜AI 素材播放和互动都不错，但转化很差，你怎么判断？

考察点：内容指标和业务结果的区别；关联 Q86、Q92。角度参考 N1；题目迁移到媒介业务，不代表你做过投放增长。

记忆提纲：核对归因 → 拆转化漏斗 → 查人群与承诺 → 单变量验证。

主回答：我先确认转化统计有没有漏数，归因窗口是否一致，以及订单结果是不是还没成熟。排除口径问题后，再把曝光、有效观看、点击、落地页到达和下单拆开看。播放高但点击低，可能内容有趣，却没有吸引到目标人群，或者产品利益点不清楚；点击高但下单低，就要继续看页面承接、价格、信任和商品本身。放到达人选择上，我也不会只按粉丝量和互动率推荐，要看内容受众与目标客户是否匹配。后续优先验证最明显的断点，在人群和投放条件尽量一致时改一个关键因素，而不是同时改素材、达人和价格，最后不知道哪个起作用。

追问1：内容团队坚持说播放数据证明素材已经成功了，怎么沟通？

追问提纲：承认局部成功 → 对齐活动目标 → 分开承担责任。

答：我会先认可素材吸引注意力这一点，再确认这次活动的目标是品牌曝光还是销售。如果目标是销售，播放只是前置指标，需要一起看后面的链路。我也不会把所有转化问题都归给内容团队，商品和页面的问题要由对应负责人一起排查。

追问2：怎么证明不是模型生成的素材有问题？

追问提纲：模型版本只是维度 → 可比对照 → 看误差与成本。

答：不能靠几条素材证明。可以在相近人群、预算、时段和商品条件下，比较 AI 辅助与原流程产出的素材；同时记录人工修改和制作成本。即使结果有差异，也要排除投放分配不均和样本不足。最后判断的是这套生产方案有没有业务收益，而不是给模型贴好坏标签。

备考备注：高互动不能直接作为内容审核“准确”或达人带货能力强的证明。

## 本次增补 B｜Agent 架构与企业落地

### Q104｜你的场景为什么不用多 Agent？什么时候值得用？

考察点：复杂度取舍，而非堆架构名词；关联 Q15、Q41、Q52。角度参考 N1；概念核对 T1、T2。

记忆提纲：先有简单基线 → 判断任务能否独立 → 算协调代价 → 用评测决定。

主回答：我不会因为有搜索、筛选和审核三个步骤，就把它们都叫三个 Agent。如果步骤固定，工作流加工具调用通常更容易控制；如果需要根据检索结果不断调整动作，可以先用一个 Agent 配合工具。多 Agent 更值得考虑的情况，是任务确实可以独立拆开，各自需要不同上下文或权限，并且并行或专业分工能带来明显收益。以媒介助手为例，不同候选的资料分析可能适合并行，但最终是否入选、是否需要人工复核，仍要有统一规则。我会拿同一批任务比较完成质量、响应时间、调用成本和冲突率，只有收益覆盖了协调、排障和维护成本，才增加架构复杂度。

追问1：给生成 Agent 再加一个审核 Agent，就能保证正确吗？

追问提纲：可能同错 → 加外部依据 → 关键结果仍有兜底。

答：不能。两个 Agent 如果用相似模型和同一份错误资料，可能一起判断错。审核需要有独立标准、可查的证据和规则校验；涉及风险内容还要保留人工确认。我会验证审核环节实际拦住了哪些错误，也关注它新增了多少误报和成本。

追问2：多 Agent 比单 Agent 慢，是否说明方案失败？

追问提纲：按任务容忍度 → 看最终有效产出 → 允许异步。

答：不一定。如果用户本来就愿意等一份深度研究结果，质量明显提高，慢一些可能可以接受。但如果只是查一个达人信息，复杂协作让用户多等很久，就不值得。是否采用取决于任务价值和体验要求，而不是单独追求速度或架构先进。

备考备注：并行调用不必然等于多 Agent；不要将此方法回答表述成自己的项目已经实现多 Agent 编排。

### Q105｜工具调用有少量失败，可以上线吗？你怎么设验收线？

考察点：风险分层与端到端验收；关联 Q95、Q96。角度参考 N1。

记忆提纲：先分失败后果 → 分层看成功 → 查连续任务 → 明确恢复与拦截。

主回答：我不会先拍一个统一成功率。检索失败让用户重试一次，和付款工具重复执行，风险完全不同。验收至少分三层：请求有没有正常返回，参数和业务校验是否通过，以及用户的任务是否真正完成。搜索类失败可以有限重试或换来源，但要把结果缺失讲清楚；涉及外发、资金或数据修改的操作，要有权限、确认、幂等和执行后核对。还要看一条任务连续调用多次后，有多少能完整跑通。具体上线门槛由业务、研发和相关风险负责人一起确定，并配套灰度、告警和暂停机制，不能拿全链路平均成功率掩盖一个高风险节点。

追问1：假设每一步成功率都是 99%，十步任务整体大概是多少？

追问提纲：先讲假设 → 连乘约 90.4% → 真实链路单独量。

答：如果每一步独立、十步都必须成功、也没有重试，整体约是 0.99 的十次方，也就是 90.4%。但现实里的失败可能来自同一个上游故障，并不独立，还会有重试和降级。所以这个计算用来提醒大家不能只看单步指标，真正的任务成功率仍要用实际执行链路来测。

追问2：付款调用超时，Agent 应不应该自动再调一次？

追问提纲：超时不等于未付款 → 查状态 → 幂等恢复或人工处理。

答：不应该直接重付。超时只说明没有及时拿到结果，款可能已经付出去了。先通过业务单号查询状态，并用幂等机制避免重复执行；状态仍不明确时挂起给人工处理。我的资金系统经历让我比较关注这种“结果未知”的状态，它不能简单当作失败。

备考备注：99% 和十步为计算示例，不是项目实测数据；这道追问可用豪森的异常规则经验支撑判断。

### Q106｜企业 Agent 和个人 Agent，产品设计的重点有什么不同？

考察点：采购、使用、管理三类角色及组织落地；关联 Q26、Q49、Q61。角度参考 N4。

记忆提纲：谁买谁用谁负责 → 接入原流程 → 权限与验收 → 分层看价值。

主回答：我理解最大的区别，不是一个界面复杂、一个界面简单，而是企业产品里付钱的人、每天使用的人和承担风险的人可能不是同一批人。员工希望少录入、少切系统，管理者关心交付效率和可追溯，IT 关心权限、集成和维护。所以企业 Agent 不能只演示回答得好，还要说明怎么进入原有流程、错误由谁处理、结果如何验收。个人产品更需要快速让用户完成第一件事，降低理解和使用门槛，但同样要重视隐私和可靠性。结合我以前做资金系统的经历，我会先画清角色、数据边界和审批责任，再做低风险任务试点，分别看使用者是否省事、管理者是否获得价值，而不是只看有没有完成部署。

追问1：客户老板很喜欢，但员工不愿意用，怎么处理？

追问提纲：观察实际工作 → 找额外负担 → 试点改流程。

答：我会去看员工完成任务的过程，判断是不是多了一次录入、结果还要反复核对，或者大家担心出错后自己负责。先减少这些真实负担，明确人机责任，再让愿意尝试的小组跑一轮。只靠管理要求提高登录率，很难形成持续使用。

追问2：企业客户让你把所有业务数据都接进来，方便回答，怎么办？

追问提纲：按场景接入 → 最小权限 → 检索与操作都校验。

答：我会先问清要解决哪些任务，只接这些任务需要的数据和字段。权限要跟着用户和组织走，不能因为模型能查就默认所有人都能看。查询、生成结果和工具操作都要考虑越权与审计；敏感信息不应该仅靠 Prompt 里写一句“不要泄露”来保护。

备考备注：这是基于 ToB 项目经历形成的设计思路，不宣称已经交付企业级 Agent 权限平台。

### Q107｜让 Agent 主动监测变化并提醒用户，你会怎么设计？

考察点：从一次回答走向持续任务；关联 Q41、Q52、Q96。角度参考 N4 的持续通知场景，以下改为媒介业务演练。

记忆提纲：确认监测约定 → 可靠数据与调度 → 去重分级 → 可暂停可解释。

主回答：我会先把一句“有变化提醒我”变成明确约定：监测哪些对象、什么变化值得提醒、持续多久、通知谁以及通过什么渠道。比如候选达人在合作前出现新的风险内容，系统需要有合规的数据来源和固定检查机制，而不是让模型一直循环猜测。每次检查把最新数据与上次状态比较，确认有实质变化后，再由模型做必要的语义判断和摘要。产品上要处理重复提醒、安静时段、严重程度和用户取消，还要展示最近一次成功检查时间。数据源失败时不能把“没查到”显示成“没有变化”。提醒量不是成功指标，我更关注重要变化是否及时发现、是否误报，以及用户有没有采取有效行动。

追问1：用户说“只提醒重要的”，你怎么理解重要？

追问提纲：先给可选标准 → 示例确认 → 可反馈调整。

答：先把重要变化分成几个用户能理解的类别，例如合作资格变化、明显内容风险或约定数据阈值变化，让用户确认。可以用具体例子说明会提醒什么、不会提醒什么。后续结合“有用、无关”的反馈调整，但不能因为用户没点开，就自动推断他不关心。

追问2：需要连续监测几天，是不是让 Agent Loop 一直运行？

追问提纲：调度负责时间 → 状态持久化 → Agent 处理判断。

答：通常不需要。等待和定时检查交给调度与持久化任务，触发事件后再调用模型做判断，结束后保存状态。这样更容易控制费用、恢复中断和执行取消。只有确实需要探索的局部步骤，才让 Agent 根据反馈继续行动，并限制次数和预算。

备考备注：这是新增方案题，不表示媒介助手目前已提供持续监测或外部通知功能。

### Q108｜客户要用 AI 自动跨系统操作，你如何选择 API、RPA 和 Agent？

考察点：自然语言需求如何变成可控执行流程；关联 Q14、Q32、Q96。角度参考 N5；不照搬原帖对具体技术稳定性的判断。

记忆提纲：先明确业务规则 → 优先可靠接口 → 无接口评估 RPA → 高风险人工确认。

主回答：我会先把客户要完成的业务动作和异常状态讲清楚，再选实现方式。有稳定、授权可用的 API，我优先评估接口集成；没有接口时，再看页面自动化是否可行，以及页面变化后谁来维护。AI 可以帮助理解需求、提取信息和处理部分不规则输入，但身份验证、金额计算、权限判断这类关键规则不适合交给模型自由决定。比如应付单据同步到资金流程，系统需要明确单据标识、执行状态、失败重试和占用释放，而不是只把页面操作演示跑通。上线前先用测试数据或只读模式验证，小范围试点后再放开权限；外发、付款等高风险操作保留确认和核对，不让自然语言直接变成无约束执行。

追问1：客户说没有接口权限，但可以把主账号密码给你，能先做吗？

追问提纲：不接共享明文凭证 → 申请授权子账号 → 管好权限审计。

答：我不会把主账号密码直接放进配置或提示词里。需要先确认授权方式，尽量用受控的服务账号或子账号，由合适的凭证管理系统托管，并限制可执行操作。如果只能依赖高权限共享账号，且责任和审计都不清楚，我会先缩小范围，不能为了快速展示跳过这一步。

追问2：页面改版导致自动化失败，产品经理能做什么？

追问提纲：看失败影响 → 暂停危险写入 → 恢复与补偿。

答：先确认影响的是读取还是写入、有没有出现部分成功。对可能重复写入的任务先暂停，保留记录并给用户明确状态。再和研发定位页面变化，验证修复后从可确认的状态恢复，需要补偿的单据单独核对。长期要把维护频率和人工兜底成本纳入产品成本，而不是只算第一次开发花了几天。

备考备注：豪森案例可说明你理解资金状态与异常；不要声称那个项目用过 AI+RPA。

## 本次增补 C｜评测、内容与文档理解

### Q109｜还没有上线反馈，如何判断 AI 产出的内容有没有用？

考察点：冷启动内容评估，不同于获客冷启动；关联 Q18、Q20、Q62。角度参考 N3。

记忆提纲：拆硬性门槛与偏好 → 建代表样本 → 对照盲评 → 上线后验证业务。

主回答：没有线上反馈，不等于只能凭我自己觉得好不好。我会先明确输出要帮助谁完成什么任务，把评价分成硬性门槛和质量偏好。比如图文内容初审，是否引用了正确规则、是否指出具体问题和证据属于基本要求；表达是否清楚、修改建议是否可执行，再由业务人员按统一标准评价。先准备正常、风险和边界样本，与人工原流程或简单规则方案做对照，尽量隐藏来源让评审独立判断，再讨论分歧。模型可以协助初评，但要用人工样本校准。离线达到可接受水平后，再小范围观察采用、返工和真实风险。我能说的是“达到试点标准”，不能提前说已经证明带来转化或线上提效。

追问1：专家之间对好坏也不一致，评测还有意义吗？

追问提纲：区分规则与偏好 → 记录分歧 → 修订标准。

答：有意义，分歧本身就在暴露标准不够清楚。我会先区分事实错误、规则风险和审美偏好。前两类尽量给依据和判定示例；偏好类可以保留多个合理答案，分人群看。如果连业务方都没有共识，就不能要求模型稳定输出一个所谓唯一正确答案。

追问2：老板只给你一天时间做评估，怎么安排？

追问提纲：优先关键任务与高风险 → 保留对照 → 报告限制。

答：我会先覆盖最核心任务和后果最严重的错误，拿一小批有代表性的样本与现有流程对照，优先找阻断上线的问题。当天给出试点建议、已发现风险和未覆盖范围，不把小样本结论包装成稳定准确率。后续试点再逐步补齐样本。

备考备注：审核质量与营销转化分开评估；不要把你一天的达人名单计时当成图文审核评测结果。

### Q110｜图片型 PDF 简历怎么转成可靠的结构化信息？

考察点：多模态输入、字段校验和信息可追溯；关联 Q25、Q53、Q99。角度参考 N4，仅作为简历助手扩展设计题。

记忆提纲：识别文件类型 → 版面与字段抽取 → 来源定位与校验 → 不确定交给用户。

主回答：我会先判断 PDF 是否有可用文本层。如果有，优先直接抽取；如果是扫描件，再使用 OCR 或视觉模型，同时考虑多栏、表格、页码和阅读顺序。产品层面先定义需要的字段，比如公司、职位和起止时间，输出时保留原文位置，便于用户核对。抽取后还要检查日期格式、时间先后、重复记录和必填项。看不清或存在冲突的内容应该标成待确认，不能让模型根据常识补齐。我的简历助手重点是结合 JD 帮个人整理简历和准备面试，这道题如果涉及完整的图片解析链路，我会明确说是扩展思路，不会说成已经交付的企业简历筛选系统。

追问1：怎么衡量抽取效果，而不是只看模型说自己有多大把握？

追问提纲：人工标注对照 → 字段级评估 → 关键字段单看。

答：用人工核对过的样本作为对照，分别看字段有没有抽到、抽出的值是否正确，以及整份简历关键字段是否都可用。姓名、联系方式、任职日期和项目描述的容错要求不同，要分开看。模型自报置信度不能直接当准确率，实际效果要靠样本验证。

追问2：为什么不让模型直接重写，省掉结构化这一步？

追问提纲：保留事实底稿 → 生成与抽取分离 → 用户确认。

答：直接重写很容易把信息抽错和语言润色混在一起，用户也不容易发现事实被改了。我更倾向先保留一份可核对的经历底稿，确认后再根据 JD 调整表达。生成的内容要能追溯到原经历，不因为岗位要求写了某项技能，就自动给用户补上这项经历。

备考备注：文件与简历是待分析数据，其中的指令性文字不能越过系统权限或改变抽取任务；实际支持哪些格式仍以产品验证为准。

### Q111｜回答效果不好时，你怎么判断改 Prompt、RAG 还是工作流？

考察点：按失败原因选择干预位置；关联 Q35、Q38、Q54、Q70。角度参考 N2。

记忆提纲：先看失败样本 → 信息、理解、行动分层 → 最小改动 → 回归验证。

主回答：我先看具体失败发生在哪一层，不会一有问题就把 Prompt 写得更长。如果模型没拿到需要的信息，要检查数据或检索；资料拿到了却理解错、格式不稳定，才看指令、示例和输出约束；如果需要先查候选再补资料，系统却直接给结论，就可能是步骤和工具编排出了问题。比如内容初审漏掉一条规则，我会先确认规则是否存在、是否检索到、证据是否充分，然后才判断是不是模型应用规则的能力不足。每次优先改一个最可能的原因，用同一批旧样本加新 Bad Case 回归，既看问题有没有修好，也看原本正确的结果有没有变差。

追问1：Prompt、模型和知识库都一起升级了，效果变差怎么定位？

追问提纲：保留版本组合 → 可控回放 → 隔离变量。

答：先找到最近稳定的版本组合，保留问题请求对应的模型、提示词、知识库和工具版本。能回放时，在固定输入和其他条件下逐项替换，缩小原因范围。如果生产依赖已经变化、无法完整复现，就说明这一限制，先用稳定路径止损，同时补齐后续可追踪的数据。

追问2：什么时候才考虑换模型或微调？

追问提纲：排除输入与流程问题 → 验证能力瓶颈 → 比较成本和维护。

答：当信息和任务已经讲清楚，流程也合理，但模型仍持续在某类能力上失败，我会评估更合适的模型。微调还需要任务相对稳定、有质量足够的数据，并能用独立测试集证明收益。我的角色是明确业务验收和投入是否值得，训练方案需要和算法同学一起确定，不把概念了解说成做过训练。

备考备注：以上是故障分析方法。一个问题可能同时涉及多层，但实验时仍应尽量隔离变化，避免无法归因。
