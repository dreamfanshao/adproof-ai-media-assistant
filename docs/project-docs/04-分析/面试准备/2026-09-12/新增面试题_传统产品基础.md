## 基础一｜需求判断、产品设计与版本规划（Q76-Q83）

### Q76｜用户需求和用户提出的解决方案有什么区别？怎么判断伪需求？

考察点：能否从功能要求追到具体任务，而不是用个人偏好判断需求真假。

记忆提纲：① 谁在什么场景 ② 想达成什么结果 ③ 现有办法和损失 ④ 用行为验证

概念速记：需求是用户在具体场景中要解决的问题；功能是可能的解决方案。“伪需求”不是用户撒谎，常见情况是场景不成立、痛点很弱，或把不合适的方案误当成必要需求。

主回答：我会先把用户说的功能和背后的目标分开。比如“想要自动找达人”是方案，真正的问题可能是逐个看主页太慢、筛选口径不一致。我会追问最近一次怎么做、多久发生一次、花了多少时间、不解决有什么影响，再看现有工具能不能满足。只有口头说喜欢，还不足以证明值得开发。我会用原型或小范围试用观察用户是否愿意投入时间、交出真实任务，以及做完后是否继续使用。验证不成立时，先调整人群、场景或方案，不急着给用户贴上“伪需求”的标签。

追问1：只有一个朋友提出需求，值得做吗？

追问提纲：需求线索 → 同类用户验证 → 限制投入

答：可以作为起点，但不足以证明有普遍市场。我会找不同工作背景的同类用户验证，看看问题是否重复出现。在证据不足时先做低成本验证，不直接扩大开发投入。

追问2：用户说愿意付钱，能证明需求成立吗？

追问提纲：口头意愿不等于行为 → 看真实承诺

答：只能增加一点信心，还要看是否愿意真实试用、提供任务，或者在清楚交付内容后实际付费。不能把问卷里的付费意愿直接当成收入预测。

备考备注：与 Q10 的个人调研经历配合练习。本题讲方法，不增加真实访谈人数或付费成果。

### Q77｜用户访谈、问卷、可用性测试和竞品分析分别解决什么问题？

考察点：能否按问题选择研究方法，识别样本和提问偏差。

记忆提纲：① 访谈找原因 ② 问卷看分布 ③ 测试看操作 ④ 竞品看替代方案

概念速记：定性研究重在理解原因和过程；定量研究重在估计规模、比例和差异。用户画像是影响需求和行为的特征集合，不只是年龄、性别等标签。

主回答：我会先明确想知道什么。不了解用户为什么这样工作，先访谈和观察；已经有清楚的假设，想看它在更大样本中的分布，再考虑问卷；想知道流程能不能用，就让用户拿原型完成任务，观察卡在哪里。竞品分析则看同一个任务有哪些替代方式、各自的门槛和不足，不只是做功能对照表。访谈时我会多问最近一次真实经历，少问“你是不是觉得很麻烦”。比如媒介助手，更有用的分组是独立媒介和团队媒介、任务频率、交付标准，而不只是人口属性。

追问1：问十个人够了吗？

追问提纲：研究目标 → 样本差异 → 新信息是否持续出现

答：没有固定人数适用于所有问题。早期访谈可以先做小样本找线索，再覆盖关键用户类型；要估计比例或做统计比较，就需要另行设计样本，不能拿十次访谈推断整体市场。

追问2：竞品都有的功能，我们是不是必须做？

追问提纲：是否同一人群 → 是否核心任务 → 价值与成本

答：不一定。先看竞品服务的人和我们的目标是否一致，再判断这个功能是进入市场的基础门槛，还是只适合特定客户。不能因为竞品菜单里有，就自动排进我们的版本。

备考备注：可用性测试看用户能否完成任务，不等于验证他愿意长期使用或付费。

### Q78｜BRD、MRD、PRD 分别是什么？PRD 需要写到什么程度？

考察点：是否理解商业判断、市场判断与可执行需求的区别。

记忆提纲：① BRD 为什么投入 ② MRD 为谁做和机会在哪 ③ PRD 做什么及如何验收

概念速记：BRD 常指商业需求文档；MRD 常指市场需求文档；PRD 是产品需求文档。实际名称和拆分方式因团队而异，不必机械准备三份文件。

主回答：我的理解是，BRD 主要帮助判断这件事值不值得投入，MRD 说明目标市场、用户问题和竞争机会，PRD 则把确定的方向变成团队可以开发和验收的要求。PRD 不只是页面截图，至少要说清背景和目标、用户与场景、本期范围、流程、规则、状态与异常、数据和权限，以及验收与效果指标。以资金计划为例，只写“额度不足提示”不够，还要明确谁的额度、按哪个周期、什么时候占用、失败怎么释放。文档写到团队可以据此评估和验证就有价值，不追求篇幅越长越专业。

追问1：PRD 要把技术实现写死吗？

追问提纲：产品约束明确 → 实现方案共同评估

答：要明确业务行为、性能和安全约束，但具体架构和实现方式应该与研发评估。涉及跨系统接口等关键依赖，可以附契约和约束，不能因为自己会开发就替研发包办所有技术决策。

追问2：需求评审后又变了，怎么更新？

追问提纲：记录变化 → 评估影响 → 同步版本

答：记录改了什么、为什么改、影响哪些流程和验收项，再和相关负责人确认排期。更新同一份有效版本，并通知研发测试，不能只在聊天里补一句就算完成变更。

备考备注：文档不是职责证明，面试时最好准备一条真实规则及其验收方式来举证。

### Q79｜用户故事、用户旅程、业务流程和状态机有什么区别？

考察点：能否选择合适的表达方式，把一个需求讲完整。

记忆提纲：① 故事讲目标 ② 旅程看全过程 ③ 流程看协作顺序 ④ 状态机管转换

概念速记：用户故事常用“作为某类用户，我希望完成某事，以便获得某种价值”；用户旅程包含阶段、触点、行为与痛点；业务流程描述角色和活动；状态机描述对象在事件触发下的状态变化。

主回答：这几个工具观察的角度不同。用户故事先说明谁要什么和为什么，比如媒介希望保存候选名单，方便后续联系。用户旅程会从接到任务一直看到筛选、复核和交付，发现跨页面甚至线下的阻碍。业务流程把用户、系统和人工的动作连起来。状态机则用来讲一个对象什么时候可以变化，比如检索任务从等待到运行，再到成功、失败或取消。我不会每个需求都画全套，而是选能消除歧义的表达；跨模块、多角色和异常多的需求，流程与状态通常尤其重要。

追问1：状态机对产品经理有什么实际价值？

追问提纲：允许转换 → 触发条件 → 权限与异常

答：它能提前暴露“这时能不能点”“取消后还能不能回写结果”等问题。把转换条件、操作者和失败处理明确下来，研发与测试才不容易各自理解一套逻辑。

追问2：画了流程，为什么还要验收条件？

追问提纲：描述过程不等于验证结果

答：流程说明怎么走，验收条件说明走到什么结果才算符合要求。例如提交检索之后，重复点击是否只创建一次任务，失败时是否保留已有结果，这些需要可以检查的具体条件。

备考备注：旅程图中的情绪和痛点应有观察依据，不能为了图完整而替用户编感受。

### Q80｜线框图、交互原型、视觉稿与验收标准有什么区别？

考察点：是否只会画页面，还是能说明交互规则和可交付状态。

记忆提纲：① 线框定结构 ② 原型讲交互 ③ 视觉定样式 ④ 验收查行为

概念速记：低保真适合快速讨论结构，高保真更接近最终界面；保真度高不等于需求已经验证。可用性强调任务完成难度，用户体验还包括预期、信任和整个使用过程。

主回答：线框图主要确认页面信息和操作顺序，交互原型说明点击之后怎么走，视觉稿进一步确定字体、颜色和间距。真正能交付，还需要补空状态、加载、错误、权限和边界情况，并写出验收标准。比如异步找达人，不能只画最终列表，还要让用户知道任务有没有启动、可以等多久、失败后怎么继续。做评审时，我会让大家按真实任务走一遍，而不是只看页面好不好看；做用户测试时，尽量让用户自己操作，观察是否能理解和完成任务。

追问1：原型可以点击，就能直接交给研发吗？

追问提纲：交互之外还有规则、数据与异常

答：还要补数据来源、字段校验、权限和异常规则。能点击说明展示路径连起来了，不代表真实数据和失败场景已经明确。

追问2：怎么写一个清楚的验收条件？

追问提纲：给定条件 → 触发动作 → 可观察结果

答：可以按“给定、当、那么”写。比如在任务运行中再次点击提交，应返回现有任务或明确阻止重复创建，并且不能重复扣费；具体策略由评审确认，测试据此检查。

备考备注：示例用于理解验收写法，不宣称项目已实现计费。

### Q81｜Kano、RICE、MoSCoW 怎么理解？排优先级时怎么用？

考察点：是否能用框架辅助取舍，而不是给每个需求随意打分。

记忆提纲：① 先看目标和硬约束 ② 再看价值覆盖 ③ 考虑证据和成本 ④ 明确暂时不做

概念速记：Kano 看需求满足与满意度的关系，包括基本、期望、魅力等类型；RICE = 覆盖量 × 影响 × 置信度 ÷ 工作量；MoSCoW 按本期必须、应该、可以、暂不做区分范围。

主回答：我会先排查安全、关键依赖和明确承诺这些约束，再比较需求对当前目标的贡献。Kano 可以帮助理解哪些是缺了就无法使用的基础项，哪些是额外加分；RICE 适合把覆盖范围、影响、证据强弱和投入放在一起讨论；MoSCoW 则方便确定这一版到底保什么。比如找达人，如果真实数据取不到，增加推荐解释也解决不了主任务。评分只能帮助暴露假设，不能替代判断；估计缺乏依据时，我会降低置信度或先做验证，不把一个精确分数当成确定收益。

追问1：业务方说每个需求都是 Must，怎么办？

追问提纲：不做后果 → 本期目标 → 时间资源约束

答：逐项问如果这版不做，核心流程是否走不通、是否违反明确承诺。再把总工作量和可用时间摆出来，请共同负责人确认取舍，而不是把所有需求都贴上必须标签。

追问2：RICE 分最高，就一定先做吗？

追问提纲：依赖与风险 → 估计可信度 → 解释例外

答：不一定。低分需求可能是其他功能的前置条件，也可能涉及必须处理的安全问题。可以调整顺序，但应说清原因，不让评分成为装饰。

备考备注：RICE 四项必须采用一致的时间范围和工作量单位，置信度要有证据。方法参考见新增来源 S1。

### Q82｜路线图、需求池和版本计划有什么区别？怎么控制需求蔓延？

考察点：能否把产品方向拆成可推进的版本，并管理范围变化。

记忆提纲：① 路线图讲方向 ② 需求池存机会 ③ 版本计划定范围 ④ 变更重新取舍

概念速记：Roadmap 表达阶段目标与方向；Backlog 是持续整理和排序的待办；版本计划说明近期交付范围、依赖、负责人和验收。Scope creep 指未充分评估和控制的范围持续扩张。

主回答：我会用路线图解释接下来优先解决哪些问题，用需求池保存待验证和待开发的事项，再从中选出本期版本。越接近交付，范围和验收就应该越明确；远期不适合把每个功能和日期都承诺死。新需求进来时，我会看它是否影响本期目标、需要多少额外工作、会挤掉什么，再决定替换、延期还是下个版本。比如名单功能尚未验证，就不断加入团队权限和收费体系，很容易拖慢验证。我更关注这个版本让我们确定了什么，而不只是做了多少项功能。

追问1：需求池越来越长，怎么处理？

追问提纲：目标相关性 → 新证据 → 合并与归档

答：定期按目标和证据重新看，合并重复项，对长期没有价值依据的需求标记暂缓或归档。需求池不是承诺清单，不是每一项最终都必须开发。

追问2：客户要求确定上线日期，但技术还有不确定性呢？

追问提纲：先验证关键依赖 → 分阶段承诺 → 及时同步风险

答：先和研发识别最大不确定点，安排短验证，再给有依据的计划。可以承诺阶段检查点和已确定范围，不能未经评估直接保证完整交付日期。

备考备注：需求范围、时间、质量和资源需要共同权衡，延期不是唯一解，砍范围也不是不经确认就能做。

### Q83｜Demo、PoC、MVP 和 PMF 分别验证什么？上线就算成功了吗？

考察点：是否分得清展示、技术验证、需求验证与持续市场接受。

记忆提纲：① Demo 看得懂 ② PoC 做得到 ③ MVP 值得用 ④ PMF 持续被需要

概念速记：Demo 用于演示；PoC 是概念可行性验证；MVP 用最小必要投入验证关键产品假设；PMF 指产品与目标市场形成较强匹配。它们不是必须按顺序各做一套的四个系统。

主回答：我会按要消除的不确定性来区分。Demo 帮助别人理解体验，PoC 回答关键技术链路能不能成立，MVP 则让目标用户在真实任务中验证方案是否有价值。PMF 更进一步，需要看目标用户是否持续使用、愿意付出成本，以及需求能否重复出现。拿媒介助手来说，页面能演示不代表能真实检索；能检索也不代表用户愿意持续用。上线只说明发布完成，还要继续验证结果是否被采用、复用是否发生，以及质量和成本能否支撑长期服务。

追问1：MVP 可以直接成为最终上线产品吗？

追问提纲：可以延续 → 验证目的不同 → 逐步补齐

答：可以在同一个产品上继续迭代，不一定推倒重做。但早期为了验证省掉的稳定性、权限或运营能力，可能需要在扩大使用前补齐；涉及基本安全的要求不能省。

追问2：注册人数多，能说明 PMF 吗？

追问提纲：获客不等于价值 → 看持续行为和付出

答：不能单独说明。可能只是推广带来的尝鲜，还要看目标用户是否持续完成核心任务、是否复用或付费，以及停止使用的原因。没有一条通用于所有产品的 PMF 数字门槛。

备考备注：项目当前阶段按已确认事实说明，不把方法题中的验证计划写成已取得的市场结果。

## 基础二｜产品指标、增长与商业价值（Q84-Q88）

### Q84｜北极星指标、过程指标、护栏指标，以及 OKR/KPI 有什么区别？

考察点：能否从用户价值出发选指标，并说明如何防止局部优化。

记忆提纲：① 北极星看价值 ② 过程指标找抓手 ③ 护栏限制代价 ④ 目标管理不等于指标堆砌

概念速记：北极星指标概括产品持续交付的核心用户价值；过程指标解释哪些行为推动结果；护栏指标限制不可接受的副作用。KPI 是关键绩效指标；OKR 用目标和可衡量的关键结果组织阶段工作，两者可以共用指标。

主回答：我会先问用户为什么使用产品，再决定主指标，而不是先选 DAU。比如媒介助手，用户需要的是可用于后续工作的名单，我会考虑“每周完成并被采用的有效名单任务数”作为候选价值指标，再验证它是否与持续使用相关。过程上看发起、完成、复核和采用各环节，护栏看质量、耗时和单任务成本。这样即使任务量上升，也能发现是不是靠降低质量换来的。OKR 可以围绕提高首次价值达成来设目标，关键结果用这些指标衡量；做完一个功能通常是行动，不自动等于达成了结果。

追问1：一个产品必须只有一个指标吗？

追问提纲：聚焦主价值 → 配诊断和护栏 → 多业务分层

答：不是只能看一个数。可以用一个主指标帮助聚焦，同时保留诊断和护栏。多条价值链差异很大时，可以按业务分别设指标，再看整体目标，不能强行把不同任务相加。

追问2：“上线内容审核功能”能作为关键结果吗？

追问提纲：里程碑可以记录 → 用户结果另行验证

答：它可以是交付里程碑，但如果目标是改善审核效率，还要衡量合格任务完成、复核负担或返工情况。上线说明功能交付了，不说明用户的工作已经改善。

备考备注：候选北极星属于设计建议，不代表项目已正式采纳或具备完整线上埋点。详见 Q11、Q43 的项目口径。

### Q85｜PV、UV、DAU、WAU、MAU 是什么？活跃人数怎么算？

考察点：是否理解计数、去重、时间范围和有效行为。

记忆提纲：① PV 数浏览 ② UV 去重访客 ③ 活跃定义行为和周期 ④ 黏性结合场景

概念速记：PV 是页面浏览次数；UV 是指定周期按既定标识去重的访客数；DAU、WAU、MAU 分别是日、周、月活跃用户数。周和月可以采用自然周期或滚动窗口，必须注明。

主回答：我会先定义什么行为算活跃，再计算对应周期内的去重用户。页面浏览、登录和完成一次核心任务代表不同深度，不能默认都等价。比如媒介助手，可以分别看访问活跃与任务活跃，再看二者的差距。DAU 不能简单相加得到 MAU，因为同一人可能每天回来。分析黏性时可以看 DAU/MAU，但要统一窗口；跨月比较时可以用日均 DAU 与对应月 MAU 的比值，并说明口径。对低频工作工具，周或任务周期的复用往往比每天打开更有意义。

追问1：同一天一个用户打开十次，PV、UV 和 DAU 各是多少？

追问提纲：是否触发浏览事件 → 是否同一身份 → 是否满足活跃定义

答：假设十次都触发页面浏览、身份识别一致且符合活跃定义，则 PV 为 10、UV 为 1、DAU 为 1。如果活跃要求完成任务，而他只是浏览，任务口径的 DAU 就不能计入他。

追问2：DAU 涨了，是不是说明产品变好了？

追问提纲：来源和构成 → 核心行为 → 留存质量

答：先看是新增推广、老用户回访，还是统计变化，再看这些用户有没有完成关键任务、后续是否留下来。活动引来的短期访问，不一定代表产品价值提升。

备考备注：设备数、账号数和人数不是天然相同；排除测试账号及异常流量时要有稳定、可追溯的规则。

### Q86｜激活率、转化率和漏斗怎么定义？AARRR 是什么？

考察点：能否把用户成长过程拆成可验证的行为，而不是把所有比例统称转化。

记忆提纲：① 明确起点终点 ② 固定人群和时间窗 ③ 看相邻与整体转化 ④ 找掉点原因

概念速记：激活是用户首次体验到关键价值，不一定等于注册；转化率 = 在约定窗口内完成目标的合格对象数 ÷ 起点合格对象数。AARRR 常指获客、激活、留存、收入、推荐，是观察生命周期的框架，不是强制操作顺序。

主回答：我会先说清转化的起点、终点、对象和时间窗。比如观察注册后七天内有多少用户完成首个有效名单任务，这可以作为激活的候选口径，不能把登录就直接当成体验到价值。漏斗上再拆注册、发起任务、生成结果、人工复核和采用，看哪一步掉得最多，同时看绝对人数。掉点不一定都是页面问题，也可能是不适合的用户进来了、结果质量差，或者任务本来就不需要继续。我会结合失败记录和用户观察，再确定优先改哪里。

追问1：100 人进入，40 人提交，20 人完成，怎么算？

追问提纲：同一批人 → 相邻转化 → 全程转化

答：假设这三步是同一批用户、符合顺序和时间窗，提交转化为 40%，提交到完成为 50%，全程完成为 20%。不能把不同批次的每日人数直接拼成同一个漏斗。

追问2：转化率从 20% 到 30%，提升了多少？

追问提纲：绝对变化用百分点 → 相对变化除以原值

答：提升 10 个百分点，相对提升是 50%，因为增加的 10% 除以原来的 20%。报告里要写清楚是哪一种，不能只说“提升 10%”。

备考备注：本题数字全部为教学示例。起点为 0 时转化率无定义，不应写成 0% 伪装成正常观测。

### Q87｜次日留存、七日留存、同期群和流失率怎么理解？

考察点：是否固定观察人群、返回行为和完整观察窗口。

记忆提纲：① 固定首次行为人群 ② 定义返回行为 ③ 等窗口完整 ④ 区分精确日与区间

概念速记：按自然日的第 N 日留存 = 某日完成起始事件的用户中，在第 N 天完成返回事件的人数 ÷ 当日起始人数。Cohort 是按共同起始条件分组的同期群；流失需要另行定义多长时间未使用或是否停止订阅。

主回答：我会先明确谁是这批用户、从哪件事开始计时，以及回来做什么才算留存。比如从首次完成任务开始，看七天后的任务复用，和从注册开始看是否登录，是不同指标。还要区分第七天回来、七天内回来，以及第七天或之后回来，这些不能混算。按渠道或首用月份分同期群，可以减少用户构成变化对判断的干扰。对低频媒介工具，我会结合任务周期看周复用，不能因为第二天没有工作就判定产品没有价值。

追问1：100 人注册，第七天 20 人回来，D7 就是 20% 吗？

追问提纲：属于同一群 → 满足返回事件 → 窗口已完整

答：在注册作为起始事件、20 人属于这 100 人且满足规定返回行为，并且第七天已经观察完整的前提下，是 20%。不能把第七天全站回访人数直接除以当初注册人数。

追问2：流失率就是 1 减留存率吗？

追问提纲：定义可能不同 → 未在当天返回不等于永久离开

答：不一定。1 减 D7 只表示这批用户在指定第七天没有按定义回来，不等于已经流失。订阅取消和连续一段时间无使用是另外的口径，要明确对象与窗口后再计算。

备考备注：自然日与滚动 24 小时可能给出不同结果；不同平台的名称也可能不同。时间边界参考新增来源 S2。

### Q88｜ARPU、ARPPU、CAC、LTV 和 ROI 分别看什么？

考察点：是否区分收入、利润、获客成本与长期价值，不把流量直接当商业成功。

记忆提纲：① 每用户收入 ② 每付费用户收入 ③ 获客成本 ④ 长期贡献与回本

概念速记：ARPU = 同期收入 ÷ 约定用户数；ARPPU = 同期收入 ÷ 付费用户数；CAC = 可归属获客投入 ÷ 新增客户数。LTV 是用户生命周期价值，必须注明采用收入还是毛利/贡献口径；ROI =（收益 - 投入）÷ 投入，收益不能不加说明地用流水代替。

主回答：这些指标分别回答收入从哪里来、获客花了多少，以及客户长期值不值得服务。我会先统一周期和对象，例如 CAC 的客户是注册用户还是付费客户，要明确说清。对 AI 工具，不能只看订阅收入，还要考虑模型、数据源和服务交付的变动成本。LTV 可以根据不同用户群的留存、付费和贡献逐步估计，但早期样本少时不适合给一个很确定的终身价值。我会先看单任务贡献、付费持续性和回本周期，再决定是否加大获客投入。

追问1：能直接用 ARPU 除以流失率算 LTV 吗？

追问提纲：简化模型有假设 → 收入与贡献分开 → 早期慎用

答：那是依赖稳定收入、稳定流失等假设的简化估计，周期还必须一致。若看贡献价值，还需要考虑毛利或变动成本；早期和分群差异很大的产品，更适合跟踪同期群实际贡献，不硬套公式。

追问2：收入涨了，为什么利润反而可能下降？

追问提纲：折扣与用户结构 → 单位交付成本 → 获客投入

答：可能通过折扣换来了低贡献用户，也可能重度用户带来更多模型和人工成本，或者获客开支增长更快。所以要拆收入结构和单位成本，不能只看总收入。

备考备注：这是产品商业指标学习，不是已实现付费经营的经历；没有用户收入与成本记录时，不编造 LTV/CAC。

## 基础三｜SQL、埋点与分析验证（Q89-Q93）

### Q89｜SQL 多表关联、分组、去重和 NULL，产品分析时怎么用？

考察点：能否按业务粒度写对查询，而不是只会拼语法。

记忆提纲：① 确定一行代表什么 ② 选择关联方式 ③ 正确分组计数 ④ 检查空值和放大

概念速记：INNER JOIN 保留匹配行，LEFT JOIN 保留左表行；GROUP BY 聚合到指定粒度；WHERE 在分组前筛行，HAVING 在分组后筛组。COUNT(*) 数行，COUNT(字段) 不计 NULL，COUNT(DISTINCT 字段) 计非空去重值。

主回答：我会先明确最终要统计用户、任务还是达人。比如用户表和任务表是一对多，关联后一个用户可能出现多行，不能直接把行数当用户数。需要保留没做过任务的用户时用左连接，再在正确粒度上计算。分析某天完成任务的用户数，可以先限制状态和时间，再对用户标识去重。NULL 我会先判断是缺失、未发生还是不适用，不直接都替换为零。查询完成后，用少量已知样本和总量核对结果，避免 SQL 能执行，但业务口径错了。

追问1：LEFT JOIN 后在 WHERE 限制右表状态，会怎样？

追问提纲：未匹配右表为 NULL → 可能被 WHERE 排除

答：如果写“右表状态等于成功”，未匹配的行会被过滤，可能丢掉原本想保留的无任务用户。需要保留他们时，可以把匹配条件放到 ON 中，或先按目标口径聚合右表再关联。

追问2：什么时候用 HAVING？

追问提纲：先按对象聚合 → 再按聚合结果筛选

答：比如找完成任务数不少于三次的用户，可以先筛选成功任务，再按用户分组，用 HAVING 对 COUNT(*) 的结果做限制。这个“三次”是分组后的条件，不是单行字段条件。

备考备注：结合 Q69 练习一致性排查。逻辑删除、历史版本和重试也会影响计数，不能只依赖 DISTINCT 掩盖问题。

### Q90｜窗口函数、日期窗口和去重，能解决哪些产品分析问题？

考察点：是否能处理首次行为、前后比较及周期数据，而非只会总量统计。

记忆提纲：① 窗口保留明细 ② 排序找首次或最新 ③ 时间范围统一 ④ 去重遵守业务键

概念速记：窗口函数在相关行之间计算，同时保留每行；ROW_NUMBER 可在分组内编号，LAG 可取前一行值。GROUP BY 通常把多行收成聚合结果，二者目的不同。

主回答：当我需要保留任务明细，又想知道它是用户的第几次任务，就可以考虑窗口函数。比如按用户分组、按完成时间和任务标识排序，用 ROW_NUMBER 找第一次成功任务，分析首次价值达成；用 LAG 对比相邻记录，辅助看变化。统计周期时，我会明确时区，并尽量用“开始时间包含、结束时间不包含”的范围，避免跨天重复。去重也必须先定义什么算同一事件或同一版本，不能为了让数变小，就随便保留一行。

追问1：两条记录时间相同，取最新一条怎么保证稳定？

追问提纲：明确版本语义 → 增加确定性排序键

答：时间相同不足以确定业务新旧，应优先看版本号或可靠更新时间，再加唯一标识保证排序稳定。唯一标识用于打破并列，不代表它天然能判断哪条业务上更新。

追问2：LAG 算到的是昨天吗？

追问提纲：前一行不一定前一天 → 检查日期连续性

答：不一定。LAG 取的是排序后的上一行，如果某天没有记录，上一行可能是几天前。需要日环比时要先补齐日期或明确按日期关联，再按业务含义处理缺失。

备考备注：窗口函数是补充学习项，不默认你已经熟练掌握。定义参考新增来源 S3；建议实际写查询验证后再在面试中声明熟练。

### Q91｜埋点、事件、属性和指标口径是什么？产品经理怎么写埋点需求？

考察点：能否把业务问题转成可信的行为记录，并考虑身份、重复和隐私。

记忆提纲：① 先明确决策问题 ② 定义事件与触发 ③ 补身份属性和去重 ④ 验证再出指标

概念速记：事件记录发生了什么，属性说明当时的上下文；埋点是采集行为的方式；指标是在事件和业务数据上按约定口径计算出的结果。埋点表应包含事件名、触发时机、字段类型、来源、版本和验收方式。

主回答：我会先想清楚这份数据要帮助做什么决策，再决定采哪些事件。比如分析找达人任务为什么没完成，需要区分提交、创建成功、执行结束和结果采用，不能只记录按钮点击。每个事件要说明在哪一侧触发、什么条件下只记录一次，以及关联哪个用户和任务。再补场景、版本和失败原因等必要属性，避免收集与分析无关的原始隐私内容。开发完成后，用一条测试任务检查事件顺序、重复和缺失，再和业务表对账，确认可信后才上看板。

追问1：前端显示成功，就可以记任务成功吗？

追问提纲：UI 展示与业务事实分开 → 确定权威来源

答：任务完成一般应以服务端确认的业务状态为准；前端事件可记录用户是否真正看到结果。两者解决不同问题，网络中断时尤其不能只靠前端提示判断任务是否执行成功。

追问2：怎样避免同一事件被重复统计？

追问提纲：唯一标识 → 上报与去重规则 → 保留重试信息

答：为事件设计稳定标识，并明确重发时是否复用它，数据侧按规则去重。任务本身的多次尝试要另外保留，不要为了消除上报重复，把真实重试也删掉。

备考备注：本题是埋点设计方法，不代表媒介助手已有正式增长分析系统。安全与权限是数据设计的一部分。

### Q92｜趋势、分群、漏斗、同期群和相关性分析，分别什么时候用？

考察点：是否先定义问题，再选分析角度，并避免把相关当因果。

记忆提纲：① 趋势找时间变化 ② 分群找差异 ③ 漏斗找环节 ④ 同期群控构成

概念速记：环比与相邻可比周期比较，同比与上一年对应周期比较；分群按用户、场景、渠道等拆分；漏斗看步骤转化；同期群固定起始人群看后续行为。相关表示共同变化，不直接说明谁导致谁。

主回答：我会先把问题说具体，再决定分析方法。比如任务完成率下滑，先看从什么时候开始，是持续变化还是单日波动，再按版本、渠道和任务类型拆分；如果只在某个环节掉，就看漏斗和失败样本。研究留存时再固定同期群，避免新用户比例变化干扰结论。即使发现使用某功能的人留存高，也可能是高意愿用户更爱用它，不能直接说这个功能提高了留存。数据先帮助提出解释，再用更接近因果的实验或其他验证来判断。

追问1：环比下降，但同比上涨，矛盾吗？

追问提纲：基准不同 → 季节性和日历 → 解释背景

答：不矛盾，因为比较的基准不同。可能本月比上月弱，但比去年同月更好。还要看工作日数量、活动和季节性，不能只挑对自己有利的比较方式。

追问2：每个主要分群都改善，整体为什么反而变差？

追问提纲：权重改变 → 低转化群占比提高 → 固定构成对比

答：可能低转化人群占比大幅上升，把整体拉低了，这类现象常被称为辛普森悖论。应同时看分群表现和流量构成，必要时按固定权重比较，别只凭总数评价版本效果。

备考备注：观察性分析能提供证据但通常不能单独证明因果；小样本、节假日和数据延迟应先排查。

### Q93｜A/B 测试、灰度、统计显著性和 MDE 有什么区别？

考察点：是否知道实验能回答什么、何时结果可信，以及不应怎么解释数字。

记忆提纲：① 随机对照看效果 ② 灰度控制发布风险 ③ 显著不等于重要 ④ 样本不足不硬下结论

概念速记：A/B 测试用可比较的随机分组估计方案效果；灰度是分阶段放量，不天然构成实验。MDE 是预先关心的最小可检测效果；统计功效描述在设定效果真实存在时检出它的概率；p 值不是“方案正确的概率”。

主回答：我会先提出一个可验证的假设，确定主指标和不能恶化的护栏，再和数据同学确认分流单位、样本量、周期和分析方式。A/B 的关键是分组可比，灰度更多是控制风险，两者可以结合但不能互相替代。读结果时既看差异和置信区间，也看差异有没有业务意义、护栏是否受损，并先排除分流比例或埋点异常。像我的个人项目，如果流量不足，我会先做离线对照和小范围任务验证，不把少量用户的前后变化说成可靠的 A/B 因果结论。

追问1：p 小于 0.05，是否表示有 95% 概率方案有效？

追问提纲：条件概率方向不同 → 显著性不等于业务收益

答：不是。p 值是在零假设和统计模型成立时，出现当前或更极端数据的概率。还要看效果大小、不确定范围和业务代价，不能把它翻译成方案有 95% 概率正确。

追问2：实验没显著，是不是两个方案一样？

追问提纲：证据不足不等于相同 → 看区间和功效 → 不随意提前停止

答：不是，可能样本不足，也可能真实差异很小。要看区间是否仍包含有意义的收益或损失；如果想证明足够接近，需要另设等效性判断。常规实验不能反复看数，一显著就停，除非采用适配的序贯方法。

备考备注：95% 置信区间表示，在方法假设成立时反复抽样构造区间，约 95% 的区间会覆盖真实参数；不简单等于“真实效果以 95% 概率落在这次区间里”。分流异常与护栏参考 S4；本题不冒充正式线上实验经历。

## 基础四｜研发协作、服务质量与 AI 技术沟通（Q94-Q99）

### Q94｜敏捷、Scrum、Sprint、UAT 和 DoD 是什么？产品经理怎么参与？

考察点：是否理解迭代协作和验收责任，而不是把敏捷等同于催进度。

记忆提纲：① 短周期反馈 ② 目标与范围协商 ③ 业务验收与质量门槛 ④ 复盘改协作

概念速记：敏捷强调持续反馈与适应；Scrum 是一种具体框架，Sprint 为不超过一个月的固定长度周期。UAT 是用户验收测试；DoD 是完成的共同质量标准。Review 检视产品结果，Retrospective 复盘团队工作方式。

主回答：我理解敏捷的重点是尽早交付可检查的结果，再根据反馈调整，不是需求随时改、研发随时接。如果团队采用 Scrum，我会结合实际角色参与目标与需求排序，澄清规则和验收条件，再与研发协商本期范围。开发过程中及时解决业务疑问和依赖，上线前通过 UAT 确认能否完成实际工作，同时遵守测试、安全和文档等完成标准。迭代后既看功能效果，也看协作哪里返工多。我的正式经历主要是开发与交付协作，不会把它说成独立担任过 Scrum 产品负责人。

追问1：开发说做完了，测试说没做完，怎么办？

追问提纲：编码完成不等于交付完成 → 对照验收与 DoD

答：先看“完成”是不是指不同阶段。代码写好、测试通过、业务验收和可发布不是一回事，应提前约定统一完成标准。再把未满足项列出来确定责任和处理方式，不靠口头争论。

追问2：验收标准和 DoD 是一回事吗？

追问提纲：单项业务条件 → 通用质量标准

答：验收标准通常针对具体需求，比如额度释放是否符合规则；DoD 更像团队对增量完成的共同要求，例如必要测试已通过。两者互补，业务功能能用不意味着质量要求都满足了。

备考备注：Scrum 的角色与事件参考 S5。产品经理职位不自动等于 Scrum 中的 Product Owner；缺陷严重程度与修复优先级也应分开讨论。

### Q95｜QPS、TPS、并发量、P95 延迟、SLI/SLO/SLA 怎么转成产品要求？

考察点：是否能把服务能力与用户体验联系起来，而不是只听懂缩写。

记忆提纲：① 区分流量和在途量 ② 看整体与长尾等待 ③ 定义服务目标 ④ 决定排队、限流与降级

概念速记：QPS 常指每秒请求/查询数；TPS 在交易系统常指每秒事务数，在模型场景可能指 tokens/s，必须确认单位。并发量是同一时刻处理中任务或连接的数量。P95 是约 95% 样本不超过的延迟值；SLI 是测量指标，SLO 是内部目标，SLA 是对外服务约定。

主回答：听到这些词，我会先确认测的是哪个环节、什么单位，以及用户实际感受到什么。比如平均接口响应很快，不代表生成名单的端到端等待很短，还要看排队和长尾。QPS 和并发也不能直接互换，同样请求速率下，单次处理越久，在途任务通常越多。产品侧我会和研发根据使用高峰、任务时限和成本确定目标，再选择异步处理、排队提示、并发限制或降级。对 AI 交互还会区分首个输出出现的时间与全部结果完成的时间，不拿一个速度指标代替整体体验。

追问1：100 QPS、平均处理 2 秒，能估算并发吗？

追问提纲：稳定流量 → 同一系统边界 → 平均在途量

答：在系统稳定、统计边界一致等条件下，平均在途量可粗估为 100 乘 2，即约 200。如果两秒包含排队，这估计也包含排队请求；不能直接拿它当线程数或容量上限，仍需压测。

追问2：研发说要把所有请求都做到一秒内，产品该怎么判断？

追问提纲：任务等待容忍度 → 尾部目标 → 成本和可行性

答：先看用户任务是否真的需要，再明确目标覆盖比例、输入规模和异常情况。长任务可能更适合及时反馈进度，而不是为极少数请求投入过高成本；外部承诺必须有验证依据。

备考备注：SLI/SLO/SLA 参考 S6。模型首 token 延迟常称 TTFT，输出速度快不等于首 token 到得快。本题数字是教学示例，不是项目压测结果。

### Q96｜API、同步异步、回调、幂等、超时和重试，产品经理要理解什么？

考察点：能否把系统边界变成可理解、可恢复的业务行为。

记忆提纲：① 接口说明契约 ② 长任务异步反馈 ③ 重复请求防副作用 ④ 超时先查状态

概念速记：API 约定系统间如何交互；同步通常等待当前调用返回结果，异步可先返回任务标识再获取结果；回调由执行方通知接收方，轮询由查询方反复获取状态。幂等强调同一业务操作重复执行不产生额外业务副作用。

主回答：产品经理不一定负责写接口，但要知道请求代表什么、结果什么时候可信、失败后用户怎么办。比如找达人耗时较长，可以先返回任务标识，让用户查看进度，再通过通知或轮询获取结果。重复点击不能意外生成多份同一业务任务，所以要与研发约定幂等范围。超时也不等于执行失败，可能任务已经成功只是响应没回来，应先查状态，再决定是否重试。这样才能避免重复下单、重复占用或重复扣费，同时让用户清楚哪些结果可以继续使用。

追问1：前端把按钮禁用，就算幂等了吗？

追问提纲：前端仅改善体验 → 后端保证业务唯一性

答：不算。用户可以刷新、多端操作，网络也可能自动重发。前端限制只能减少误触，后端仍要用业务标识、幂等键或约束处理重复，并规定同一请求返回什么结果。

追问2：所有失败都应该自动重试吗？

追问提纲：区分可恢复错误 → 次数与间隔 → 副作用和成本

答：不应该。参数不对或没有权限通常要先修正；临时超时、限流可以考虑有限重试和退避。还要评估操作是否幂等、是否重复收费，以及多次失败后怎样转人工或提示用户。

备考备注：资金项目可以帮助举例业务状态风险，但不要声称自己设计过尚未确认的支付网关或计费系统。

### Q97｜AI 调用量、Token 成本、调用成功率和单任务成本怎么定义？

考察点：是否把供应商消耗、系统执行和用户结果分开衡量。

记忆提纲：① 一次任务可能多次调用 ② 费用按真实计费项 ③ 成功分接口与任务 ④ 计算失败和重试代价

概念速记：Token 是模型处理文本等输入输出时使用的计量单元，不等于一个汉字或一个单词。调用量计实际请求，任务量按业务标识去重。单成功任务成本可定义为同一任务批次的总可归属成本 ÷ 成功任务数，分子包含失败尝试与重试。

主回答：我会先把一个用户任务和内部模型调用分开。一次找达人可能包含解析、匹配等多次调用，次数增加可能是任务量增长，也可能是重试或循环失控。费用要按输入输出、缓存和其他计费项核算，再加上约定范围内的数据源、基础设施或人工成本。接口正常返回不等于输出可用，更不等于用户完成了任务。我会同时看首次调用成功率、最终任务完成率、结果采用和单成功任务成本，避免通过返回空结果或无限重试把成功率做高。

追问1：怎样计算一个任务的模型费用？

追问提纲：归集调用 → 按计费分类 → 汇总重试和工具

答：把该任务各次调用关联起来，按供应商当时的输入、输出和缓存等价格计算并求和；如有图像、音频或工具单独计费也要计入。再与实际账单核对，不用一个长期固定单价估算所有模型。

追问2：总成本下降了，就值得上线新方案吗？

追问提纲：同任务结构比较 → 质量和采用不能丢 → 人工成本补齐

答：还要确认是不是任务量或难度下降导致的，并看质量、完成率和人工返工有没有变差。只有在可比任务上，总交付成本更合理、效果满足要求，才说明方案可能更优。

备考备注：本地 Eval 与用量记录不等于已部署线上成本看板。统计口径应说明是否含人力和固定成本，以及账单与请求记录的差异。

### Q98｜准确率、精确率、召回率、F1、幻觉率和 Bad Case 怎么理解？

考察点：能否根据错误代价选择指标，避免被一个高分误导。

记忆提纲：① 明确正类和样本 ② 区分误报与漏报 ③ 按业务代价取舍 ④ Bad Case 回流评测

概念速记：设“有风险”为正类：TP 是正确报风险，FP 是误报风险，FN 是漏报风险，TN 是正确判无风险。准确率 = (TP+TN)/全部样本；精确率 = TP/(TP+FP)；召回率 = TP/(TP+FN)；F1 = 2×精确率×召回率/(精确率+召回率)。

主回答：我会先确认评的是什么对象，以及哪一种错更严重。审核里，精确率看报出的风险有多少是真的，召回率看真实风险有多少被找出来；如果绝大多数内容本来就没风险，全部判安全也可能得到很高的准确率。高风险漏报通常需要重点控制，但也不能让误报把人工复核压垮。生成任务的幻觉率还要另定单位，可以按含无依据事实的回答计，也可以按具体断言计，不能混用。Bad Case 是不满足预期的案例，我会按数据、检索、模型和流程分类，定位后加入回归评测。

追问1：20 条实际有风险，报出 25 条，正确报出 15 条，怎么算？

追问提纲：TP=15 → FP=10 → FN=5 → 分别代入

答：精确率为 15/25，即 60%；召回率为 15/20，即 75%；F1 约为 66.7%。没有总样本数或 TN，不能继续算准确率。这里的数字只用于练习，不是我的项目指标。

追问2：模型自己说“置信度 95%”，能当准确率吗？

追问提纲：自报分数不是实测 → 标注集验证 → 关注校准

答：不能。自报分数不等于对真实样本统计出的正确比例，除非经过可靠验证和校准。我要用独立标注样本评估，并记录高置信错误，不能把模型语气确定当成可靠。

备考备注：分类公式参考 S7。分母为零时应按约定标注无定义或采用明确的工具处理规则；F1 不考虑 TN，也不能替代错误成本评估。幻觉之外，漏项、拒答和格式错误应另行分类。

### Q99｜SFT、LoRA、Embedding 和 RAG 各解决什么问题？怎么转成产品决策？

考察点：是否分清训练方法、参数更新方式、语义表示与检索增强。

记忆提纲：① SFT 学任务示范 ② LoRA 降低可训练参数量 ③ Embedding 表示相似性 ④ RAG 补外部依据

概念速记：SFT 是监督微调，利用输入与期望输出等示范数据训练；LoRA 是参数高效微调方法，通常冻结基础权重并训练低秩适配参数，可用于 SFT，二者不是二选一。Embedding 把内容表示为向量，RAG 则在生成时引入检索到的资料。

主回答：我会先看效果差的原因，再讨论技术。知识经常更新、回答缺少依据时，优先评估检索和 RAG；任务格式或行为长期不稳定，有足够高质量示范数据时，再与算法评估 SFT。LoRA 可以作为实现微调的一种方式，减少需要训练的参数，但不保证效果一定更好，也不能解决数据质量问题。Embedding 更多用在相似检索等环节，向量相近不代表内容一定真实或业务上合适。最终我会比较独立评测结果、上线维护和成本，而不是因为某个词热门就采用；我对微调的定位是理解方案和协作判断，不冒充训练实操经验。

追问1：用了 Embedding，就一定用了 RAG 吗？

追问提纲：向量可独立服务检索 → RAG 需要连接生成

答：不一定。Embedding 可以只用于搜索、聚类或推荐；只有把检索资料用于支持生成的链路，才是在做检索增强生成。反过来，RAG 也不强制只能使用向量检索。

追问2：把企业全部文档拿去微调，就不用知识库了吗？

追问提纲：知识更新与引用 → 权限管理 → 方法可组合

答：不能这样简单替代。微调不保证逐条记住事实，也不天然提供更新、权限过滤和出处引用；这些需求更适合评估知识检索。微调可以改善行为，RAG 可以提供资料，两者也可以组合并分别验证。

备考备注：SFT 与 LoRA 参考 S8、S9。关于个人项目的实际 RAG/Embedding 实现程度，以 Q54 和已验证材料为准，概念学习不改变项目事实。
