## 基础一｜需求判断、产品设计与版本规划（Q76-Q83）

### Q76｜用户需求和用户提出的解决方案有什么区别？怎么判断伪需求？

考察点：能否从功能要求追到具体任务，而不是用个人偏好判断需求真假。

记忆提纲：① 谁在什么场景 ② 想达成什么结果 ③ 现有办法和损失 ④ 用行为验证

概念速记：需求是用户在具体场景中要解决的问题；功能是可能的解决方案。“伪需求”不是用户撒谎，常见情况是场景不成立、痛点很弱，或把不合适的方案误当成必要需求。

主回答：我会先把用户说的功能和背后的目标分开。比如“想要自动找达人”是方案，真正的问题可能是逐个看主页太慢、筛选口径不一致。我会追问最近一次怎么做、多久发生一次、花了多少时间、不解决有什么影响，再看现有工具能不能满足。只有口头说喜欢，还不足以证明值得开发。我会用原型或小范围试用观察用户是否愿意投入时间、交出真实任务，以及做完后是否继续使用。验证不成立时，先调整人群、场景或方案，不急着给用户贴上“伪需求”的标签。

追问1：只有一个朋友提出需求，值得做吗？

追问提纲：需求线索 → 同类用户验证 → 限制投入

答：可以作为起点，但不足以证明有普遍市场。我会找不同工作背景的同类用户验证，看看问题是否重复出现。在证据不足时先做低成本验证，不直接扩大开发投入。

追问2：用户说愿意付钱，能证明需求成立吗？

追问提纲：口头意愿不等于行为 → 看真实承诺

答：只能增加一点信心，还要看是否愿意真实试用、提供任务，或者在清楚交付内容后实际付费。不能把问卷里的付费意愿直接当成收入预测。

备考备注：与 Q10 的个人调研经历配合练习。本题讲方法，不增加真实访谈人数或付费成果。

### Q77｜用户访谈、问卷、可用性测试和竞品分析分别解决什么问题？

考察点：能否按问题选择研究方法，识别样本和提问偏差。

记忆提纲：① 访谈找原因 ② 问卷看分布 ③ 测试看操作 ④ 竞品看替代方案

概念速记：定性研究重在理解原因和过程；定量研究重在估计规模、比例和差异。用户画像是影响需求和行为的特征集合，不只是年龄、性别等标签。

主回答：我会先明确想知道什么。不了解用户为什么这样工作，先访谈和观察；已经有清楚的假设，想看它在更大样本中的分布，再考虑问卷；想知道流程能不能用，就让用户拿原型完成任务，观察卡在哪里。竞品分析则看同一个任务有哪些替代方式、各自的门槛和不足，不只是做功能对照表。访谈时我会多问最近一次真实经历，少问“你是不是觉得很麻烦”。比如媒介助手，更有用的分组是独立媒介和团队媒介、任务频率、交付标准，而不只是人口属性。

追问1：问十个人够了吗？

追问提纲：研究目标 → 样本差异 → 新信息是否持续出现

答：没有固定人数适用于所有问题。早期访谈可以先做小样本找线索，再覆盖关键用户类型；要估计比例或做统计比较，就需要另行设计样本，不能拿十次访谈推断整体市场。

追问2：竞品都有的功能，我们是不是必须做？

追问提纲：是否同一人群 → 是否核心任务 → 价值与成本

答：不一定。先看竞品服务的人和我们的目标是否一致，再判断这个功能是进入市场的基础门槛，还是只适合特定客户。不能因为竞品菜单里有，就自动排进我们的版本。

备考备注：可用性测试看用户能否完成任务，不等于验证他愿意长期使用或付费。

### Q78｜BRD、MRD、PRD 分别是什么？PRD 需要写到什么程度？

考察点：是否理解商业判断、市场判断与可执行需求的区别。

记忆提纲：① BRD 为什么投入 ② MRD 为谁做和机会在哪 ③ PRD 做什么及如何验收

概念速记：BRD 常指商业需求文档；MRD 常指市场需求文档；PRD 是产品需求文档。实际名称和拆分方式因团队而异，不必机械准备三份文件。

主回答：我的理解是，BRD 主要帮助判断这件事值不值得投入，MRD 说明目标市场、用户问题和竞争机会，PRD 则把确定的方向变成团队可以开发和验收的要求。PRD 不只是页面截图，至少要说清背景和目标、用户与场景、本期范围、流程、规则、状态与异常、数据和权限，以及验收与效果指标。以资金计划为例，只写“额度不足提示”不够，还要明确谁的额度、按哪个周期、什么时候占用、失败怎么释放。文档写到团队可以据此评估和验证就有价值，不追求篇幅越长越专业。

追问1：PRD 要把技术实现写死吗？

追问提纲：产品约束明确 → 实现方案共同评估

答：要明确业务行为、性能和安全约束，但具体架构和实现方式应该与研发评估。涉及跨系统接口等关键依赖，可以附契约和约束，不能因为自己会开发就替研发包办所有技术决策。

追问2：需求评审后又变了，怎么更新？

追问提纲：记录变化 → 评估影响 → 同步版本

答：记录改了什么、为什么改、影响哪些流程和验收项，再和相关负责人确认排期。更新同一份有效版本，并通知研发测试，不能只在聊天里补一句就算完成变更。

备考备注：文档不是职责证明，面试时最好准备一条真实规则及其验收方式来举证。

### Q79｜用户故事、用户旅程、业务流程和状态机有什么区别？

考察点：能否选择合适的表达方式，把一个需求讲完整。

记忆提纲：① 故事讲目标 ② 旅程看全过程 ③ 流程看协作顺序 ④ 状态机管转换

概念速记：用户故事常用“作为某类用户，我希望完成某事，以便获得某种价值”；用户旅程包含阶段、触点、行为与痛点；业务流程描述角色和活动；状态机描述对象在事件触发下的状态变化。

主回答：这几个工具观察的角度不同。用户故事先说明谁要什么和为什么，比如媒介希望保存候选名单，方便后续联系。用户旅程会从接到任务一直看到筛选、复核和交付，发现跨页面甚至线下的阻碍。业务流程把用户、系统和人工的动作连起来。状态机则用来讲一个对象什么时候可以变化，比如检索任务从等待到运行，再到成功、失败或取消。我不会每个需求都画全套，而是选能消除歧义的表达；跨模块、多角色和异常多的需求，流程与状态通常尤其重要。

追问1：状态机对产品经理有什么实际价值？

追问提纲：允许转换 → 触发条件 → 权限与异常

答：它能提前暴露“这时能不能点”“取消后还能不能回写结果”等问题。把转换条件、操作者和失败处理明确下来，研发与测试才不容易各自理解一套逻辑。

追问2：画了流程，为什么还要验收条件？

追问提纲：描述过程不等于验证结果

答：流程说明怎么走，验收条件说明走到什么结果才算符合要求。例如提交检索之后，重复点击是否只创建一次任务，失败时是否保留已有结果，这些需要可以检查的具体条件。

备考备注：旅程图中的情绪和痛点应有观察依据，不能为了图完整而替用户编感受。

### Q80｜线框图、交互原型、视觉稿与验收标准有什么区别？

考察点：是否只会画页面，还是能说明交互规则和可交付状态。

记忆提纲：① 线框定结构 ② 原型讲交互 ③ 视觉定样式 ④ 验收查行为

概念速记：低保真适合快速讨论结构，高保真更接近最终界面；保真度高不等于需求已经验证。可用性强调任务完成难度，用户体验还包括预期、信任和整个使用过程。

主回答：线框图主要确认页面信息和操作顺序，交互原型说明点击之后怎么走，视觉稿进一步确定字体、颜色和间距。真正能交付，还需要补空状态、加载、错误、权限和边界情况，并写出验收标准。比如异步找达人，不能只画最终列表，还要让用户知道任务有没有启动、可以等多久、失败后怎么继续。做评审时，我会让大家按真实任务走一遍，而不是只看页面好不好看；做用户测试时，尽量让用户自己操作，观察是否能理解和完成任务。

追问1：原型可以点击，就能直接交给研发吗？

追问提纲：交互之外还有规则、数据与异常

答：还要补数据来源、字段校验、权限和异常规则。能点击说明展示路径连起来了，不代表真实数据和失败场景已经明确。

追问2：怎么写一个清楚的验收条件？

追问提纲：给定条件 → 触发动作 → 可观察结果

答：可以按“给定、当、那么”写。比如在任务运行中再次点击提交，应返回现有任务或明确阻止重复创建，并且不能重复扣费；具体策略由评审确认，测试据此检查。

备考备注：示例用于理解验收写法，不宣称项目已实现计费。

### Q81｜Kano、RICE、MoSCoW 怎么理解？排优先级时怎么用？

考察点：是否能用框架辅助取舍，而不是给每个需求随意打分。

记忆提纲：① 先看目标和硬约束 ② 再看价值覆盖 ③ 考虑证据和成本 ④ 明确暂时不做

概念速记：Kano 看需求满足与满意度的关系，包括基本、期望、魅力等类型；RICE = 覆盖量 × 影响 × 置信度 ÷ 工作量；MoSCoW 按本期必须、应该、可以、暂不做区分范围。

主回答：我会先排查安全、关键依赖和明确承诺这些约束，再比较需求对当前目标的贡献。Kano 可以帮助理解哪些是缺了就无法使用的基础项，哪些是额外加分；RICE 适合把覆盖范围、影响、证据强弱和投入放在一起讨论；MoSCoW 则方便确定这一版到底保什么。比如找达人，如果真实数据取不到，增加推荐解释也解决不了主任务。评分只能帮助暴露假设，不能替代判断；估计缺乏依据时，我会降低置信度或先做验证，不把一个精确分数当成确定收益。

追问1：业务方说每个需求都是 Must，怎么办？

追问提纲：不做后果 → 本期目标 → 时间资源约束

答：逐项问如果这版不做，核心流程是否走不通、是否违反明确承诺。再把总工作量和可用时间摆出来，请共同负责人确认取舍，而不是把所有需求都贴上必须标签。

追问2：RICE 分最高，就一定先做吗？

追问提纲：依赖与风险 → 估计可信度 → 解释例外

答：不一定。低分需求可能是其他功能的前置条件，也可能涉及必须处理的安全问题。可以调整顺序，但应说清原因，不让评分成为装饰。

备考备注：RICE 四项必须采用一致的时间范围和工作量单位，置信度要有证据。方法参考见新增来源 S1。

### Q82｜路线图、需求池和版本计划有什么区别？怎么控制需求蔓延？

考察点：能否把产品方向拆成可推进的版本，并管理范围变化。

记忆提纲：① 路线图讲方向 ② 需求池存机会 ③ 版本计划定范围 ④ 变更重新取舍

概念速记：Roadmap 表达阶段目标与方向；Backlog 是持续整理和排序的待办；版本计划说明近期交付范围、依赖、负责人和验收。Scope creep 指未充分评估和控制的范围持续扩张。

主回答：我会用路线图解释接下来优先解决哪些问题，用需求池保存待验证和待开发的事项，再从中选出本期版本。越接近交付，范围和验收就应该越明确；远期不适合把每个功能和日期都承诺死。新需求进来时，我会看它是否影响本期目标、需要多少额外工作、会挤掉什么，再决定替换、延期还是下个版本。比如名单功能尚未验证，就不断加入团队权限和收费体系，很容易拖慢验证。我更关注这个版本让我们确定了什么，而不只是做了多少项功能。

追问1：需求池越来越长，怎么处理？

追问提纲：目标相关性 → 新证据 → 合并与归档

答：定期按目标和证据重新看，合并重复项，对长期没有价值依据的需求标记暂缓或归档。需求池不是承诺清单，不是每一项最终都必须开发。

追问2：客户要求确定上线日期，但技术还有不确定性呢？

追问提纲：先验证关键依赖 → 分阶段承诺 → 及时同步风险

答：先和研发识别最大不确定点，安排短验证，再给有依据的计划。可以承诺阶段检查点和已确定范围，不能未经评估直接保证完整交付日期。

备考备注：需求范围、时间、质量和资源需要共同权衡，延期不是唯一解，砍范围也不是不经确认就能做。

### Q83｜Demo、PoC、MVP 和 PMF 分别验证什么？上线就算成功了吗？

考察点：是否分得清展示、技术验证、需求验证与持续市场接受。

记忆提纲：① Demo 看得懂 ② PoC 做得到 ③ MVP 值得用 ④ PMF 持续被需要

概念速记：Demo 用于演示；PoC 是概念可行性验证；MVP 用最小必要投入验证关键产品假设；PMF 指产品与目标市场形成较强匹配。它们不是必须按顺序各做一套的四个系统。

主回答：我会按要消除的不确定性来区分。Demo 帮助别人理解体验，PoC 回答关键技术链路能不能成立，MVP 则让目标用户在真实任务中验证方案是否有价值。PMF 更进一步，需要看目标用户是否持续使用、愿意付出成本，以及需求能否重复出现。拿媒介助手来说，页面能演示不代表能真实检索；能检索也不代表用户愿意持续用。上线只说明发布完成，还要继续验证结果是否被采用、复用是否发生，以及质量和成本能否支撑长期服务。

追问1：MVP 可以直接成为最终上线产品吗？

追问提纲：可以延续 → 验证目的不同 → 逐步补齐

答：可以在同一个产品上继续迭代，不一定推倒重做。但早期为了验证省掉的稳定性、权限或运营能力，可能需要在扩大使用前补齐；涉及基本安全的要求不能省。

追问2：注册人数多，能说明 PMF 吗？

追问提纲：获客不等于价值 → 看持续行为和付出

答：不能单独说明。可能只是推广带来的尝鲜，还要看目标用户是否持续完成核心任务、是否复用或付费，以及停止使用的原因。没有一条通用于所有产品的 PMF 数字门槛。

备考备注：项目当前阶段按已确认事实说明，不把方法题中的验证计划写成已取得的市场结果。

## 基础二｜产品指标、增长与商业价值（Q84-Q88）

### Q84｜北极星指标、过程指标、护栏指标，以及 OKR/KPI 有什么区别？

考察点：能否从用户价值出发选指标，并说明如何防止局部优化。

记忆提纲：① 北极星看价值 ② 过程指标找抓手 ③ 护栏限制代价 ④ 目标管理不等于指标堆砌

概念速记：北极星指标概括产品持续交付的核心用户价值；过程指标解释哪些行为推动结果；护栏指标限制不可接受的副作用。KPI 是关键绩效指标；OKR 用目标和可衡量的关键结果组织阶段工作，两者可以共用指标。

主回答：我会先问用户为什么使用产品，再决定主指标，而不是先选 DAU。比如媒介助手，用户需要的是可用于后续工作的名单，我会考虑“每周完成并被采用的有效名单任务数”作为候选价值指标，再验证它是否与持续使用相关。过程上看发起、完成、复核和采用各环节，护栏看质量、耗时和单任务成本。这样即使任务量上升，也能发现是不是靠降低质量换来的。OKR 可以围绕提高首次价值达成来设目标，关键结果用这些指标衡量；做完一个功能通常是行动，不自动等于达成了结果。

追问1：一个产品必须只有一个指标吗？

追问提纲：聚焦主价值 → 配诊断和护栏 → 多业务分层

答：不是只能看一个数。可以用一个主指标帮助聚焦，同时保留诊断和护栏。多条价值链差异很大时，可以按业务分别设指标，再看整体目标，不能强行把不同任务相加。

追问2：“上线内容审核功能”能作为关键结果吗？

追问提纲：里程碑可以记录 → 用户结果另行验证

答：它可以是交付里程碑，但如果目标是改善审核效率，还要衡量合格任务完成、复核负担或返工情况。上线说明功能交付了，不说明用户的工作已经改善。

备考备注：候选北极星属于设计建议，不代表项目已正式采纳或具备完整线上埋点。详见 Q11、Q43 的项目口径。

### Q85｜PV、UV、DAU、WAU、MAU 是什么？活跃人数怎么算？

考察点：是否理解计数、去重、时间范围和有效行为。

记忆提纲：① PV 数浏览 ② UV 去重访客 ③ 活跃定义行为和周期 ④ 黏性结合场景

概念速记：PV 是页面浏览次数；UV 是指定周期按既定标识去重的访客数；DAU、WAU、MAU 分别是日、周、月活跃用户数。周和月可以采用自然周期或滚动窗口，必须注明。

主回答：我会先定义什么行为算活跃，再计算对应周期内的去重用户。页面浏览、登录和完成一次核心任务代表不同深度，不能默认都等价。比如媒介助手，可以分别看访问活跃与任务活跃，再看二者的差距。DAU 不能简单相加得到 MAU，因为同一人可能每天回来。分析黏性时可以看 DAU/MAU，但要统一窗口；跨月比较时可以用日均 DAU 与对应月 MAU 的比值，并说明口径。对低频工作工具，周或任务周期的复用往往比每天打开更有意义。

追问1：同一天一个用户打开十次，PV、UV 和 DAU 各是多少？

追问提纲：是否触发浏览事件 → 是否同一身份 → 是否满足活跃定义

答：假设十次都触发页面浏览、身份识别一致且符合活跃定义，则 PV 为 10、UV 为 1、DAU 为 1。如果活跃要求完成任务，而他只是浏览，任务口径的 DAU 就不能计入他。

追问2：DAU 涨了，是不是说明产品变好了？

追问提纲：来源和构成 → 核心行为 → 留存质量

答：先看是新增推广、老用户回访，还是统计变化，再看这些用户有没有完成关键任务、后续是否留下来。活动引来的短期访问，不一定代表产品价值提升。

备考备注：设备数、账号数和人数不是天然相同；排除测试账号及异常流量时要有稳定、可追溯的规则。

### Q86｜激活率、转化率和漏斗怎么定义？AARRR 是什么？

考察点：能否把用户成长过程拆成可验证的行为，而不是把所有比例统称转化。

记忆提纲：① 明确起点终点 ② 固定人群和时间窗 ③ 看相邻与整体转化 ④ 找掉点原因

概念速记：激活是用户首次体验到关键价值，不一定等于注册；转化率 = 在约定窗口内完成目标的合格对象数 ÷ 起点合格对象数。AARRR 常指获客、激活、留存、收入、推荐，是观察生命周期的框架，不是强制操作顺序。

主回答：我会先说清转化的起点、终点、对象和时间窗。比如观察注册后七天内有多少用户完成首个有效名单任务，这可以作为激活的候选口径，不能把登录就直接当成体验到价值。漏斗上再拆注册、发起任务、生成结果、人工复核和采用，看哪一步掉得最多，同时看绝对人数。掉点不一定都是页面问题，也可能是不适合的用户进来了、结果质量差，或者任务本来就不需要继续。我会结合失败记录和用户观察，再确定优先改哪里。

追问1：100 人进入，40 人提交，20 人完成，怎么算？

追问提纲：同一批人 → 相邻转化 → 全程转化

答：假设这三步是同一批用户、符合顺序和时间窗，提交转化为 40%，提交到完成为 50%，全程完成为 20%。不能把不同批次的每日人数直接拼成同一个漏斗。

追问2：转化率从 20% 到 30%，提升了多少？

追问提纲：绝对变化用百分点 → 相对变化除以原值

答：提升 10 个百分点，相对提升是 50%，因为增加的 10% 除以原来的 20%。报告里要写清楚是哪一种，不能只说“提升 10%”。

备考备注：本题数字全部为教学示例。起点为 0 时转化率无定义，不应写成 0% 伪装成正常观测。

### Q87｜次日留存、七日留存、同期群和流失率怎么理解？

考察点：是否固定观察人群、返回行为和完整观察窗口。

记忆提纲：① 固定首次行为人群 ② 定义返回行为 ③ 等窗口完整 ④ 区分精确日与区间

概念速记：按自然日的第 N 日留存 = 某日完成起始事件的用户中，在第 N 天完成返回事件的人数 ÷ 当日起始人数。Cohort 是按共同起始条件分组的同期群；流失需要另行定义多长时间未使用或是否停止订阅。

主回答：我会先明确谁是这批用户、从哪件事开始计时，以及回来做什么才算留存。比如从首次完成任务开始，看七天后的任务复用，和从注册开始看是否登录，是不同指标。还要区分第七天回来、七天内回来，以及第七天或之后回来，这些不能混算。按渠道或首用月份分同期群，可以减少用户构成变化对判断的干扰。对低频媒介工具，我会结合任务周期看周复用，不能因为第二天没有工作就判定产品没有价值。

追问1：100 人注册，第七天 20 人回来，D7 就是 20% 吗？

追问提纲：属于同一群 → 满足返回事件 → 窗口已完整

答：在注册作为起始事件、20 人属于这 100 人且满足规定返回行为，并且第七天已经观察完整的前提下，是 20%。不能把第七天全站回访人数直接除以当初注册人数。

追问2：流失率就是 1 减留存率吗？

追问提纲：定义可能不同 → 未在当天返回不等于永久离开

答：不一定。1 减 D7 只表示这批用户在指定第七天没有按定义回来，不等于已经流失。订阅取消和连续一段时间无使用是另外的口径，要明确对象与窗口后再计算。

备考备注：自然日与滚动 24 小时可能给出不同结果；不同平台的名称也可能不同。时间边界参考新增来源 S2。

### Q88｜ARPU、ARPPU、CAC、LTV 和 ROI 分别看什么？

考察点：是否区分收入、利润、获客成本与长期价值，不把流量直接当商业成功。

记忆提纲：① 每用户收入 ② 每付费用户收入 ③ 获客成本 ④ 长期贡献与回本

概念速记：ARPU = 同期收入 ÷ 约定用户数；ARPPU = 同期收入 ÷ 付费用户数；CAC = 可归属获客投入 ÷ 新增客户数。LTV 是用户生命周期价值，必须注明采用收入还是毛利/贡献口径；ROI =（收益 - 投入）÷ 投入，收益不能不加说明地用流水代替。

主回答：这些指标分别回答收入从哪里来、获客花了多少，以及客户长期值不值得服务。我会先统一周期和对象，例如 CAC 的客户是注册用户还是付费客户，要明确说清。对 AI 工具，不能只看订阅收入，还要考虑模型、数据源和服务交付的变动成本。LTV 可以根据不同用户群的留存、付费和贡献逐步估计，但早期样本少时不适合给一个很确定的终身价值。我会先看单任务贡献、付费持续性和回本周期，再决定是否加大获客投入。

追问1：能直接用 ARPU 除以流失率算 LTV 吗？

追问提纲：简化模型有假设 → 收入与贡献分开 → 早期慎用

答：那是依赖稳定收入、稳定流失等假设的简化估计，周期还必须一致。若看贡献价值，还需要考虑毛利或变动成本；早期和分群差异很大的产品，更适合跟踪同期群实际贡献，不硬套公式。

追问2：收入涨了，为什么利润反而可能下降？

追问提纲：折扣与用户结构 → 单位交付成本 → 获客投入

答：可能通过折扣换来了低贡献用户，也可能重度用户带来更多模型和人工成本，或者获客开支增长更快。所以要拆收入结构和单位成本，不能只看总收入。

备考备注：这是产品商业指标学习，不是已实现付费经营的经历；没有用户收入与成本记录时，不编造 LTV/CAC。

## 基础三｜SQL、埋点与分析验证（Q89-Q93）

### Q89｜SQL 多表关联、分组、去重和 NULL，产品分析时怎么用？

考察点：能否按业务粒度写对查询，而不是只会拼语法。

记忆提纲：① 确定一行代表什么 ② 选择关联方式 ③ 正确分组计数 ④ 检查空值和放大

概念速记：INNER JOIN 保留匹配行，LEFT JOIN 保留左表行；GROUP BY 聚合到指定粒度；WHERE 在分组前筛行，HAVING 在分组后筛组。COUNT(*) 数行，COUNT(字段) 不计 NULL，COUNT(DISTINCT 字段) 计非空去重值。

主回答：我会先明确最终要统计用户、任务还是达人。比如用户表和任务表是一对多，关联后一个用户可能出现多行，不能直接把行数当用户数。需要保留没做过任务的用户时用左连接，再在正确粒度上计算。分析某天完成任务的用户数，可以先限制状态和时间，再对用户标识去重。NULL 我会先判断是缺失、未发生还是不适用，不直接都替换为零。查询完成后，用少量已知样本和总量核对结果，避免 SQL 能执行，但业务口径错了。

追问1：LEFT JOIN 后在 WHERE 限制右表状态，会怎样？

追问提纲：未匹配右表为 NULL → 可能被 WHERE 排除

答：如果写“右表状态等于成功”，未匹配的行会被过滤，可能丢掉原本想保留的无任务用户。需要保留他们时，可以把匹配条件放到 ON 中，或先按目标口径聚合右表再关联。

追问2：什么时候用 HAVING？

追问提纲：先按对象聚合 → 再按聚合结果筛选

答：比如找完成任务数不少于三次的用户，可以先筛选成功任务，再按用户分组，用 HAVING 对 COUNT(*) 的结果做限制。这个“三次”是分组后的条件，不是单行字段条件。

备考备注：结合 Q69 练习一致性排查。逻辑删除、历史版本和重试也会影响计数，不能只依赖 DISTINCT 掩盖问题。

### Q90｜窗口函数、日期窗口和去重，能解决哪些产品分析问题？

考察点：是否能处理首次行为、前后比较及周期数据，而非只会总量统计。

记忆提纲：① 窗口保留明细 ② 排序找首次或最新 ③ 时间范围统一 ④ 去重遵守业务键

概念速记：窗口函数在相关行之间计算，同时保留每行；ROW_NUMBER 可在分组内编号，LAG 可取前一行值。GROUP BY 通常把多行收成聚合结果，二者目的不同。

主回答：当我需要保留任务明细，又想知道它是用户的第几次任务，就可以考虑窗口函数。比如按用户分组、按完成时间和任务标识排序，用 ROW_NUMBER 找第一次成功任务，分析首次价值达成；用 LAG 对比相邻记录，辅助看变化。统计周期时，我会明确时区，并尽量用“开始时间包含、结束时间不包含”的范围，避免跨天重复。去重也必须先定义什么算同一事件或同一版本，不能为了让数变小，就随便保留一行。

追问1：两条记录时间相同，取最新一条怎么保证稳定？

追问提纲：明确版本语义 → 增加确定性排序键

答：时间相同不足以确定业务新旧，应优先看版本号或可靠更新时间，再加唯一标识保证排序稳定。唯一标识用于打破并列，不代表它天然能判断哪条业务上更新。

追问2：LAG 算到的是昨天吗？

追问提纲：前一行不一定前一天 → 检查日期连续性

答：不一定。LAG 取的是排序后的上一行，如果某天没有记录，上一行可能是几天前。需要日环比时要先补齐日期或明确按日期关联，再按业务含义处理缺失。

备考备注：窗口函数是补充学习项，不默认你已经熟练掌握。定义参考新增来源 S3；建议实际写查询验证后再在面试中声明熟练。

### Q91｜埋点、事件、属性和指标口径是什么？产品经理怎么写埋点需求？

考察点：能否把业务问题转成可信的行为记录，并考虑身份、重复和隐私。

记忆提纲：① 先明确决策问题 ② 定义事件与触发 ③ 补身份属性和去重 ④ 验证再出指标

概念速记：事件记录发生了什么，属性说明当时的上下文；埋点是采集行为的方式；指标是在事件和业务数据上按约定口径计算出的结果。埋点表应包含事件名、触发时机、字段类型、来源、版本和验收方式。

主回答：我会先想清楚这份数据要帮助做什么决策，再决定采哪些事件。比如分析找达人任务为什么没完成，需要区分提交、创建成功、执行结束和结果采用，不能只记录按钮点击。每个事件要说明在哪一侧触发、什么条件下只记录一次，以及关联哪个用户和任务。再补场景、版本和失败原因等必要属性，避免收集与分析无关的原始隐私内容。开发完成后，用一条测试任务检查事件顺序、重复和缺失，再和业务表对账，确认可信后才上看板。

追问1：前端显示成功，就可以记任务成功吗？

追问提纲：UI 展示与业务事实分开 → 确定权威来源

答：任务完成一般应以服务端确认的业务状态为准；前端事件可记录用户是否真正看到结果。两者解决不同问题，网络中断时尤其不能只靠前端提示判断任务是否执行成功。

追问2：怎样避免同一事件被重复统计？

追问提纲：唯一标识 → 上报与去重规则 → 保留重试信息

答：为事件设计稳定标识，并明确重发时是否复用它，数据侧按规则去重。任务本身的多次尝试要另外保留，不要为了消除上报重复，把真实重试也删掉。

备考备注：本题是埋点设计方法，不代表媒介助手已有正式增长分析系统。安全与权限是数据设计的一部分。

### Q92｜趋势、分群、漏斗、同期群和相关性分析，分别什么时候用？

考察点：是否先定义问题，再选分析角度，并避免把相关当因果。

记忆提纲：① 趋势找时间变化 ② 分群找差异 ③ 漏斗找环节 ④ 同期群控构成

概念速记：环比与相邻可比周期比较，同比与上一年对应周期比较；分群按用户、场景、渠道等拆分；漏斗看步骤转化；同期群固定起始人群看后续行为。相关表示共同变化，不直接说明谁导致谁。

主回答：我会先把问题说具体，再决定分析方法。比如任务完成率下滑，先看从什么时候开始，是持续变化还是单日波动，再按版本、渠道和任务类型拆分；如果只在某个环节掉，就看漏斗和失败样本。研究留存时再固定同期群，避免新用户比例变化干扰结论。即使发现使用某功能的人留存高，也可能是高意愿用户更爱用它，不能直接说这个功能提高了留存。数据先帮助提出解释，再用更接近因果的实验或其他验证来判断。

追问1：环比下降，但同比上涨，矛盾吗？

追问提纲：基准不同 → 季节性和日历 → 解释背景

答：不矛盾，因为比较的基准不同。可能本月比上月弱，但比去年同月更好。还要看工作日数量、活动和季节性，不能只挑对自己有利的比较方式。

追问2：每个主要分群都改善，整体为什么反而变差？

追问提纲：权重改变 → 低转化群占比提高 → 固定构成对比

答：可能低转化人群占比大幅上升，把整体拉低了，这类现象常被称为辛普森悖论。应同时看分群表现和流量构成，必要时按固定权重比较，别只凭总数评价版本效果。

备考备注：观察性分析能提供证据但通常不能单独证明因果；小样本、节假日和数据延迟应先排查。

### Q93｜A/B 测试、灰度、统计显著性和 MDE 有什么区别？

考察点：是否知道实验能回答什么、何时结果可信，以及不应怎么解释数字。

记忆提纲：① 随机对照看效果 ② 灰度控制发布风险 ③ 显著不等于重要 ④ 样本不足不硬下结论

概念速记：A/B 测试用可比较的随机分组估计方案效果；灰度是分阶段放量，不天然构成实验。MDE 是预先关心的最小可检测效果；统计功效描述在设定效果真实存在时检出它的概率；p 值不是“方案正确的概率”。

主回答：我会先提出一个可验证的假设，确定主指标和不能恶化的护栏，再和数据同学确认分流单位、样本量、周期和分析方式。A/B 的关键是分组可比，灰度更多是控制风险，两者可以结合但不能互相替代。读结果时既看差异和置信区间，也看差异有没有业务意义、护栏是否受损，并先排除分流比例或埋点异常。像我的个人项目，如果流量不足，我会先做离线对照和小范围任务验证，不把少量用户的前后变化说成可靠的 A/B 因果结论。

追问1：p 小于 0.05，是否表示有 95% 概率方案有效？

追问提纲：条件概率方向不同 → 显著性不等于业务收益

答：不是。p 值是在零假设和统计模型成立时，出现当前或更极端数据的概率。还要看效果大小、不确定范围和业务代价，不能把它翻译成方案有 95% 概率正确。

追问2：实验没显著，是不是两个方案一样？

追问提纲：证据不足不等于相同 → 看区间和功效 → 不随意提前停止

答：不是，可能样本不足，也可能真实差异很小。要看区间是否仍包含有意义的收益或损失；如果想证明足够接近，需要另设等效性判断。常规实验不能反复看数，一显著就停，除非采用适配的序贯方法。

备考备注：95% 置信区间表示，在方法假设成立时反复抽样构造区间，约 95% 的区间会覆盖真实参数；不简单等于“真实效果以 95% 概率落在这次区间里”。分流异常与护栏参考 S4；本题不冒充正式线上实验经历。

## 基础四｜研发协作、服务质量与 AI 技术沟通（Q94-Q99）

### Q94｜敏捷、Scrum、Sprint、UAT 和 DoD 是什么？产品经理怎么参与？

考察点：是否理解迭代协作和验收责任，而不是把敏捷等同于催进度。

记忆提纲：① 短周期反馈 ② 目标与范围协商 ③ 业务验收与质量门槛 ④ 复盘改协作

概念速记：敏捷强调持续反馈与适应；Scrum 是一种具体框架，Sprint 为不超过一个月的固定长度周期。UAT 是用户验收测试；DoD 是完成的共同质量标准。Review 检视产品结果，Retrospective 复盘团队工作方式。

主回答：我理解敏捷的重点是尽早交付可检查的结果，再根据反馈调整，不是需求随时改、研发随时接。如果团队采用 Scrum，我会结合实际角色参与目标与需求排序，澄清规则和验收条件，再与研发协商本期范围。开发过程中及时解决业务疑问和依赖，上线前通过 UAT 确认能否完成实际工作，同时遵守测试、安全和文档等完成标准。迭代后既看功能效果，也看协作哪里返工多。我的正式经历主要是开发与交付协作，不会把它说成独立担任过 Scrum 产品负责人。

追问1：开发说做完了，测试说没做完，怎么办？

追问提纲：编码完成不等于交付完成 → 对照验收与 DoD

答：先看“完成”是不是指不同阶段。代码写好、测试通过、业务验收和可发布不是一回事，应提前约定统一完成标准。再把未满足项列出来确定责任和处理方式，不靠口头争论。

追问2：验收标准和 DoD 是一回事吗？

追问提纲：单项业务条件 → 通用质量标准

答：验收标准通常针对具体需求，比如额度释放是否符合规则；DoD 更像团队对增量完成的共同要求，例如必要测试已通过。两者互补，业务功能能用不意味着质量要求都满足了。

备考备注：Scrum 的角色与事件参考 S5。产品经理职位不自动等于 Scrum 中的 Product Owner；缺陷严重程度与修复优先级也应分开讨论。

### Q95｜QPS、TPS、并发量、P95 延迟、SLI/SLO/SLA 怎么转成产品要求？

考察点：是否能把服务能力与用户体验联系起来，而不是只听懂缩写。

记忆提纲：① 区分流量和在途量 ② 看整体与长尾等待 ③ 定义服务目标 ④ 决定排队、限流与降级

概念速记：QPS 常指每秒请求/查询数；TPS 在交易系统常指每秒事务数，在模型场景可能指 tokens/s，必须确认单位。并发量是同一时刻处理中任务或连接的数量。P95 是约 95% 样本不超过的延迟值；SLI 是测量指标，SLO 是内部目标，SLA 是对外服务约定。

主回答：听到这些词，我会先确认测的是哪个环节、什么单位，以及用户实际感受到什么。比如平均接口响应很快，不代表生成名单的端到端等待很短，还要看排队和长尾。QPS 和并发也不能直接互换，同样请求速率下，单次处理越久，在途任务通常越多。产品侧我会和研发根据使用高峰、任务时限和成本确定目标，再选择异步处理、排队提示、并发限制或降级。对 AI 交互还会区分首个输出出现的时间与全部结果完成的时间，不拿一个速度指标代替整体体验。

追问1：100 QPS、平均处理 2 秒，能估算并发吗？

追问提纲：稳定流量 → 同一系统边界 → 平均在途量

答：在系统稳定、统计边界一致等条件下，平均在途量可粗估为 100 乘 2，即约 200。如果两秒包含排队，这估计也包含排队请求；不能直接拿它当线程数或容量上限，仍需压测。

追问2：研发说要把所有请求都做到一秒内，产品该怎么判断？

追问提纲：任务等待容忍度 → 尾部目标 → 成本和可行性

答：先看用户任务是否真的需要，再明确目标覆盖比例、输入规模和异常情况。长任务可能更适合及时反馈进度，而不是为极少数请求投入过高成本；外部承诺必须有验证依据。

备考备注：SLI/SLO/SLA 参考 S6。模型首 token 延迟常称 TTFT，输出速度快不等于首 token 到得快。本题数字是教学示例，不是项目压测结果。

### Q96｜API、同步异步、回调、幂等、超时和重试，产品经理要理解什么？

考察点：能否把系统边界变成可理解、可恢复的业务行为。

记忆提纲：① 接口说明契约 ② 长任务异步反馈 ③ 重复请求防副作用 ④ 超时先查状态

概念速记：API 约定系统间如何交互；同步通常等待当前调用返回结果，异步可先返回任务标识再获取结果；回调由执行方通知接收方，轮询由查询方反复获取状态。幂等强调同一业务操作重复执行不产生额外业务副作用。

主回答：产品经理不一定负责写接口，但要知道请求代表什么、结果什么时候可信、失败后用户怎么办。比如找达人耗时较长，可以先返回任务标识，让用户查看进度，再通过通知或轮询获取结果。重复点击不能意外生成多份同一业务任务，所以要与研发约定幂等范围。超时也不等于执行失败，可能任务已经成功只是响应没回来，应先查状态，再决定是否重试。这样才能避免重复下单、重复占用或重复扣费，同时让用户清楚哪些结果可以继续使用。

追问1：前端把按钮禁用，就算幂等了吗？

追问提纲：前端仅改善体验 → 后端保证业务唯一性

答：不算。用户可以刷新、多端操作，网络也可能自动重发。前端限制只能减少误触，后端仍要用业务标识、幂等键或约束处理重复，并规定同一请求返回什么结果。

追问2：所有失败都应该自动重试吗？

追问提纲：区分可恢复错误 → 次数与间隔 → 副作用和成本

答：不应该。参数不对或没有权限通常要先修正；临时超时、限流可以考虑有限重试和退避。还要评估操作是否幂等、是否重复收费，以及多次失败后怎样转人工或提示用户。

备考备注：资金项目可以帮助举例业务状态风险，但不要声称自己设计过尚未确认的支付网关或计费系统。

### Q97｜AI 调用量、Token 成本、调用成功率和单任务成本怎么定义？

考察点：是否把供应商消耗、系统执行和用户结果分开衡量。

记忆提纲：① 一次任务可能多次调用 ② 费用按真实计费项 ③ 成功分接口与任务 ④ 计算失败和重试代价

概念速记：Token 是模型处理文本等输入输出时使用的计量单元，不等于一个汉字或一个单词。调用量计实际请求，任务量按业务标识去重。单成功任务成本可定义为同一任务批次的总可归属成本 ÷ 成功任务数，分子包含失败尝试与重试。

主回答：我会先把一个用户任务和内部模型调用分开。一次找达人可能包含解析、匹配等多次调用，次数增加可能是任务量增长，也可能是重试或循环失控。费用要按输入输出、缓存和其他计费项核算，再加上约定范围内的数据源、基础设施或人工成本。接口正常返回不等于输出可用，更不等于用户完成了任务。我会同时看首次调用成功率、最终任务完成率、结果采用和单成功任务成本，避免通过返回空结果或无限重试把成功率做高。

追问1：怎样计算一个任务的模型费用？

追问提纲：归集调用 → 按计费分类 → 汇总重试和工具

答：把该任务各次调用关联起来，按供应商当时的输入、输出和缓存等价格计算并求和；如有图像、音频或工具单独计费也要计入。再与实际账单核对，不用一个长期固定单价估算所有模型。

追问2：总成本下降了，就值得上线新方案吗？

追问提纲：同任务结构比较 → 质量和采用不能丢 → 人工成本补齐

答：还要确认是不是任务量或难度下降导致的，并看质量、完成率和人工返工有没有变差。只有在可比任务上，总交付成本更合理、效果满足要求，才说明方案可能更优。

备考备注：本地 Eval 与用量记录不等于已部署线上成本看板。统计口径应说明是否含人力和固定成本，以及账单与请求记录的差异。

### Q98｜准确率、精确率、召回率、F1、幻觉率和 Bad Case 怎么理解？

考察点：能否根据错误代价选择指标，避免被一个高分误导。

记忆提纲：① 明确正类和样本 ② 区分误报与漏报 ③ 按业务代价取舍 ④ Bad Case 回流评测

概念速记：设“有风险”为正类：TP 是正确报风险，FP 是误报风险，FN 是漏报风险，TN 是正确判无风险。准确率 = (TP+TN)/全部样本；精确率 = TP/(TP+FP)；召回率 = TP/(TP+FN)；F1 = 2×精确率×召回率/(精确率+召回率)。

主回答：我会先确认评的是什么对象，以及哪一种错更严重。审核里，精确率看报出的风险有多少是真的，召回率看真实风险有多少被找出来；如果绝大多数内容本来就没风险，全部判安全也可能得到很高的准确率。高风险漏报通常需要重点控制，但也不能让误报把人工复核压垮。生成任务的幻觉率还要另定单位，可以按含无依据事实的回答计，也可以按具体断言计，不能混用。Bad Case 是不满足预期的案例，我会按数据、检索、模型和流程分类，定位后加入回归评测。

追问1：20 条实际有风险，报出 25 条，正确报出 15 条，怎么算？

追问提纲：TP=15 → FP=10 → FN=5 → 分别代入

答：精确率为 15/25，即 60%；召回率为 15/20，即 75%；F1 约为 66.7%。没有总样本数或 TN，不能继续算准确率。这里的数字只用于练习，不是我的项目指标。

追问2：模型自己说“置信度 95%”，能当准确率吗？

追问提纲：自报分数不是实测 → 标注集验证 → 关注校准

答：不能。自报分数不等于对真实样本统计出的正确比例，除非经过可靠验证和校准。我要用独立标注样本评估，并记录高置信错误，不能把模型语气确定当成可靠。

备考备注：分类公式参考 S7。分母为零时应按约定标注无定义或采用明确的工具处理规则；F1 不考虑 TN，也不能替代错误成本评估。幻觉之外，漏项、拒答和格式错误应另行分类。

### Q99｜SFT、LoRA、Embedding 和 RAG 各解决什么问题？怎么转成产品决策？

考察点：是否分清训练方法、参数更新方式、语义表示与检索增强。

记忆提纲：① SFT 学任务示范 ② LoRA 降低可训练参数量 ③ Embedding 表示相似性 ④ RAG 补外部依据

概念速记：SFT 是监督微调，利用输入与期望输出等示范数据训练；LoRA 是参数高效微调方法，通常冻结基础权重并训练低秩适配参数，可用于 SFT，二者不是二选一。Embedding 把内容表示为向量，RAG 则在生成时引入检索到的资料。

主回答：我会先看效果差的原因，再讨论技术。知识经常更新、回答缺少依据时，优先评估检索和 RAG；任务格式或行为长期不稳定，有足够高质量示范数据时，再与算法评估 SFT。LoRA 可以作为实现微调的一种方式，减少需要训练的参数，但不保证效果一定更好，也不能解决数据质量问题。Embedding 更多用在相似检索等环节，向量相近不代表内容一定真实或业务上合适。最终我会比较独立评测结果、上线维护和成本，而不是因为某个词热门就采用；我对微调的定位是理解方案和协作判断，不冒充训练实操经验。

追问1：用了 Embedding，就一定用了 RAG 吗？

追问提纲：向量可独立服务检索 → RAG 需要连接生成

答：不一定。Embedding 可以只用于搜索、聚类或推荐；只有把检索资料用于支持生成的链路，才是在做检索增强生成。反过来，RAG 也不强制只能使用向量检索。

追问2：把企业全部文档拿去微调，就不用知识库了吗？

追问提纲：知识更新与引用 → 权限管理 → 方法可组合

答：不能这样简单替代。微调不保证逐条记住事实，也不天然提供更新、权限过滤和出处引用；这些需求更适合评估知识检索。微调可以改善行为，RAG 可以提供资料，两者也可以组合并分别验证。

备考备注：SFT 与 LoRA 参考 S8、S9。关于个人项目的实际 RAG/Embedding 实现程度，以 Q54 和已验证材料为准，概念学习不改变项目事实。

### Q07｜AI 应用和 Agent 有什么区别？

考察点：概念清楚，知道何时需要自主执行。

记忆提纲：① 产品与执行方式 ② 固定流程也能做 AI ③ Agent 动态选行动 ④ 自主性有成本

主回答：AI 应用是在说产品用 AI 解决什么问题，Agent 是完成任务的一种执行方式。比如固定步骤分析 JD、改简历，就是 AI 应用，不一定需要 Agent。若系统拿到搜索结果后，要判断下一步查什么、调哪个工具、什么时候结束，就更适合 Agent。它的价值是处理路径不固定的任务，代价是更难控制成本和错误。我不会默认应用都要做成 Agent，而是看动态决策能否带来实际收益。〔来源1〕

追问1：媒介助手属于哪种？

追问提纲：整体是应用 → 模块不同自主度

答：整体是 AI 应用。审核更适合固定阶段的 Workflow；找达人有按结果继续检索或结束的循环。目前不少动作由代码策略控制，模型做意图和内容理解，是受控执行，不是全程自主规划。

追问2：什么场景不用 Agent？

追问提纲：路径明确 → 错误代价高 → 规则先行

答：固定字段提取、报表汇总、按明确规则校验，通常先用固定流程。付款这类高风险动作，也不能因为模型说要执行就直接执行，必须有确定的权限、业务校验和确认环节。

答：上海是我这次明确的求职城市。我会重点找企业 AI 应用和效率工具团队，希望发挥原来的企业项目经验，也希望在一个城市持续积累，不跟着短期热点频繁换方向。

追问2：大厂和创业公司怎么选？

追问提纲：优先中大厂 → 看真实职责

答：目前优先中大型公司，想在成熟协作环境里把产品基本功补扎实。但最终也看岗位：有没有真实用户、能否负责完整模块、评价标准是否清楚。只有公司名气、实际工作不匹配，也会慎重。

### Q75｜未来 3—5 年，你的职业规划是什么？

考察点：职业方向是否稳定，成长目标是否建立在岗位责任与实际成果上。

记忆提纲：① 先独立负责模块 ② 再做透业务场景 ③ 兼顾效果与商业 ④ 管理随责任发展

主回答：未来一年，我希望先完成从开发到 AI 应用产品的转变，能独立负责一个明确模块，把需求判断、研发推进和上线后的效果复盘做完整。两到三年，希望在一个业务领域持续积累，比如企业效率或营销工具，能够负责完整场景，既判断模型能力，也判断用户价值和投入产出。三到五年，希望有能力负责更完整的产品方向，做跨团队的优先级和资源取舍。如果有带团队的机会，我愿意承担，但会以已经做出的产品结果为基础。对我来说，这次转岗希望建立的是长期产品能力，而不是短期追一个 AI 头衔。

追问1：三年后没有带团队的机会，你会离开吗？

追问提纲：职责成长 → 业务积累 → 不以头衔单一判断

答：不会只因为没有管理头衔就离开。我会看负责的问题是否更复杂、决策范围是否扩大、是否持续积累产品成绩。如果能深入业务并承担更大的结果责任，资深个人贡献者也是有价值的发展路径。

追问2：AI 变化很快，怎么保证规划不失效？

追问提纲：稳定目标 → 灵活技术路径 → 周期复盘

答：我规划的是需求判断、数据分析、协作和结果验证能力，具体模型和工具会随业务更新。阶段性复盘岗位和技术变化，调整学习内容与项目选择，但不会因为出现一个新概念就频繁更换职业方向。

备考备注：对应本次原题 13。与 Q08 共用职业主线；本题展开到 3—5 年，面试时按对方要求选择长短版本，避免两道题给出不同方向。

## 二｜个人项目：把产品决策讲具体（含 Q65 从 0 到 1 推进）

### Q09｜用两分钟介绍媒介助手

考察点：讲清用户、问题、关键方案和结果，不罗列功能。

记忆提纲：① 逐个找人和查证很慢 ② 筛选与审核两项任务 ③ AI 理解、规则执行、人复核 ④ 自测与下一步

主回答：媒介助手是我从朋友的实际工作里发现的机会。她做素人投放，需要搜关键词、逐个看主页和内容，再整理名单；图文宣传表达还要另行检查。问题不只是搜索慢，而是重复筛选和查证占用了时间。我把产品分成两块：找达人时，先把自然语言需求转成条件，代码处理粉丝范围和去重，模型辅助判断内容是否匹配，再进入候选管理；审核时，把图文、规则依据和风险位置放在一起，给修改建议，最终由人确认。我独立推进了调研、需求、Figma 原型、开发和测试。在一天自测里，20 人名单从约 3 小时缩短到 40—60 分钟。目前还在备案、准备上线，下一步重点看真实媒介采用率，以及审核是否减少复核工作量。

追问1：41 人能说明什么？

追问提纲：技术验收 → 不是用户成果

答：那是历史验收里真实落库的达人数量，说明检索、保存、展示和导出链路跑通。它不是注册人数，也不能直接证明候选质量。业务价值要看有多少人被媒介认为值得进一步沟通。

追问2：一人项目如何证明协作？

追问提纲：独立推进与团队协作分开举证

答：这个项目主要证明我能独立做取舍、推进到底。团队协作用保融经历说明：从产品澄清到测试联调、实施上线，再到驻场客户沟通，这些是在多人交付环境里实际做过的。

### Q10｜如何发现和验证需求？

考察点：把一句抱怨转成可验证的用户问题。

记忆提纲：① 还原真实任务 ② 找耗时和返工 ③ 确认可用标准 ④ 用任务验证

主回答：我会先看用户最近完成的一次任务，而不是直接问想要什么功能。媒介说找人慢，要拆出时间花在想关键词、看主页、判断匹配还是整理名单；再问哪些候选最后会被淘汰，达到什么标准才能交出去。这样才能判断 AI 该介入哪一步。媒介助手的起点是朋友的真实需求，之后更重要的验证是让同类用户带自己的任务来试，看总耗时、采用和返工，而不是只问界面喜不喜欢。

追问1：访谈问了什么？

追问提纲：最近一次 → 淘汰理由 → 交付标准

答：已经确认的是她通过关键词搜索、逐个进入主页筛选，很耗时间。继续深挖时，我会围绕“最近一份名单怎么做出来”“为什么排除某个人”“交给同事后还重做什么”来问，比泛泛问想要哪些 AI 功能更有效。

追问2：其他媒介流程不同怎么办？

追问提纲：任务分群 → 先服务一类

答：先看是否属于不同群体。个人媒介重视快速初筛，机构团队可能还需要审批和多人协作。第一版先做好一个群体的核心任务，共性用标准流程，少量差异用可配置条件，不直接做成大平台。

### Q11｜核心问题和北极星指标是什么？

考察点：分清价值规模、任务质量和诊断指标。

记忆提纲：① 交出可用名单 ② 北极星看价值产出 ③ 完成率解释质量 ④ 审核分开衡量

主回答：核心价值是让媒介更省力地交出可用名单。稳定使用后，我会把“每周被用户确认可用于下一步沟通的名单任务数”作为北极星候选，因为它包含使用量和被认可的价值。名单任务完成率、总耗时、候选采用率用来解释它为什么变化。当前冷启动阶段，先验证单次任务有没有价值，比追总量更重要。审核是另一类任务，要单独看有效初审和人工复核成本，不能把两类产出简单相加。

追问1：为什么不用 DAU？

追问提纲：非每日任务 → 登录不等于价值

答：媒介不一定每天建名单，登录也可能只是看一眼。DAU 能观察活跃，但不能代表工作完成。北极星更应该贴近被认可的交付，同时要固定任务粒度，防止把一件事拆成很多任务来做高数量。

追问2：有效候选怎么定义？

追问提纲：硬条件合格 → 业务愿意推进

答：先满足事先确认的粉丝、主题等必要条件，再由媒介判断是否值得联系。系统高分只是筛选信号，不直接等于有效，更不等于合作。统计时要把候选、采用和合作分开。

### Q12｜如何确定 MVP 和优先级？

考察点：围绕关键假设缩范围，不是机械减少功能。

记忆提纲：① 最大不确定性 ② 最小完整任务 ③ 安全底线保留 ④ 非核心后置

主回答：MVP 要用最小投入验证产品是否成立。媒介助手有两个关键假设：真实数据能取得，筛出来的人值得用。所以先验证数据链路，再围绕解析条件、检索筛选、人工确认、保存导出做一条完整路径。团队权限、多平台和复杂运营后置，但必要的用户隔离和失败恢复不能省。审核可以独立验证，不能因为与媒介相关就无限扩大首版范围；资源紧时先证明找人这一项价值。

追问1：为什么审核也进入 MVP？

追问提纲：另一具体任务 → 承认范围取舍

答：它也是媒介工作中的问题，而且可以独立使用。但同一群用户，不代表两项任务都值得首版做。复盘看范围偏宽；更合理的是先验证找人，审核用小样本单独测试，再决定是否正式合并。

追问2：只给一周砍什么？

追问提纲：保完整任务 → 削管理复杂度

答：保留真实数据、核心条件、结果解释、人工选人和导出，不做复杂分组、团队权限和商业化。审核先做受控验证。这样一周后至少能判断一项任务有没有价值。

### Q13｜为什么自然语言输入，不用传统表单？

考察点：按输入特性选择交互，不为了 AI 化改入口。

记忆提纲：① 复杂表达用文本 ② 精确约束用控件 ③ 执行前确认 ④ 混合输入

主回答：自然语言不应该完全替代表单。媒介需求既有粉丝范围，也有“像真实分享、不要机构感”这种难枚举的描述。自然语言适合后者，数值、日期和明确排除项仍适合控件。我的方案是先解析成用户看得懂的条件，再允许修改确认后执行。这样降低输入门槛，也避免模型误解一个关键条件，后面整批检索都跑偏。

追问1：解析错了怎么办？

追问提纲：高影响先确认 → 无损修改

答：粉丝上限、排除项这类关键条件执行前展示；明显冲突或缺失时先问清。修改后更新结构化条件，不让用户重新打一大段话，也不把“没填写”自动当成“不限制”。

追问2：哪些条件必须用控件？

追问提纲：可枚举 → 误解代价大

答：粉丝区间、时间范围、批次数量和明确开关优先用控件；内容风格和经历要求保留文本加样例。不是控件越多越好，而是用最低操作成本把关键约束确定下来。

### Q14｜为什么不把全部筛选和审核交给模型？

考察点：合理分工，兼顾质量、成本和可排错性。

记忆提纲：① 确定规则用代码 ② 语义理解用模型 ③ 高风险人确认 ④ 按错误调整分工

主回答：因为这些判断需要的能力不同。粉丝超没超范围、达人是否重复，代码更稳定，也没必要花模型费用；判断内容是否符合某种经历或风格，模型更有优势。审核还要区分疑似风险和最终结论，关键内容由人复核。这样不仅省成本，也容易排错：究竟是条件设错、数据缺失，还是模型理解错，而不是所有问题都混在一段回答里。

追问1：规则和模型冲突怎么办？

追问提纲：硬约束不覆盖 → 语义规则看语境

答：用户明确的粉丝区间是硬约束，模型评分再高也不能覆盖。审核关键词则要看上下文，引用、否定与直接宣传不一样。命中可触发检查，但不能所有命中都直接判成违规。

追问2：什么时候调整边界？

追问提纲：错误分类 → 对照验证

答：规则误伤多、表达变化大时，让模型参与理解；模型在固定条件上反复出错，就补代码校验。调整后用原来的失败样本和独立测试样本一起检查，不只看修好了一个例子。

### Q15｜项目到底是 Workflow 还是 Agent？

考察点：解释执行设计及理由，不靠模块名包装。

记忆提纲：① 审核固定阶段 ② 检索按反馈调整 ③ 约束由代码控制 ④ 按需开放自主性

主回答：我按任务特点分开设计。审核要检查素材、规则、证据和风险，阶段相对确定，用固定 Workflow 更容易保证覆盖和追溯。找达人会遇到数量不足、重复多、关键词效果差，需要按结果续搜或结束，适合做反馈循环。当前动作选择主要由代码策略控制，模型负责意图和内容判断。我的重点不是追求更自主，而是让系统在明确约束下完成任务，错误时知道在哪一步停下来。

追问1：Workflow 与 Agent 边界在哪？

追问提纲：谁决定下一步 → 自主程度

答：固定代码分支可以很复杂，也可以循环，但仍是预设控制；模型根据目标和观察自主选择下一步工具或路径，才体现更强的 Agent 自主性。两者可以混合，有循环不自动等于完整 ReAct。

追问2：为什么有 Planner 和 Skill？

追问提纲：组织计划 → 复用能力

答：Planner 组织执行计划，Skill 封装专项能力，便于复用和测试。计划也可以由代码生成，不能因为模块叫 Planner 就说有模型自主规划。职责分开，后续换策略时就不用重做每项能力。

### Q16｜为什么每批 20 人？不足怎么办？

考察点：数量、质量、等待与成本的取舍。

记忆提纲：① 复核负担 ② 等待与调用成本 ③ 不凑数 ④ 保存续检进度

主回答：20 人是当前批量的产品取舍，不是技术只能取到这个数。批量越大，读取和判断越多，等待和复核负担也越大；太少又不够选择。因此先用 20 人作验证起点，观察采用和等待情况。不足时继续检索，但不能牺牲核心条件凑满；数据耗尽或服务受限，就返回真实结果和原因，保留进度，避免下次重新查一遍。

追问1：20 怎么验证？

追问提纲：比较批量 → 足量候选的总成本

答：比较不同批量下，拿到足够可用候选要多久、检查多少人、消耗多少接口成本。如果 10 人就够，20 人可能浪费；若多数任务要筛很多人，就考虑渐进交付和继续检索。

追问2：为什么不分页展示 50 人？

追问提纲：展示成本不等于处理成本

答：分页只解决页面放不放得下，不自动减少获取和分析 50 人的成本。可以测试边检索边交付，但不能只是分几页，就认为等待和人工负担消失了。

### Q17｜怎么让结果可解释、可追溯？

考察点：可解释性如何服务用户决策，而非展示一大段模型推理。

记忆提纲：① 展示判断证据 ② 定位原始内容 ③ 保存版本快照 ④ 支持纠错

主回答：我希望解释能帮助用户决定“用不用这个结果”。达人结果要说明匹配了什么、哪些条件没满足，并能回到主页或内容；审核则展示风险原文、规则依据和修改理由。后台还要保存任务输入、规则和知识版本，方便复现争议。没必要把模型的整段推理展示出来，用户更需要可核实的证据和不确定项。有出处只是第一步，还要验证出处确实支持这个判断。

追问1：证据错了怎么办？

追问提纲：暂停确定结论 → 修正来源 → 回归

答：先把对应结果标成待确认，不继续用错误证据支撑结论。再分清原数据错、定位错还是模型曲解。修正后重跑相关项，并把这个例子放进回归集，避免只换一段解释。

追问2：引用正确率怎么算？

追问提纲：固定分母 → 存在、定位、支持

答：以抽检引用为单位，只有来源存在、定位正确、内容支持结论都满足，才计为正确。同时看重要结论有没有漏引；只统计已引用部分，可能掩盖关键结论根本没证据的问题。

### Q18｜怎么评估项目效果？

考察点：将业务价值、AI 质量与工程表现连起来。

记忆提纲：① 业务任务是否更好完成 ② 分阶段找原因 ③ 同质量比较总成本 ④ 线上线下联动

主回答：我会分三层。业务层看可用名单是否更快交出、审核是否减少查证和返工；质量层看条件解析、候选相关性、审核漏报误报和引用；工程层看成功率、等待和单任务费用。比如系统搜得快但候选不合格，人工复核更久，不能算提效。评估要把等待、修改和整理都算进总任务成本，再用分阶段指标解释原因。本地 Eval 用来发现回归，真实用户任务用来证明业务价值，两者不能互相替代。

追问1：小样本全对为什么不能宣传？

追问提纲：覆盖偏差 → 调试泄漏 → 不确定性

答：可能只测了容易题，或者这些题已经参与调试。即使全对，也只能说明这批样本表现好，不能推成普遍准确率。我会同时报告数量、类型和测试条件，再扩到真实难例。

追问2：谁标注，分歧怎么办？

追问提纲：业务专家 → 独立判断 → 争议裁定

答：候选由熟悉任务的媒介判断，复杂审核找有审核经验的人。先写清标准，部分样本双人独立标注；分歧保留原因，再讨论适用条件。不是简单投票凑一致，而是把模糊规则明确下来。

### Q19｜项目当前取得什么结果？

考察点：能否把交付成果、初步价值和下一步验证分清。

记忆提纲：① 两条功能路径 ② 一天计时自测 ③ 准备上线阶段 ④ 下阶段验证采用

主回答：目前的成果有两类。功能上，已完成找达人、候选管理和导出，以及图文辅助审核相关开发和内部验证。价值上，我亲自做过一天测试，20 人名单从原来约 3 小时缩短到 40—60 分钟，说明这个方向有继续验证的价值。项目还在备案、准备上线，接下来不是继续堆功能，而是让真实媒介带任务试用，验证候选采用和重复使用；审核也要独立测复核耗时与漏报，不能借用找人的提效结果。

追问1：跑通和稳定上线有什么区别？

追问提纲：一次成功 → 多条件可用 → 能恢复

答：跑通说明特定输入和环境下能完成；稳定上线还要覆盖不同用户、数据源异常、并发和网络问题，失败后能恢复，并且有监控。一次成功不能证明持续服务能力。

追问2：内部验收有哪些边界？

追问提纲：版本与样本 → 业务结果另测

答：内部验收确认的是这版功能是否按规则工作，不能直接证明所有行业适用或用户愿意持续用。模型、规则或数据源变了，关键场景还要回归；业务价值需要真实使用另外验证。

### Q20｜准备怎么冷启动？

考察点：先找到能验证价值的人，而不是泛泛说做推广。

记忆提纲：① 同类媒介种子用户 ② 真实任务陪跑 ③ 首次完成与复用 ④ 有案例后推广

主回答：我会先找正在做素人名单、愿意带真实任务来的媒介，而不是先追求注册量。第一批从朋友及她介绍的同行开始，陪他们完成一次任务，记录原流程、最终采用和没用上的原因。做成一次后，再看下一次类似任务会不会主动回来。等能够讲清“哪类需求、怎么用、结果怎样”，再在小红书分享真实案例引流。冷启动前期最重要的是缩短价值验证，不是把流量先灌进来。

追问1：首批用户从哪来？

追问提纲：现有关系 → 符合任务条件

答：先通过媒介朋友联系同行，但筛选条件是近期有真实需求、愿意反馈，而不只是认识我。后面用同场景的案例内容吸引陌生用户，逐步降低熟人样本的偏差。

追问2：朋友反馈会偏吗？

追问提纲：看行为 → 引入陌生样本

答：会。所以不只听“挺好”，更看有没有用真实任务、采用多少、下次还用不用。也要尽快引入不认识我的用户。熟人反馈适合发现明显问题，不能直接证明市场需求。

### Q21｜竞品和差异化是什么？

考察点：理解替代方案和选择理由，不拿技术名词当壁垒。

记忆提纲：① 平台与人工都是替代 ② 比完整任务成本 ③ 聚焦细分流程 ④ 验证差异是否成立

主回答：我会比较两类替代：达人发现平台，以及人工搜索加表格的现有做法。真正要比的是同一份名单从需求到交付的总成本，包括数据覆盖、候选质量、复核和整理，而不只是有没有自然语言输入。媒介助手的切入点是个人媒介的工作流程，把需求理解、筛选、候选管理和图文初审衔接起来。这个差异要靠用户采用验证，Agent、RAG 本身不是壁垒。后续更值得积累的是业务标准、任务反馈和持续可用的数据能力。

追问1：平台也加自然语言搜索呢？

追问提纲：功能不再稀缺 → 比流程价值

答：那就不能把自然语言当差异化。要看我们是否在某类任务的采用率、复核时间和使用成本上更好；如果没有明确优势，就缩小场景，而不是继续增加一个相似功能。

追问2：为什么不用成熟平台？

追问提纲：尊重替代 → 验证未满足需求

答：如果成熟平台已经解决得好，用户就该用它。我的机会应来自它没有满足的需求，比如某类筛选标准或操作负担；这些必须通过访谈和同任务比较确认，不能预先假定对手贵或不好用。

### Q22｜数据读取不稳定或受限怎么办？

考察点：是否把数据依赖当作产品成立条件，能给替代路径。

记忆提纲：① 来源与权限 ② 错误分类 ③ 保存进度并透明降级 ④ 替代数据方式

主回答：我会把数据能力作为产品前提管理。先确认来源、使用权限和覆盖，再把失败分成超时、限流、余额或权限不足。短暂错误可以有限重试，权限问题不能靠不断重试解决。用户侧要保留已有候选和进度，说明缺了什么、如何继续；长期无法稳定取数，就评估合规数据源或用户导入名单。审核处理用户上传素材，可以独立工作，不让找人故障把整个产品都锁住。

追问1：最终无法稳定合规取数，产品还有价值吗？

追问提纲：承认主假设失败 → 重新验证替代场景

答：自动找人的核心价值会受影响，不能继续承诺原来的效果。可以验证用户导入后的筛选管理或独立审核，但这是范围调整，需要重新看用户是否愿意用；不能靠保留一个界面维持项目。

追问2：有小红书官方授权吗？

追问提纲：直接回答 → 区分技术与许可

答：目前没有已确认的官方授权。项目有真实数据读取和第三方接口路径，但技术能调用不等于获得平台商业许可。正式对外提供服务前，必须把来源和使用范围核实清楚。

### Q23｜模型成本和延迟高，怎么优化？

考察点：按瓶颈优化，并算到用户任务而不是只算 Token。

记忆提纲：① 拆任务耗时与费用 ② 先减无效工作 ③ 按难度分模型 ④ 质量回归后放量

主回答：先把一份任务拆成取数、检索、模型分析和后处理，找实际瓶颈。有时慢的是数据接口，不是模型。优化顺序上，先用代码过滤和去重，避免没必要的调用；再减少重复上下文，对可复用且不过期的数据做缓存；独立步骤考虑并行，难易任务分别路由。最终看每份合格名单或有效审核的总成本和 P95 等待时间。如果调用便宜了，却让人工返工增加，优化就没有成立。

追问1：先优化成本还是延迟？

追问提纲：看业务卡点 → 守住质量底线

答：若用户经常等不及退出，先处理等待；若完成率正常但每单成本超过可承受范围，就先降成本。两者都紧时先缩任务范围或渐进交付，而不是直接换最便宜的模型。

追问2：降级阈值怎么定？

追问提纲：用户容忍度 → 实测分布 → 明确结果状态

答：结合正常耗时分布和用户可接受的等待设时限，重试受总预算限制。超过后是返回部分结果、转异步还是人工处理，要按任务定。审核图片失败只能叫部分完成，不能降成纯文本却仍显示全量通过。

### Q24｜重做一次会改变什么？

考察点：复盘是否改变投入顺序，而不是只说多做调研。

记忆提纲：① 更早做真人任务 ② 缩到一个主任务 ③ 先立衡量口径 ④ 证据决定扩展

主回答：我会更早把真实用户测试放进里程碑，并先缩到找达人这一个主任务。之前同时推进找人和审核，功能增长比用户验证快。重做时，第一轮先确认用户原来怎么筛、名单什么标准算可用，再做最小路径，让用户用一次；在这之前就记录人工基线和采用标准。只有确实减少总工作量，再扩候选管理和审核深度。这样每一轮投入都有上一次反馈支撑。

追问1：当时为什么没这样做？

追问提纲：开发惯性 → 认识结果差距

答：开发背景让我比较容易从需求直接进入实现，也想把整套流程证明可行。后来发现“功能做完”和“用户愿意反复用”之间还有距离，所以需要调整验证顺序。

追问2：最想验证什么假设？

追问提纲：同质量更省事 → 愿意再用

答：在候选质量不下降的前提下，真实媒介自己复核和整理后是否仍然省时间，并愿意下一次继续用。如果只是系统输出快、人工要全部重看，核心价值就还没证明。

### Q25｜介绍一下简历助手

考察点：小项目也能说明明确场景和产品判断。

记忆提纲：① 岗位匹配的准备负担 ② 事实与 JD 对齐 ③ 简历到面试衔接 ④ 本地自用

主回答：简历助手解决的是投不同岗位时，简历表达和面试准备脱节的问题。输入已有经历和 JD 后，它帮助识别岗位重点，调整相关经历的表达，再生成可能被追问的内容。我的重点不是写得更夸张，而是让岗位要求、经历证据和面试说法对应起来：JD 要求某项能力，不代表用户就拥有它。这个项目是我从零设计开发、本地自用的小工具，主要用来验证这条准备流程。

追问1：为什么不一次 Prompt 生成？

追问提纲：事实核对与表达分离 → 定位错误

答：简单场景一次生成也可以，但事实缺失时容易把 JD 要求混进经历。分开做岗位分析、事实确认和表达，更容易发现哪里出了问题。是否分多次调用，要看质量提升是否值得额外等待，不是步骤越多越好。

追问2：怎么防止虚构？

追问提纲：事实表 → 缺项确认 → 输出核对

答：把公司、日期、职责、数据作为已确认事实单独保留；缺项就问，不让模型从 JD 补经历。输出后重点核对数字和贡献归属。表达可以润色，但每个成果都应该能在面试里用真实事情解释。

### Q65｜从 0 到 1 的 AI 产品，怎么从场景挖掘推进到上线迭代？

考察点：能否把业务价值、技术可行性、上线质量和持续迭代接起来。

记忆提纲：① 选场景、定基线 ② 验数据、做验证 ③ 收范围、定分工 ④ 灰度上线、看效果

主回答：我会先跟业务走一遍真实任务，找出最耗时、最容易出错的环节，再结合使用频率、收益、数据条件和错误代价选场景，同时记录现有方式的质量、耗时和成本。接着用一小批真实样本验证，比较规则方案和模型方案，确认 AI 的收益值得投入。确定方向后，把 MVP 收到一条完整任务上，明确输入输出、人工确认、异常处理和验收指标。模型选型由我和算法一起评估，训练与调参由算法负责；如果成熟模型已经够用，就不必自研。上线前固定评测集，检查端到端质量、延迟和成本，再小范围放量并准备回退方案。上线后看用户是否完成任务、是否采用结果和再次使用，再按问题出在数据、检索、模型还是交互来安排迭代。

追问1：模型指标达标，但用户觉得不好用怎么办？

追问提纲：核对评测代表性 → 观察完整任务 → 改正确环节

答：先看评测样本是否覆盖真实任务，再观察用户完成工作的全过程。可能答案正确但等得太久、需要反复复制、人工复核负担太大。把这些成本算进去，再决定改模型还是改流程，不能只拿离线分数说服用户。

追问2：你的媒介助手完整做过这些阶段吗？

追问提纲：讲已做阶段 → 限定用户验证和训练经历

答：我已经做过需求梳理、原型、开发测试和本人计时自测，模型主要通过现有能力接入。我还没有独立负责过自研模型训练到规模化运营的完整过程，上线后的长期用户效果要按实际记录说明。上面的回答是我接手项目时的推进思路。

备考备注：对应本次原题 3。与 Q12 的 MVP 优先级、Q37 的选型和 Q40 的评测配合练习。MVP 关注用最小投入验证关键假设，不要求所有业务模块都做齐；上线是一项发布动作，不能单凭上线就判断需求已经验证成功。

## 三｜企业项目：体现需求分析和交付判断（Q26—Q33）

### Q26｜讲一个参与最深、最复杂的项目

考察点：复杂在哪里，你做了什么判断，最后交付了什么。

记忆提纲：① 母子公司资金计划 ② 三模块状态联动 ③ 正常、失败、延期分开 ④ 我的职责与运行结果

主回答：我参与最深的是豪森药业资金管理项目，也去过现场。验收末期有一项需求：总公司要提前给多家子公司安排下季度每月的资金计划，子公司的外部应付账款会触发下拨和额度占用，超额要预警；当天没付出或付款失败，要上划资金并释放占用，延期账款当天不付。难点不是多做一个额度字段，而是人民币付款、资金计划、应收应付三个模块的状态必须对应。我承担需求澄清、流程与异常规则设计、开发联调，把正常、未支付、失败和延期分别讲清、落实到系统。这项功能已投入运行。它最能体现我的能力，是把复杂业务从口头要求变成各方都能执行和检查的流程。

追问1：最终谁做决策？

追问提纲：业务规则谁确认 → 方案由我澄清推进

答：涉及资金政策和客户业务口径，由客户及产品、项目负责人确认。我负责把可选方案、异常和影响讲清，推动确认并完成实现，不代替客户决定财务政策。

追问2：哪些是你独立负责的？

追问提纲：具体需求的完整责任 → 非整个项目

答：这项需求的澄清、流程和异常设计、开发联调由我承担，上线后期也单独承接需求开发。整个资金管理项目还有其他团队成员，我的贡献要落在这项需求上，不把其他模块都算给自己。

### Q27｜用业务语言解释资金计划需求

考察点：理解业务对象和约束，不陷入接口和数据库字段。

记忆提纲：① 计划是额度 ② 下拨是资金动作 ③ 付款决定后续处理 ④ 状态最终一致

主回答：可以把它理解为总公司给每家子公司安排每月可用的资金计划。有账要付时，系统安排资金下拨并记录占用，超出计划就提醒。钱如果当天没有付出去，或者付款失败，要按规则上划并释放对应占用。这里有三件事：计划额度、资金实际在哪里、账款是否付成，不能混成一个状态。否则可能钱回来了，额度还占着；也可能额度释放了，钱却没回来。这个需求就是要让三者按业务规则保持一致。

追问1：为什么付款失败要释放额度？

追问提纲：未完成支出 → 避免虚占 → 与上划对应

答：按照这项业务约定，未完成的付款不能一直占着计划，否则后续可用额度会被低估。但释放必须与对应的资金和业务状态核对，不能收到一个失败通知就无条件加回额度。

追问2：上划和释放占用是同一件事吗？

追问提纲：资金转移 ≠ 额度记账

答：不是。上划是钱回到母公司，释放占用是计划可用额度恢复。两者要关联，但应分别记录完成状态，这样出问题时才知道该查资金动作还是额度记录。

备考备注：超额规则是预警，不改成自动禁止付款；延期只确认当天不付，具体拨款与占用时点需要回查，不能自行推断。

### Q28｜面对模糊需求，怎么澄清？

考察点：能把歧义转成可决策、可验收的具体问题。

记忆提纲：① 谁在什么场景遇到什么问题 ② 真实业务走一遍 ③ 分叉和异常 ④ 规则与验收确认

主回答：我会先问目标，再拿一笔实际业务走完整流程。至少讲清谁发起、数据从哪来、什么时候触发、哪些条件影响结果，以及失败后谁处理。豪森这项需求里，重点就是把应付账款、下拨、付款和额度占用分开，再确认未支付、失败、延期的不同处理。最后把歧义整理成具体场景和预期结果，跟产品、客户确认，也让测试据此准备。这样确认的是同一件事，不是大家都说“理解了”。

追问1：举一个避免返工的例子？

追问提纲：延期是明确例外 → 提前进入设计和测试

答：延期账款就是一个必须提前说明的例外。如果只按“有应付就付款”理解，功能做完也不符合客户要求。我在这项需求里参与了延期等异常规则的澄清和设计，让它不是等上线才补的特殊情况。

追问2：客户和产品意见不一致怎么办？

追问提纲：同场景比较 → 分清决策权 → 留结论

答：用同一笔业务演示不同方案会造成什么结果，再区分是业务政策分歧，还是操作习惯分歧。政策由有权的人确认，技术影响由研发说明；确认后留下结论和验收标准，避免开发各自选一种理解。

### Q29｜异常规则和状态机怎么设计？

考察点：从正常流程走向可恢复、可审计的系统。

记忆提纲：① 分清业务对象 ② 事件触发状态转换 ③ 转换条件与动作 ④ 幂等、补偿、人工兜底

主回答：先分清对象，再给每个对象列状态，而不是画一张什么都塞进去的大流程图。比如应付账款、付款任务、资金上划和额度占用可以关联，但状态各有含义。每次转换要写清触发事件、前置条件、执行动作和失败出口。重复通知、超时、乱序也要考虑：业务动作不能重复记账，处理中不能直接显示成功，自动恢复不了的要有人工处理入口。这样异常发生后，系统知道卡在哪、下一步由谁处理。

追问1：重复消息怎么处理？

追问提纲：业务幂等键 → 原子约束 → 回放不重复生效

答：我的设计会用业务单号、操作类型和必要版本标识同一个动作，由服务端用唯一约束或原子状态更新保证只生效一次。单纯“先查再写”在并发下仍可能重复，还要保留处理记录，方便重试和核对。

追问2：补偿失败怎么办？

追问提纲：异常可见 → 有限重试 → 人工恢复

答：保留失败原因、已完成动作和待恢复状态，区分可重试与必须人工处理的情况。有限重试仍失败就告警，提供对账线索和人工处理流程。补偿本身也要防重复，不能为了结束任务把它改成成功。

备考备注：本题是设计方法；豪森已确认做过流程与异常设计，但具体幂等键、事务和补偿实现未经本轮核验，不直接归为当时成果。

### Q30｜怎么推动跨团队协作？

考察点：不是联系人多，而是能否减少信息差、明确责任并解决阻塞。

记忆提纲：① 共同目标与验收 ② 依赖和负责人 ③ 阻塞及时升级 ④ 结论同步

主回答：我会让协作围绕同一个交付结果展开。需求阶段先确认业务口径和边界；开发阶段明确接口、依赖和责任人；联调时用同一批场景检查；上线再和实施确认操作及异常处理。保融工作里，我实际对接过产品、测试、实施和客户，也在驻场时直接沟通。我的习惯是把“还差什么、谁确认、影响哪一步”说具体，不能只是群里发一句“麻烦看一下”，然后被动等回复。

追问1：讲一次冲突？

追问提纲：不编事件 → 用真实协调说明处理方式

答：我没有一个细节记得很完整、适合展开的激烈冲突案例。更有代表性的是豪森这类需求澄清：付款、上划和额度涉及不同模块，我负责把正常与例外情形摆出来，与产品和客户确认，减少不同理解进入开发。如果讨论资源冲突，我会把影响和优先级交给有权的负责人取舍。

追问2：没有汇报关系怎么推动别人？

追问提纲：共同影响 → 最小明确请求 → 负责人取舍

答：先说明对方这一步影响什么交付，提出具体、可完成的请求和时间。如果确实有更高优先级的工作，就协调负责人调整计划，而不是靠不停催促。协作不等于让所有人优先做我的事。

### Q31｜多个需求都很急，怎么排优先级？

考察点：能否给出排序原则和机会成本。

记忆提纲：① 风险与主流程 ② 截止期和影响范围 ③ 依赖与投入 ④ 明确被延期的工作

主回答：我先分事故、交付阻塞和一般新增需求。资金或数据正确性问题优先看风险；再看是否卡住客户主流程、有没有不可移动的时间窗口、影响多少任务；最后比较投入、依赖和临时方案。比如付款主流程故障，通常比报表样式优化更急。但优先级不能只靠谁说得急，必须把插入一项会挤掉什么讲清楚，涉及跨项目资源时由负责人确认新的承诺。

追问1：销售要求插单呢？

追问提纲：核实承诺 → 列影响 → 重新排期

答：确认是否已经对客户承诺、真实截止时间和不做的损失，再让研发估最小范围。值得插单就同步哪些工作延期、谁通知相关方；不默认通过加班把所有承诺都保住。

追问2：如何拒绝需求？

追问提纲：认可问题 → 解释取舍 → 给替代或重评条件

答：我会说明当前不排的原因，以及用户可以怎样暂时完成工作，并约定什么条件变化后重新评估。拒绝的是本期投入，不是否认问题，也不只是说“研发没时间”。

### Q32｜临近上线客户改需求，怎么办？

考察点：范围控制和风险沟通，而不是一味答应或一味拒绝。

记忆提纲：① 判断变更性质 ② 评估连带影响 ③ 最小必要调整 ④ 重定验收和计划

主回答：先判断这是缺陷、原需求没澄清，还是新增范围。缺陷和漏掉的核心规则不能简单按新增需求拒绝；真正新增则要评估对数据、接口、测试和上线窗口的影响。然后给可选方案：本期做最小必要部分、分期上线，或者顺延。确认后同步产品、研发、测试和实施，并更新验收。关键不是客户改不改，而是改动的成本和风险不能隐形。

追问1：客户坚持全部按时完成？

追问提纲：具体估算 → 提供选项 → 升级取舍

答：把需要的工作和关键依赖列出来，说明按原日期能交付什么，扩大范围需要什么条件。仍有冲突就请项目负责人共同沟通，不能先承诺一个做不到的计划，再把风险留到上线前。

追问2：你能自己承诺上线时间吗？

追问提纲：个人估算 → 联合确认 → 对外承诺

答：能估自己负责的工作，但完整上线还依赖联调、测试、实施和客户窗口。我会拿这些依赖一起确认，再由对应负责人对外承诺，而不是只按写完代码的时间算上线时间。

### Q33｜没有量化数据怎么证明价值？

考察点：用可核实的交付证据表达价值，不把没有数字等同没有成果。

记忆提纲：① 原业务要求 ② 落地机制 ③ 投入运行 ④ 下次补效果衡量

主回答：我会把业务变化说具体。豪森这项需求把资金计划、应付触发、付款结果和异常处理落实到系统，功能已经投入运行。我承担了从澄清到联调的工作，能解释每种情况为什么这样处理，这是业务理解和交付的证据。没有记录的节省人力，我不报数字。如果重新做，我会在交付前定义异常处理耗时、人工干预次数和额度差异，后续就能判断不只是上线了，而是哪里改善了。

追问1：为什么当时没埋点？

追问提纲：职责与关注点 → 承认缺口 → 改进方法

答：当时职责以开发交付为主，重点在规则正确和验收，没有建立完整的业务效果基线。现在转产品，我会把衡量方式提前放进需求，而不是等上线后再想能提什么数字。

追问2：可以提供什么证据？

追问提纲：脱敏流程 → 职责范围 → 不泄露客户资料

答：可以讲脱敏后的业务流程、关键异常和我负责的部分，解释测试怎样覆盖。涉及任职可以提供相应证明；客户账户、合同和内部文档不会带出来，不能为了证明项目泄露资料。

## 四｜AI 基础：回答选型、边界与验证（Q34—Q43）

### Q34｜RAG、Workflow、Agent 分别是什么？

考察点：能把概念放回架构，不将三者当成互斥技术。

记忆提纲：① RAG 补知识 ② Workflow 定流程 ③ Agent 选行动 ④ 三者可以组合

主回答：它们解决的不是同一个层面的问题。RAG 解决模型回答时依据什么外部资料；Workflow 解决一项任务按什么预设步骤完成；Agent 更强调根据目标和执行反馈决定下一步行动。比如内容审核可以是固定 Workflow，其中先取相关规则供模型判断；开放式调查则可能让 Agent 动态决定继续查什么。先看缺的是知识、稳定流程还是动态决策，再决定组合，不能看到 AI 项目就把三个词都堆进去。〔来源1、3〕

追问1：RAG 为什么不等于知识库问答？

追问提纲：技术机制 → 多种业务输出

答：问答只是表现形式。审核可以检索规则后识别风险，报告生成可以检索资料后形成结论。共同点是外部知识参与生成或判断，而不是必须有聊天窗口。

追问2：举一个适合 Agent 的任务？

追问提纲：路径未知 → 反馈决定补查

答：围绕一个开放问题做资料研究。看完第一批结果，可能发现还缺价格或用户证据，需要选择补查方向。相反，按固定清单提字段，通常不需要这么大的自主空间。

### Q35｜如何设计并评估 RAG？

考察点：能分开检索问题和生成问题，知道怎样验证改动。

记忆提纲：① 知识治理 ② 相关召回与重排 ③ 有据生成 ④ 分层评测

主回答：我会先定义要回答的业务问题和可用知识范围，处理文档时保留结构、来源、版本和权限。检索阶段根据问题找相关片段，需要时组合关键词与向量，再用重排减少噪声；生成阶段要求结论能对应资料，缺证据就说明缺口。评测也分开：相关内容有没有召回、排得够不够靠前，模型有没有忠实使用，以及最终用户能不能完成任务。如果资料没进上下文，继续改回答 Prompt 通常不是优先项。〔来源3〕

追问1：Chunk 大小怎么定？

追问提纲：业务语义完整 → 噪声与成本 → 用样本比较

答：先按内容结构切，不直接套一个字数。规则条款尽量保留适用条件和例外，必要时保留父级上下文。切太小会丢含义，太大会混入无关信息，用真实问题比较召回与答案质量后再定。

追问2：什么时候混合检索？

追问提纲：精确术语 + 同义表达 → 融合后验证

答：既有条款号、品牌名等精确匹配，又有用户不同说法时值得测试。关键词和向量各有优势，但分数不能直接随意相加，需要融合或重排，再看对漏检、延迟和成本的实际改善。

### Q36｜怎么控制幻觉？

考察点：不是背“加 RAG”，而是定位错误并控制对用户的影响。

记忆提纲：① 找错误来源 ② 给相关证据 ③ 校验重要结论 ④ 不确定时交接

主回答：我会先分清错误来自哪里：资料没有或过期、检索没找到，还是模型看到了却推断过头。对应地做知识治理、检索优化和生成约束。重要字段用代码校验，事实结论要能回到原文；高风险结果让人复核，依据不足不强行下结论。像审核里，给出一个真实法条并不代表判断正确，还要看是否适用于这段内容。最后用错误样本检查风险是否减少，不能把加了 RAG 当成解决幻觉的证明。

追问1：有引用但不支持结论怎么办？

追问提纲：判为错误 → 取消确定结论 → 定位责任层

答：这是事实依据不成立，不算通过。先把相关结论转成待核实，再判断是资料选错还是模型曲解，分别修改检索或生成约束。引用数量增加，不能抵消引用质量差。

追问2：拒答率太高怎么办？

追问提纲：可答覆盖 → 部分回答 → 风险分级

答：检查问题是否本来可答、知识是否齐全、拒答规则是否过宽。可以先回答有依据的部分，再说明缺什么。低风险建议和高风险判断用不同策略，但不能为降低拒答率放开无依据结论。

### Q37｜怎么选模型？

考察点：任务评测、成本判断与上线风险，而不是熟悉多少品牌。

记忆提纲：① 必要能力与约束 ② 同任务盲测 ③ 质量过线后比成本 ④ 小范围验证

主回答：先列必须满足的条件，比如中文图文理解、结构化输出、工具调用、数据使用要求和延迟预算。再用自己的典型任务、难例和失败案例做同条件比较，尽量让评审不知道来自哪个模型。质量达到要求后，比较总任务费用和稳定性；简单任务可以走更经济的模型，难例再升级。不能只看榜单或几次回答很顺就决定，更不能为了省钱，把成本转成更多人工返工。

追问1：贵模型只提升 2% 怎么办？

追问提纲：先定指标口径 → 看错误价值 → 算增量收益

答：先问是相对提升还是百分点、在哪些样本上提升。如果主要减少严重漏报，价值可能很高；若只是措辞更好，未必值得。再看增加的费用和等待，必要时只将高风险或难例路由给它。

追问2：模型升级怎么处理？

追问提纲：版本固定 → 回归与灰度 → 可回退

答：先跑固定测试集和历史失败案例，检查质量、格式、工具调用与耗时，再小范围试用。保留旧版本和配置，出现回归能回退。模型更新不应绕过产品验收。

### Q38｜怎么设计和管理 Prompt？

考察点：把业务标准变成可维护、可测试的指令。

记忆提纲：① 明确任务和边界 ② 定义输出契约 ③ 用正反例讲标准 ④ 版本化回归

主回答：我会先把业务判断标准写清楚，再转成 Prompt。包括输入是什么、需要做哪些判断、不能做什么、输出哪些字段，以及资料不足怎么处理。模糊标准用正反例说明，比如“达人提供某项服务”和“达人本人有相关经历”不能混为一谈。固定规则、当前资料和用户输入分开组织；输出再用 Schema 和业务规则校验。每次改动记录版本，用同一组样本比较，不把写得长、写得专业当效果更好。

追问1：Few-shot 过拟合怎么办？

追问提纲：代表性示例 → 独立测试 → 看未见表达

答：示例覆盖不同表达和边界，但留出不参与调试的测试集。不能把每个失败答案都塞回 Prompt 再测原题；要看同一规则下的新表达是否也改善，必要时减少过于具体的示例。

追问2：Prompt 泄露怎么办？

追问提纲：不放秘密 → 权限在系统 → 限制外泄影响

答：Prompt 不应该存密钥，业务权限也不能靠模型保密来保障。即便提示词被看到，工具调用仍要经过服务端鉴权和参数校验。内部策略需要访问控制，但提示词保密不是核心安全边界。

### Q39｜什么时候 RAG，什么时候微调？

考察点：按问题类型选手段，理解成本和资料更新方式。

记忆提纲：① 缺知识用检索 ② 行为不稳评估微调 ③ 先做简单基线 ④ 数据与成本决定投入

主回答：如果问题是业务知识经常更新、回答需要出处，我先考虑 RAG；如果知识给够了，模型仍不能稳定按特定格式或风格完成任务，再评估 Prompt、示例是否够用，是否值得微调。微调要有质量足够的训练数据和独立评测，也增加训练与维护成本，不是每个垂直场景都值得做。两者可以结合：检索提供新知识，微调改善任务行为。对媒介助手，优先把知识和判断标准组织好，比一开始训练模型更合理。

追问1：微调后知识过期怎么办？

追问提纲：实时事实外置 → 版本评测

答：需要更新和可追溯的事实仍从资料或工具读取，不能完全依赖参数记忆。如果业务行为也发生变化，再更新训练数据并回归。微调过不代表事实永远正确。

追问2：什么时候直接用长上下文？

追问提纲：资料少且范围明确 → 比质量与成本

答：资料量不大、权限清楚、一次任务范围明确，可以先把完整材料给模型，做一个简单基线。知识规模、噪声或成本上来后，再评估专门检索。能放得下不等于一定看得准，也需要测关键内容覆盖。

### Q40｜怎么建立 AI 产品评测体系？

考察点：评测如何服务迭代和发布决策。

记忆提纲：① 定义任务成功 ② 分层建数据集 ③ 匹配评分方式 ④ 回归门槛与错误分析

主回答：先定义用户任务成功是什么，以及哪些错误不可接受。再从真实场景抽取正常、困难、边界和失败样本，保留独立测试集，并记录版本。确定答案用规则评分，主观质量由有业务经验的人制定标准，再考虑用校准过的模型辅助判分。报告不能只有一个总分，还要按错误类型、风险和任务阶段拆开。最后把评测变成发布门槛：这次修好了什么、有没有新增严重错误、等待和成本是否可接受。评测的用途是帮助决定能不能上线、下一步改哪里。

追问1：没有标准答案怎么办？

追问提纲：评分准则 → 锚点样例 → 独立评审

答：开放任务不一定有唯一文案，但可以有明确标准，比如必须覆盖哪些信息、哪些事实不能错、哪些风险必须识别。用好坏样例校准评审，再做分项打分或成对比较，不强求逐字一致。

追问2：离线变好，业务没变好呢？

追问提纲：指标代理失效 → 任务分布或流程问题

答：先检查测试样本是否代表真实任务，以及优化的指标是否影响用户价值。也可能结果更准了，但等待更长、操作更复杂。要回到任务漏斗和用户行为，不能继续盯着离线分数加模型能力。

### Q41｜Agent 有哪些核心部分和常见失败？

考察点：对执行系统的理解，不只是“模型加工具”。

记忆提纲：① 目标与状态 ② 决策与工具 ③ 观察与结果校验 ④ 权限预算和退出

主回答：我会把 Agent 看成一个受控执行系统。它需要明确目标和当前状态，能决定下一步、调用工具，拿到真实反馈后判断是否继续，并有权限、预算和退出机制。常见失败包括目标理解错、工具选错、参数错、重复执行，或者工具失败却继续编结果。产品要决定哪些步骤可以自主，哪些动作必须确认，还要让用户看得到进度和失败原因。只把工具接上，离可靠完成任务还有一段距离。

追问1：什么时候需要长期记忆？

追问提纲：跨任务稳定偏好 → 用户可控 → 不替代业务库

答：当用户确认过的偏好会影响后续任务时才考虑，例如长期关注的内容类型。已采用达人、任务进度这种准确业务事实应保存在数据库里。记忆要可查看、修改和删除，不能把一次随口表达永久当规则。

追问2：怎么避免无限循环？

追问提纲：硬上限 → 无进展检测 → 可恢复终止

答：步数、总时长和费用都设独立上限，系统层执行；连续拿不到新增信息或重复相同动作也要停。停止时返回已有结果和原因，保存可恢复状态，而不是只让模型自己判断“差不多该结束了”。

### Q42｜上下文和记忆怎么设计？

考察点：控制信息相关性、一致性、权限和成本。

记忆提纲：① 当前任务最小必要信息 ② 确认条件结构化 ③ 历史按需检索 ④ 记忆可更新可纠正

主回答：我会先区分当前任务状态、外部知识和长期偏好，不把所有历史聊天直接堆进上下文。当前目标、已确认条件和关键证据优先保留；旧记录按需要读取，非关键内容可以摘要。金额、排除对象、任务已完成动作这类不能失真的信息，用结构化数据保存。长期偏好需要用户确认，还要有失效和纠正机制。上下文管理的目标是让模型拿到当前需要的信息，而不是给得越多越好。

追问1：摘要丢细节怎么办？

追问提纲：关键字段不压缩 → 保留来源 → 必要时回查

答：摘要只压缩叙述，不能取代重要原值。比如粉丝上限、用户明确排除的对象单独保留，摘要带原记录引用。判断依赖某个细节时重新读取，避免在不完整概括上继续推断。

追问2：用户前后矛盾怎么办？

追问提纲：识别冲突 → 明确确认 → 更新版本

答：区分明确改需求和表达含糊。明确修改时让新确认条件替代旧条件；影响结果较大的变化要再确认，并标记版本。不能把互相冲突的要求静默混在一起执行。

### Q43｜AI 产品核心指标怎么设计？

考察点：指标服务目标，并能追到原因和代价。

记忆提纲：① 一个主目标 ② 质量护栏 ③ 过程诊断 ④ 分母与统计窗口

主回答：先明确阶段目标。媒介助手早期主要看同质量名单是否更省事，所以总任务耗时和用户确认可用是关键；进入持续使用后再看复用和有效任务量。候选相关性、重复率、审核漏报误报是质量护栏，接口成功率、模型延迟和费用是诊断指标。每个指标都要明确分母、去重口径和时间范围，比如“采用率”是候选级还是任务级。这样数字变化时才能解释业务，而不是做出一张很好看的看板。

追问1：指标冲突怎么办？

追问提纲：先设不可突破的底线 → 再优化主目标

答：例如审核要省时，但不能以严重漏报增加为代价；名单要足量，但不能放弃核心条件。先设质量和风险底线，再在可接受范围里优化耗时和成本，而不是把所有指标随意平均成一个分数。

追问2：第一版阈值怎么定？

追问提纲：人工基线 → 错误成本 → 试运行修订

答：先测现有人工表现，再让业务判断哪些错误绝不能接受、哪些可以复核纠正，形成初始门槛。用试运行看分布后调整，不凭空写一个 95%。高风险错误还要单独统计，不能被大量简单成功稀释。

## 五｜场景题：给出决策，不只列分析框架（含 Q67 业务分歧）

### Q44｜设计一个智能客服产品

考察点：能在模糊场景里定义范围、优先级和验证办法。

记忆提纲：① 限定售后场景 ② 查询先行、操作受控 ③ 知识与业务接口分工 ④ 转人工和解决率

主回答：我先以电商售后为例，目标是减少重复咨询和等待，但不牺牲问题解决质量。先看历史咨询，把高频、规则明确的问题做第一版，比如退换货规则、物流和订单状态。规则从知识库取，订单事实查业务接口；真正退款需要身份、权限和业务条件校验，不能只凭模型对话执行。用户不满、事实冲突或系统无法处理时，带着摘要和操作记录转人工。先灰度看有效解决率、重复咨询率、满意度和单次服务成本，再决定扩大场景。

追问1：自助解决率怎么定义？

追问提纲：明确解决证据 → 观察重复联系 → 固定分母

答：分母是约定范围内进入 AI 服务的问题任务；分子要求有用户确认或业务状态证明解决，并在约定窗口内没有同问题重复联系。没转人工、用户退出都不能直接算解决，具体窗口按售后周期确定。

追问2：知识怎么保持更新？

追问提纲：责任人 → 生效失效 → 发布测试

答：每类知识有业务负责人和生效范围，政策发布同步更新，旧版失效但留历史。更新前用典型问法回归，重点测新旧政策交界，不让模型同时拿到两版互相冲突的规则。

### Q45｜AI 功能使用率低，怎么分析？

考察点：定位流失阶段，再选措施，而不是上来加入口。

记忆提纲：① 分清没看到还是没再用 ② 看有效任务漏斗 ③ 分群与访谈 ④ 针对原因验证

主回答：先把使用率拆开：目标用户有没有看到入口、有没有开始、任务有没有完成、之后有没有再用。没看到是触达问题；开始后放弃，可能是输入门槛、等待或结果不可信；做完仍不回来，要看任务频率和实际价值。再按新老用户、任务类型和结果质量分组，结合录屏或访谈找原因。比如名单生成成功但全要人工重筛，改入口没用，应该先修匹配质量。每次只针对主要原因验证一个改动。

追问1：优先看哪三个事件？

追问提纲：曝光 → 有效提交 → 用户确认完成

答：目标用户的入口曝光、有效任务提交、用户确认完成，并且要能关联同一用户和任务。后续结合时间看复用，不能把点击开始当任务完成，也不能让技术重试多计一次使用。

追问2：怎么判断伪需求？

追问提纲：排除体验问题 → 看真实行为 → 分清低频价值

答：用户知道怎么用，结果也达到约定质量，却仍不愿把真实任务交给它，现有办法又足够好，就要怀疑需求强度。不能只看 DAU，低频但省很多工作也可能有价值；关键是任务发生时用户会不会选择它。

### Q46｜AI 功能怎么排优先级？

考察点：业务收益与 AI 可行性共同决定投入。

记忆提纲：① 痛点强度和覆盖 ② AI 增量收益 ③ 数据与实现可行性 ④ 风险和验证成本

主回答：我会先看问题有多重要、多频繁，现有办法哪里不够，再判断 AI 能提供多少增量，而不是先看哪个功能最像 AI。还要检查数据是否具备、错误代价、投入和维护成本。高价值但不确定的场景先做小验证；规则就能稳定解决的，不必上 Agent。比如达人数据是否可得，是先于复杂推荐界面的验证项。优先级的结论应包括先做什么、暂不做什么，以及什么证据会改变这个排序。

追问1：老板坚持低价值 AI 功能怎么办？

追问提纲：理解真实目标 → 限定试验 → 约定退出

答：先问老板想验证销售机会、用户需求还是技术方向。如果确实值得低成本试验，就限定用户、投入和时间，提前约定继续或停止的标准；不能只因为我暂时看不到价值就否定，也不能无限投入。

追问2：能不能用 RICE 打分？

追问提纲：统一讨论语言 → 估计不是事实

答：可以按覆盖、影响、信心和投入辅助比较，但早期很多分值是估计。我会写明依据，把高影响、低信心的部分优先验证。分数帮助讨论，不代替对依赖、风险和战略目标的判断。

### Q47｜怎么给 AI 功能做 A/B 测试？

考察点：明确假设、随机化、指标和实验有效性。

记忆提纲：① 一个可证伪假设 ② 稳定分组 ③ 主指标与质量护栏 ④ 样本和决策预设

主回答：假设我们想验证“执行前确认结构化条件能减少返工”，就把用户稳定随机分到有确认页和原流程两组，其他条件尽量一致。主指标看首次满足要求的任务完成率，护栏看放弃率、总耗时和错误条件占比。实验前确定适用人群、最小有意义变化、样本和持续周期，避免看到某天好就提前宣布成功。结束后既看差异是否可靠，也看提升是否值得新增一步操作。AI 输出有波动，但随机分组和足够样本可以比较总体效果。

追问1：样本不足怎么办？

追问提纲：不强做显著性 → 配对任务与定性验证

答：先做同类任务配对测试和任务观察，交叉安排使用顺序，减少熟练度影响。小样本用于发现大问题和估计变化范围，不包装成统计显著。等使用量足够再做正式随机实验。

追问2：模型随机性怎么控制？

追问提纲：冻结非实验变量 → 重复观察 → 保留版本

答：如果测交互，就尽量固定模型版本、Prompt、参数和知识条件；如果测模型，就把模型作为唯一主要变化。记录版本并覆盖足够任务，必要时对离线样本重复跑。低温度不等于每次完全一致。

### Q48｜用户说要 AI，但规则就能解决怎么办？

考察点：不把用户指定的技术误当作真实需求。

记忆提纲：① 问想改善什么 ② 建立简单基线 ③ 仅在必要处用 AI ④ 用任务效果沟通

主回答：我会先问他想少做哪一步、现在为什么做不好。若是固定条件过滤和重复操作，规则更稳定；若只是输入表达复杂，可以用模型理解需求，后续由代码执行。比如“粉丝在某区间”不需要模型推理，“内容像真实分享”才需要更强的语义判断。我的责任是选最合适的方案，而不是满足一个 AI 标签。只要同样的任务更省事、更可靠，简单方案也能成立。

追问1：怎么和老板解释？

追问提纲：同任务演示 → 效果成本对照

答：用同一个任务比较规则、模型和混合方案，展示准确性、等待、费用和维护差异。讨论围绕用户结果，不围绕哪种技术更先进；若 AI 只在入口有价值，就只用在入口。

追问2：混合方案怎么设计？

追问提纲：模型提理解 → 代码验约束 → 人确认高风险

答：模型先把自然语言转成结构化条件，代码校验区间和必填项，再执行检索、去重。模型补充内容匹配理由，人工做最后采用。每一步都有明确输入输出，错误也容易定位。

### Q49｜数据隐私和安全怎么处理？

考察点：从数据流识别风险，不用“加密了”概括全部安全。

记忆提纲：① 最少必要数据 ② 权限与用户隔离 ③ 外部模型及工具边界 ④ 留存、日志和删除

主回答：我会先画清楚数据从用户到服务端、模型和第三方接口的流向，判断每一步是否真的需要这些数据。业务数据按用户隔离，密钥只由服务端受控使用，访问和写入都校验权限。送给模型的私有资料要明确使用范围，日志尽量留任务号和脱敏信息；保留多久、怎么删除、异常谁处理也要有规则。加密只是其中一层，还需要验证跨用户访问、工具越权和恶意输入等场景。

追问1：调试日志与隐私怎么平衡？

追问提纲：可排错的最小记录 → 限权与期限

答：优先记录版本、任务状态、错误码和脱敏摘要。确实需要原始素材排错时，限制查看权限和保留时间，不把密钥或完整私有资料长期写进日志。调试方便不能成为无限收集的理由。

追问2：怎么防 Prompt Injection？

追问提纲：材料不当指令 → 最小工具权限 → 独立校验

答：网页、图片里的文字和知识库内容都是待分析材料，不能改变系统权限。工具只开放必要能力，服务端校验参数、用户和操作范围；高风险动作需要确认，并用恶意样本测试。单靠提示模型“不要被骗”不够。

### Q50｜与研发或算法有分歧怎么办？

考察点：把立场争论转成共同的决策问题。

记忆提纲：① 明确争议变量 ② 对齐验收标准 ③ 用样本和估算比较 ④ 负责人决策并复盘

主回答：先把分歧具体化。业务说效果差，是召回不够、错误太多，还是等待太久？研发说成本高，是模型费用、数据依赖还是维护投入？双方先认可同一组样本和验收标准，再比较方案效果、投入和风险。能通过小实验解决的，不靠职位争论；涉及范围与资源取舍，由对应负责人决策。我有开发背景，可以帮助解释实现代价，但也要坚持把用户必须达到的结果讲清楚。

追问1：技术说做不了，业务必须上线？

追问提纲：区分做不了与不能按期 → 缩范围或人工辅助

答：先问是基础能力不具备，还是当前时间和资源不够。后者可以缩范围或分期，前者需要替代路径或人工辅助。如果关键质量无法保证，就明确风险、升级决策，不用“先上线再说”掩盖问题。

追问2：你有开发背景，会不会越过研发设计？

追问提纲：产品定目标约束 → 研发定实现 → 共同验证

答：我会给思路，但不把自己的实现当唯一答案。产品负责用户问题、优先级和验收，研发负责实现和稳定性判断；技术理解应该让比较方案更高效，而不是让我替团队单方面下结论。

### Q67｜业务方认为 AI 方案与直觉不符，你怎么验证和沟通？

考察点：能否把意见分歧转成有共同标准的验证。

记忆提纲：① 找具体分歧 ② 对齐标准和损失 ③ 同样本比较 ④ 小范围验证

主回答：我会先让业务方拿一个具体例子，说明哪里不合理，是结果不符合经验，还是流程增加了工作量。然后一起确定判断标准，尤其是错选和漏选分别会带来什么损失。比如系统推荐的达人，业务觉得不适合，我会拆开看是硬条件、内容风格还是商业合作经验没有体现。接着用包含普通案例和争议案例的同一批样本，按事先约定的标准比较人工与 AI，条件允许时先隐藏结果来源，减少先入为主。如果业务经验有效，就把它补成规则、特征或评测案例；如果 AI 有优势，也先小范围试用验证。最后沟通哪些结论已经有证据、哪些还不确定，以及下一步用什么结果决定是否扩大。

追问1：业务坚持不同意，也不愿意做测试怎么办？

追问提纲：明确顾虑 → 降低验证成本 → 对齐决策责任

答：先确认是风险、时间还是对目标不认同。可以提出只在历史数据上做离线比较，或旁路观察、不影响业务。如果仍无法推进，就把收益假设、风险和验证成本交给共同负责人决定，不直接强推上线。

追问2：AI 整体更准，是否就应该采用？

追问提纲：关键场景 → 错误代价 → 总成本

答：还要看重要场景有没有退步、错误代价能否接受，以及人工复核和等待是否抵消收益。比如整体准确率提高，但高风险内容漏报变多，就不能仅凭平均分上线。必要时只在可靠的场景使用。

备考备注：对应本次原题 5。与 Q50 区别：本题主要面对业务经验和使用流程的分歧，Q50 主要面对研发或算法方案分歧。

## 六｜实现深挖：把技术说到产品价值上（Q51—Q56）

### Q51｜你说的 Skill 具体是什么，和 Tool 有什么区别？

考察点：能解释复用单元、调用边界和维护价值。

记忆提纲：① Tool 提供操作 ② Skill 组织任务方法 ③ 输入输出和失败边界 ④ 复用与独立评测

主回答：Tool 更像一项具体操作，比如查询达人接口、读取资料或保存结果；Skill 是完成一类任务的方法和能力封装，可以包含指令、规则、示例和工具使用方式。在媒介助手里，我按需求解析、图片理解、风险识别和证据关联等职责拆分，明确输入输出和失败处理。这样修改审核标准时，不必把整条流程重写，也容易单独评测哪一段出了问题。这里指自建业务 Skill，不代表它天然符合某个外部文件规范。〔来源2〕

追问1：拆这么多 Skill，是不是每一步都调模型，成本很高？

追问提纲：逻辑拆分不等于调用拆分 → 比总成本

答：不是。确定性任务不必调用模型，相关判断也可以合并在一次调用里。Skill 拆分是为了职责清楚和复用，调用如何合并要看质量与延迟，不能一拆模块就增加一次模型费用。

追问2：MCP 和 Skill 又有什么关系，你实际用了 MCP 吗？

追问提纲：连接协议与任务方法分层 → 开发工具不等于运行架构

答：MCP 解决应用怎样连接外部工具和资源，Skill 更偏怎样完成某类任务，两者能组合。我的开发环境里使用工具的方式，与媒介助手运行时架构是两件事；不能因为开发时用过 MCP，就说产品全部通过 MCP 执行。

### Q52｜你的 Agent Loop 真正体现 ReAct 的地方在哪里？

考察点：理解反馈如何改变行动，并准确说明自主程度。

记忆提纲：① 明确目标 ② 行动获得观察 ③ 按结果调整 ④ 停止与权限保护

主回答：ReAct 的关键不是把“思考”三个字打印出来，而是推理和行动交替，利用真实反馈调整下一步。找达人时，第一轮可能数量少、重复多或某类条件淘汰很多，系统据此判断继续查、扩关键词还是结束；不能预先假定搜一次就完成。我的项目借鉴了这个反馈循环，但当前不少动作由代码策略选择，模型主要负责意图与内容理解。产品上这样做，是让可控约束先稳定下来，再评估哪里值得增加模型决策。〔来源4〕

追问1：不足 20 人，能不能偷偷放宽条件补足？

追问提纲：硬约束不能偷改 → 放宽可见且可确认

答：不能。用户明确的必要条件代表任务目标，不能为了数量好看改掉。可以提示哪个条件导致候选少，让用户决定是否调整；如果已有策略允许放宽次要条件，也要显示放宽项及依据，不能让用户误以为全都满足。

追问2：怎么防止循环失控或费用过高？

追问提纲：系统硬预算 → 无增益停止 → 部分结果可交付

答：将请求数、费用、轮次和总时长放在系统层控制，达到目标、无新增或供应商错误时停止。限制不能只是 Prompt 的一句要求。上线前还要检查实际配置和异常测试，避免代码有上限逻辑、配置却把它关掉。

### Q53｜多模态具体解决了什么，为什么不只做 OCR？

考察点：从信息缺口说明视觉能力的必要性。

记忆提纲：① 风险分布在图和文 ② OCR 识字、视觉理解画面 ③ 图文结合判断 ④ 低置信与缺图处理

主回答：图文审核不能只看正文，因为关键信息可能在图片里的文字，也可能在画面与文案组合产生的含义中。OCR 主要解决识字，视觉模型能辅助理解画面、对象和图文关系。我的设计是先提取可观察信息，再结合规则判断风险，而不是直接让模型看图给“合规或不合规”。比如正文和图片表达条件不一致，要把具体位置展示给人核查。多模态的价值是减少信息遗漏，但图片看不清或未读到时，也必须明确说明。

追问1：图片没读到，但正文审核成功了，能不能显示通过？

追问提纲：覆盖不完整 → 部分完成 → 补审

答：不能显示整篇通过。应明确“正文已分析，图片未完成”，保留已检查的结果，提供重试、换图或人工处理。模型降级是工程动作，用户必须知道审核覆盖范围发生了变化。

追问2：图片和文案矛盾，听谁的？

追问提纲：不擅自裁定事实 → 指出冲突 → 人工核对

答：不能默认文字或图片一定正确。先列出两边的具体内容和冲突，让用户核对原材料；如果图片模糊，还要区分是真冲突还是识别不确定。系统帮助发现问题，不凭空替用户补一个一致的事实。

### Q54｜你的 RAG 到底做到了哪一步？

考察点：既能准确说明当前实现，也能提出有依据的下一步。

记忆提纲：① 入库与知识范围 ② 知识增强审核和引用 ③ 召回能力尚需完善 ④ 用漏检样本驱动升级

主回答：目前主要完成了知识入库、用户和知识库范围筛选、规则关联，以及把知识片段提供给审核并保留引用。它首先解决的是审核有依据、能追溯。当前取资料的方式还比较直接，部分片段按范围加载后进入上下文，不是成熟的向量召回加重排链路。下一步我会先收集“应该找到却没找到”的规则样本，建立检索评测，再比较关键词、向量与混合方式。这样升级是为了解决实际漏检，不是为了简历里多写一个技术词。

追问1：知识量大了，直接取前面的片段有什么问题？

追问提纲：位置不等于相关 → 关键内容可能没进入 → 按问题召回

答：相关规则可能排在后面，模型根本看不到；前面的无关资料又占了上下文。应该根据当前素材和风险主题召回相关片段，并检查必要规则覆盖。先把需要的证据送进去，再谈生成效果。

追问2：结果带了法条引用，是不是就可信了？

追问提纲：来源真实 → 条件适用 → 结论被支持

答：不是。还要确认条款版本、适用对象和上下文，判断这段原文是否真的支持结论。当前引用定位是可追溯基础，不是法律判断正确的保证；资料不足要保留待核实状态。

### Q55｜你搭建的 Eval 怎么运行，评分有什么局限？

考察点：能讲出评测输入、执行、判分和迭代用途。

记忆提纲：① 按任务建用例 ② Runner 执行留版本 ③ 不同结果不同评分 ④ 错误分类驱动迭代

主回答：本地 Eval 按规则解析、审核规则和语义匹配分用例，由 Runner 读取输入、执行并比较预期和输出。确定性字段适合精确匹配，开放判断需要明确评分准则和人工校准，不能一把尺子量所有任务。它现在主要帮助我在改 Prompt 或规则后发现回归，真实 Worker 主流程也有评测入口。接下来要补的是更有代表性的业务标注和独立测试集，让报告不只是“通过几题”，而是能指出哪类用户任务仍不可靠。

追问1：你说的相似度评分，就是语义相似度吗？

追问提纲：当前是字符相似 → 不能证明事实或语义正确

答：当前有一个评分器是字符二元组的余弦相似度，不是语义向量。它可以辅助检查文字接近程度，但一句话改了否定词，含义可能反过来，字面仍很接近。所以核心业务正确性要用字段、规则和人工标准检查。

追问2：怎么避免把测试分数做得很好看？

追问提纲：独立测试集 → 版本和失败都保留 → 分项报告

答：调试集和测试集分开，保留失败调用，不只统计成功返回的样本；模型、Prompt、知识和规则版本都记录。分别报告执行错误、质量错误和待评审。模型评分还要校准，不能让同一个模型自评后就认定质量过关。

备考备注：评测入口代码存在不等于最新生产全链路已执行；历史小样本通过率也不是当前 AI 总体准确率。被问到具体报告时，按能出示的版本和运行记录回答。

### Q56｜用户有多少？节省 66%—78% 的时间是怎么测的？

考察点：数据口径、因果意识，以及能否解释结果范围。

记忆提纲：① 准备上线、无正式规模结论 ② 一天本人自测 ③ 同任务耗时公式 ④ 补质量与样本记录

主回答：项目还在备案、准备上线，所以目前没有正式运营的用户规模可以汇报。耗时来自我本人一天测试的观察：制作 20 人候选名单，从原来约 3 小时缩短到 40—60 分钟。以 180 分钟为基线，耗时减少约 66.7%—77.8%。这能说明流程自动化有潜力，但测试次数和同等质量的复核记录还要补齐。下一步会让真实媒介做同类任务，把等待、筛掉不合格候选和整理都算进去，看优势是否仍成立。

追问1：只有一天测试，面试官为什么相信？

追问提纲：限定能证明什么 → 给可复现验证办法

答：这一天不能证明稳定的平均提效，我把它作为初步信号。更可靠的方法是固定任务标准，保留人工与工具的过程、耗时和最终名单，让媒介独立复核，再做多份任务比较。没有完整记录的部分，不应报成精确统计结论。

追问2：上线以后怎样统计用户和审核效果？

追问提纲：用户分层去重 → 审核独立质量与耗时

答：注册按去重账号统计，剔除测试账号；完成真实任务算激活，再看后续任务周期的复用。审核单独准备经人工标注的图文，统计漏报、误报、引用和覆盖，再比较含查证、修改在内的总人工耗时。找人的节时不能拿来当审核结果。

备考备注：处理速度约为原来的 3—4.5 倍，与“耗时减少 66.7%—77.8%”分母不同。保留“耗时减少”最清楚。41 名历史落库达人不是注册用户；同类产品数据不替代你的结果。

## 新增专题｜数据治理、指标分析与故障排查

### Q66｜数据治理和特征工程，产品经理应介入多深，怎么配合算法？

考察点：是否理解业务口径、数据质量与算法实现之间的责任边界。

记忆提纲：① 业务目标与标签 ② 字段口径与质量 ③ 算法实现与验证 ④ 线上线下一致

主回答：我会介入到能解释数据代表什么、为什么对业务有用，以及出了问题怎么验收的程度。比如先和业务、算法明确预测目标、标签定义、字段口径、更新时间、缺失值含义和数据使用范围。以达人筛选为例，“近 30 天互动”统计哪些内容、按哪个时间窗口，都会影响结果；用户愿意联系也不能直接当作合作成功的标签。特征上我会提出业务假设，与算法一起验证是否有效，具体编码、筛选和训练由算法负责。还要一起检查训练时是否混入预测时拿不到的信息、评测样本是否独立，以及线上线下处理是否一致。如果是 RAG 应用，重点更多在知识来源、切分、检索和上下文质量，不能把所有数据处理都叫传统特征工程。

追问1：算法说某个业务上很重要的特征没用，怎么办？

追问提纲：核对定义与时点 → 检查冗余和切片 → 对照实验

答：先看字段有没有按预期计算、预测时能否拿到，再看它是不是和其他特征重复，或只在某类用户上有效。请算法比较有无该特征的效果和成本；如果没有稳定收益，就接受移除，不因为业务上听起来重要而强留。

追问2：怎么发现数据泄漏？

追问提纲：预测时点 → 数据可得性 → 划分与预处理

答：沿预测时点逐个核对字段，不能把事后结果当输入，比如预测是否合作却用了最终合同状态。再检查同一对象的重复样本是否跨了训练和测试集，以及预处理是否错误使用了测试数据。具体切分还要匹配未来上线的使用方式。

备考备注：对应本次原题 4。这是协作方法，不代表已有模型训练项目经历。参考 scikit-learn 对数据泄漏和不一致预处理的说明；特征分布发生变化也不自动证明业务效果下降，需要结合结果标签验证。

### Q68｜看调用成功率、留存等核心指标，还关注什么异常信号？

考察点：能否识别口径错误、平均数掩盖的问题及质量成本间的矛盾。

记忆提纲：① 先查口径与样本量 ② 拆人群和版本 ③ 看指标是否矛盾 ④ 按链路归因

主回答：我会先确认指标本身可信，包括分母、去重、重试、测试账号和数据延迟。调用成功也要区分接口正常返回、输出可解析和用户任务真正完成。然后按模型版本、场景、用户来源、新老用户和时间段拆开看，避免整体平均掩盖局部问题。我会特别留意几种信号：成功率提高但结果采用率下降，可能是把兜底或空结果算成功；平均延迟正常但 P95 升高，说明部分用户等待明显变长；成本突然下降却伴随质量下降，要查是否切了模型或少处理了输入。留存则按同一批用户的完整观察窗口比较，再结合业务发生频率判断。发现异常后，用发布记录、漏斗和样本定位原因，不直接认定是模型变差。

追问1：留存突然上涨，为什么还可能有问题？

追问提纲：用户组成 → 留存事件 → 观察窗口

答：可能这一批用户来源更精准，也可能埋点把自动刷新当成回访，或者比较了不同长度的观察窗口。我会确认留存事件代表主动、有价值的使用，再比较同类用户，而不是只看到上涨就宣布迭代有效。

追问2：调用成功率怎么避免被重试做高？

追问提纲：调用与任务分开 → 保留首试和重试成本

答：接口调用按实际请求统计，用户任务按去重任务标识统计，不能把两者混算。同时看首次成功率、最终任务成功率、重试次数与总耗时。任务最后做成了，也要暴露为了做成付出了多少额外成本。

备考备注：对应本次原题 6。P95 是约 95% 的请求延迟不超过的值；它用于观察长尾等待。指标异常先看绝对数量和历史正常波动，不能仅凭百分比大小判断严重性。

### Q69｜你会用 SQL 做一致性校验和异常排查，配合算法定位数据问题吗？

考察点：能否从业务约束出发查出可供进一步定位的异常样本。

记忆提纲：① 定粒度和约束 ② 查重复缺失关联 ③ 查时间分布与状态 ④ 交付可复现样本

主回答：会，我的开发背景可以支持这类 SQL 检查。开始前我会先确认一行数据代表一次调用、一个任务还是一个达人，以及表之间是一对一还是一对多，再查主键重复、关键字段缺失、关联不到的数据，以及关联后行数有没有意外放大。业务上还会检查状态和结果是否一致、时间顺序是否合理，并按日期、版本比较数量和缺失率。比如排查媒介助手，我会先聚合每个任务实际保存的去重达人数，再和任务汇总里的数量核对；发现差异后，保留任务标识、时间和查询条件交给相关同学。对于算法数据，再一起核对特征窗口和预测时点。我能承担数据排查，但不会把这说成已经主导过训练数据治理。

追问1：具体会怎么写，能举一个 SQL 思路吗？

追问提纲：先聚合到同一粒度 → 再关联 → 过滤差异

答：先按任务 ID 聚合结果表，计算去重达人数量，再左连接任务表，比较实际数量与记录数量。查询重复数据时按业务唯一键分组，用 HAVING COUNT(*) 大于 1 找候选异常。最后结合业务判断这些重复是否由合法历史版本或重试产生。

追问2：数据关联后数量翻倍，一定是重复脏数据吗？

追问提纲：检查关联基数 → 确认版本与粒度 → 再修查询

答：不一定，可能本来就是一对多，比如一个达人对应多条内容，或维表保留了多个历史版本。先确认指标要统计达人还是内容，再按对应粒度聚合或选择正确时点的版本，不能直接加 DISTINCT 掩盖问题。

备考备注：对应本次原题 7。上述表与字段为面试排查思路，非生产库已执行记录。未知值与 0 应分开处理，时间窗口和时区需要一致；异常值是否错误须由业务规则判断，不能一律删除。

### Q70｜模型效果突然下降又恢复了，你怎么排查？复现不了怎么办？

考察点：能否区分观测异常、质量退化与服务波动，做到证据保全和风险控制。

记忆提纲：① 确认下降与影响 ② 留存窗口和样本 ③ 对照数据配置链路 ④ 恢复后继续追踪

主回答：我会先确认掉的是业务效果、评测分数还是接口成功率，再看样本量、统计延迟和受影响范围。如果确实影响核心任务，先按预案降级、暂停放量，或在证据支持时回退。排查时保留异常前后的任务标识、输入输出和版本信息，把正常与异常样本对比，检查用户任务是不是变难了、数据是否缺失，模型、Prompt、知识库或路由有没有变化，以及限流、超时、重试和上下文截断等问题。恢复后也不会直接结案。复现不了，就保留未知根因，补充必要的脱敏日志、固定样本定时探测和告警，再约定复查时间。关键是下次出现时能定位，同时判断是否仍需要限制高风险场景。

追问1：重跑同一个输入正常，能排除模型问题吗？

追问提纲：请求环境可能变化 → 模型有随机性 → 重复对照

答：不能。模型版本、路由、外部检索结果和生成随机性都可能影响输出。需要尽量固定当时的配置和输入，多次比较正常与异常分布。一次重跑正常只能说明这次成功，不能证明此前没有质量问题。

追问2：日志不全，该向业务怎么交代？

追问提纲：已知影响 → 已采取措施 → 未知原因与复查计划

答：明确说明异常发生时间、已知影响、当前恢复情况和采取的措施，根因证据不足就不猜。同步补哪些监控、由谁跟进、什么时候复查。可以记录服务已恢复，但根因分析保持未关闭，不能写成“偶发，已解决”。

备考备注：对应本次原题 8。数据分布变化只是排查线索，不能直接等同于效果下降；脱敏日志只保留排障必要信息，并受权限和保存期限约束。参考 OpenTelemetry 的指标、日志和链路追踪方法。

### Q73｜严重的数据口径问题影响核心指标，明天交报告怎么办？

考察点：能否在期限压力下保证信息可信、管理影响并推动修正。

记忆提纲：① 立即同步影响 ② 留存版本并止用错误结论 ③ 复算或明确缺口 ④ 补校验防复发

主回答：我会当天就同步报告负责人和数据负责人，说明问题影响哪个指标、哪些时间段，以及是否可能改变结论。先保留当前数据、查询和报告版本，暂停传播有问题的数字，并按影响范围核对依赖它的图表和判断。同时把修正拆成最小可完成范围，优先重算核心指标，再由另一位同学交叉校验。如果明天能算清，就交修正版，并解释与原口径的差异；如果算不清，就交已验证的部分，受影响指标明确标注暂不可用，说明缺什么和补交时间，必要时申请延期。我不会为了按时交付，继续使用明知有问题的结果。之后再统一指标定义、版本和自动校验，防止同样的问题反复出现。

追问1：领导要求先用旧数字交出去呢？

追问提纲：说明决策风险 → 提供可交版本 → 留痕升级

答：我会解释旧数字可能导致的错误判断，并给出已验证部分先交、争议指标单独说明的方案。如果仍被要求把错误数据作为确定结论，应该记录风险并向更合适的负责人升级，不能私自配一个看起来合理的数字。

追问2：修正后核心指标大幅下降，怎么解释？

追问提纲：业务变化与统计变化分开 → 对照口径 → 重算历史

答：用同一批数据对照新旧口径，说明哪些差异来自去重、分母或事件定义，哪些才是业务变化。必要时重算历史，让趋势可比。口径修正导致的下降不能说成业务突然变差，也不能为了好看继续沿用旧值。

备考备注：对应本次原题 11。临时估算只有在有明确方法和足够证据时才提供，并标注范围与不确定性；不能把猜测填进正式结果。此题与 Q68 的日常异常识别区分，重点是截止期限下的交付和沟通。

### Q59｜入职前三个月你准备怎么做？

考察点：先理解业务，再通过可交付结果建立信任。

记忆提纲：① 30 天摸清任务与基线 ② 60 天验证一个改进 ③ 90 天复盘结果 ④ 目标与负责人对齐

主回答：第一个月先跟业务和用户走真实任务，了解现有产品、数据、协作方式和主要问题，选一个范围明确的改进并建立基线。第二个月推进方案验证和交付，跟研发、测试确认质量门槛；第三个月看真实使用结果，决定继续扩大还是调整。每个阶段都应该有具体产出，比如问题清单、可评审方案、验收记录和效果复盘，而不是只说熟悉业务。时间会按项目周期调整，我会先和负责人对齐预期。

追问1：接手的是存量产品，没有从零项目呢？

追问提纲：存量失败点 → 小改动验证

答：从高频失败和返工多的步骤切入，结合日志、客服反馈和任务观察找问题。先做可衡量的小改动，证明改善再扩大；没有从零机会不影响做出产品价值。

追问2：试用期怎么证明你是产品，不是开发支援？

追问提纲：职责先确认 → 产品决策和效果作为交付

答：入职时就对齐负责的用户问题、需求范围和验收指标。可以写原型代码辅助验证，但主要成果应是有依据的方案、推动完成的功能和复盘结果，而不是临时接了多少开发任务。

### Q60｜讲一个你做得不够好的地方，以及怎么改？

考察点：真实反思、责任承担和行动变化。

记忆提纲：① 功能先于用户验证 ② 开发惯性造成范围扩大 ③ 验证提前进排期 ④ 看实际改变

主回答：媒介助手里，我比较早就同时推进找人和审核，希望做出完整工具，但真实用户验证没有同步跟上。这是我的判断问题，不只是资源少：我沿用了“先把功能做完”的开发习惯。后来做计时自测和评测时，发现功能可用、结果可靠、用户愿意复用是不同的事。所以接下来每个迭代会先写清谁来试、带什么任务、达到什么结果才继续，而不是把调研留到全部开发完之后。

追问1：这只是反思，有实际改变吗？

追问提纲：已有行动 → 尚未完成的验证分开

答：已经做过一天名单计时自测，也建立了本地评测入口，开始按结果检查，而不只看功能是否运行。真实用户的复用验证还没完成，这会是上线后的优先工作，不能说已经完全解决了。

追问2：如果用户试完觉得没用，你能接受停掉吗？

追问提纲：定位失败原因 → 有限修正 → 不成立则停

答：能。先分清结果质量、操作负担还是需求本身的问题。前两类可以限定投入修正；若质量和体验达到标准，用户仍不愿在真实工作里用，就该缩范围或停止，不因为已经写了很多代码继续投入。

### Q61｜媒介助手怎么商业化，免费用户怎么转付费？

考察点：理解价值、使用频率与单位经济，而不是先做会员页。

记忆提纲：① 谁因什么付费 ② 重复价值先成立 ③ 套餐与任务量匹配 ④ 收入覆盖可变成本

主回答：先确认谁有持续任务、谁为这段工作买单。个人媒介可能更关心一份可用名单省了多少时间，团队还会看交付和协作。早期先验证真实任务和复用，再用明确的额度、价格和服务范围测试付费。低频任务可以测试按次，高频可以测试套餐，但要看数据接口和模型成本是否可覆盖。免费体验应让用户看到完整价值，同时控制成本；不能把注册量直接当成商业化基础。

追问1：怎么知道用户是真愿意付费，不是客气？

追问提纲：真实任务后 → 明确价格范围 → 看购买行为

答：让用户完成真实任务后，提供明确价格、额度和限制，看是否进入实际付费试用。访谈里说愿意，只算意向；付费后有没有持续使用和续费，才进一步说明价值稳定。

追问2：怎样判断这个业务赚不赚钱？

追问提纲：单任务贡献 → 获客与留存 → 固定成本

答：先算每个付费任务的收入减可变成本，包括数据接口、模型、图片处理、失败重试和人工支持。再看客户留存、获客成本与回收周期，最后覆盖研发等固定投入。只算 Token 费用，容易把真实成本低估。

### Q62｜内容审核为什么值得做？你怎么判断它真的有用？

考察点：讲清审核独立价值、人机分工和质量取舍。

记忆提纲：① 图文查证负担 ② 定位风险与依据 ③ 人工确认而非自动裁决 ④ 漏报误报与复核耗时

主回答：审核要解决的是媒介查资料、找风险位置和反复改稿的负担，不是再做一个能聊天的窗口。方案上，把图文内容、选定规则、风险位置和修改理由放在一起，让人工复核有依据。是否有价值，要看人工完成同质量审核的总时间是否下降，同时严重漏报和误报是否在可接受范围。仅仅多报几条风险不算更好，可能让用户查得更久。因此我定位成合规辅助初审，复杂和高风险内容仍由有经验的人确认。

追问1：漏报和误报哪个更重要？

追问提纲：按风险分层 → 高风险优先召回 → 控制误报负担

答：高风险场景优先控制漏报，但误报太多会让人忽视提示，所以要同时看召回率和精确率。召回是实际风险找到了多少，精确率是报出的风险有多少成立。不同风险分别定门槛，不能只看整体准确率。

追问2：不用人工，能不能直接自动改好并发布？

追问提纲：修改可能改变事实 → 对照确认 → 不自动发布

答：现阶段不合适。改写可能改变宣传事实、证据条件或品牌意思，需要保留原文与修改对照，由人确认。资料不足时应提示补证据，不能编一句听上去安全但不真实的话，更不能直接自动发布。

### Q63｜你会写 PRD、画 Figma，怎么证明不是会用工具而已？

考察点：产物能否支持讨论、实现、测试和结果验证。

记忆提纲：① 解释用户问题 ② 说明方案取舍 ③ 状态与异常完整 ④ 原型规则验收一致

主回答：我会拿一条具体需求展开，而不是展示很多页面。比如检索不足时，用户需要知道是条件太严、数据耗尽还是服务失败，不同原因决定能做什么操作。PRD 要写清触发条件、状态、可恢复方式和验收；Figma 要让用户看得懂这些状态，研发和测试也能对上。如果页面只有正常流程，规则和异常全靠口头补充，就算工具熟练也不算产品设计完成。我的重点是让材料能帮助团队做同一个东西。

追问1：给一个可验收的例子？

追问提纲：给定条件 → 触发事件 → 可观察结果

答：例如目标 20 人、已有 12 人时接口受限：页面显示真实数量和受限原因，已有结果不丢；恢复后沿进度继续，不能重复加入旧候选，也不能未经允许修改必要条件。这些都能分别构造测试，而不是只写“体验流畅”。

追问2：需求没说清，研发已经开工怎么办？

追问提纲：锁定当前假设 → 优先澄清高影响 → 同步变更

答：先问研发按什么假设实现，尽快确认影响数据和主流程的歧义；暂时无法决定的划出范围，必要时暂停相关部分。确认后同步原型、规则和测试，避免只口头改一处，其他人还按旧理解推进。

### Q64｜代码由 Codex 写，你自己的价值是什么？

考察点：产品判断与交付责任是否由你承担，能否解释真实贡献。

记忆提纲：① 定义问题与范围 ② 决定业务分工 ③ 验证而非照单全收 ④ 对结果负责

主回答：AI 帮助我提高实现速度，但不会替我承担产品判断。我需要决定为谁解决什么问题、哪些功能先做、哪些条件不能放宽，以及什么结果才算可用。比如找达人不是返回越多越好，审核也不是给一个“通过”就结束，这些边界要我来定义。代码生成后，还要检查数据、权限、异常和实际结果，再决定能不能交付。所以“独立完成”是我负责从需求到验证的全过程，不是宣称每行代码都手写。我的价值应该用决策和结果解释，而不是用提示词数量解释。

追问1：代码你都看得懂吗，出了问题能处理吗？

追问提纲：核心链路能解释 → 分层排错 → 不懂就验证

答：主要前后端业务链路是我熟悉的范围，出错会先按输入、接口、数据和状态逐层定位。新领域的实现会查资料、做最小测试，不只相信 AI 的解释。关键逻辑如果还不能解释和验证，就不能贸然交付。

追问2：AI 给了一个看似正确的产品方案，怎么判断？

追问提纲：事实是否成立 → 取舍是否合理 → 真实任务验证

答：先核对它依据的用户和数据是否真实，再看原流程、替代方案、异常和人工成本有没有漏。最后用原型或小功能跑真实任务。方案结构完整、术语多，只能说明写得像方案，不代表适合这个用户。

### Q71｜入职后快速接手陌生 AI 业务线，你怎么切入？

考察点：能否在有限时间内理解业务、识别关键依赖并形成可交付改进。

记忆提纲：① 跟用户走任务 ② 看数据与系统链路 ③ 用失败样本补知识 ④ 选小范围改进

主回答：我会先和负责人对齐这条业务线的目标、当前阶段，以及希望我先解决什么问题，再跟业务或用户完整走一次任务，弄清输入是什么、结果交给谁、什么情况算做好。随后和算法、研发看数据来源、模型能力、评测集和线上问题，把业务流程与技术链路对上。新场景或新模态的知识，我会围绕真实失败案例补，比如语音场景先区分识别错、理解错还是执行错，避免一开始泛泛学所有技术。第一周争取形成一份业务与数据流程图、关键问题清单和待验证假设，再选一个范围小、结果能衡量的改进，和负责人确定优先级后推进。

追问1：业务和技术给你的说法互相矛盾怎么办？

追问提纲：用同一任务复盘 → 对照日志和交付标准

答：拿同一条真实任务一起看，从用户输入跟到最终结果，核对系统记录和业务实际操作。很多分歧来自观察环节不同，先确定在哪一步理解不一致，再形成共同口径，不能只选一边相信。

追问2：领导要求三天给方案，怎么办？

追问提纲：先交初步判断 → 标清假设 → 优先验证高影响项

答：三天内可以交问题界定、初步方案、关键依赖和验证安排，但会标清哪些已经确认、哪些是假设。优先验证会推翻方案的条件，比如数据拿不到或质量达不到要求，不把未经确认的判断包装成完整结论。

备考备注：对应本次原题 9。与 Q59 互补：Q59 讲前三个月的阶段产出，本题强调进入陌生业务的第一周如何建立理解和选题。

### Q72｜你了解我们公司的 AI 业务吗？最值得关注的 1—2 个问题是什么？

考察点：是否做过具体准备，能否区分公开事实、体验观察和待验证判断。

记忆提纲：① 一个具体观察 ② 任务完成与用户价值 ③ 单位经济与质量 ④ 用问题核实判断

主回答：我主要看了贵公司的［具体产品、官方案例或产品文档］。其中［一个可核实的功能或体验］让我理解，这项业务主要在帮助［目标用户］完成［核心任务］。基于这些公开信息，我会优先关注两件事：一是用户能否稳定完成这项任务，包括关键步骤的失败和返工，这会影响实际采用和复用；二是规模扩大后，每个成功任务的成本和交付质量能否保持，特别是重试和人工处理会不会明显增加。不过，我目前拿不到内部数据，这两点是待验证的问题，不能直接认定贵公司已经存在。也想了解一下，团队现阶段更看重用户增长、任务效果还是商业化？我会据此调整优先级。

追问1：说得太通用，能不能具体一点？

追问提纲：产品入口 → 真实观察 → 影响假设 → 验证指标

答：需要回到实际准备的证据，例如“在［产品入口］完成［具体任务］时，我观察到［可复核现象］，它可能影响［完成率或复核耗时］，希望了解团队是否已有相关数据”。如果没有这个观察，我会承认准备不足，不临场编造公司问题。

追问2：内部数据证明你的判断不成立呢？

追问提纲：接受新证据 → 更新判断 → 聚焦真正约束

答：那我会调整判断。外部观察只能帮助提出假设，内部数据和真实业务能让判断更准确。如果任务质量已经很好，而问题在获客或付费，我就把分析重点转过去，不为了维护面试中的观点坚持原结论。

备考备注：对应本次原题 10。尚未提供面试公司，本题为待填模板，不是公司研究结论。面试前至少填入一个真实产品事实和一个具体观察；没有试用就说“看过公开资料”，不能说“我体验后发现”。

### Q74｜你平时用哪些 AI 产品设计或数据分析工具？

考察点：是否把工具用在具体任务上，并能准确说明熟练程度。

记忆提纲：① Figma 表达方案 ② SQL 查业务数据 ③ Codex 加快验证 ④ 用产出证明熟练度

主回答：我常用的主要是 Figma、SQL 和 Codex。Figma 用来画原型和关键状态，帮助讨论用户流程；SQL 结合我熟悉的 MySQL、Oracle、PostgreSQL 等数据库，做业务查询和数据核对。Codex 用来辅助原型开发、代码排查和测试，我负责确认需求与结果。AI 项目里，我也会结合模型输出和本地 Eval 记录，检查失败案例、版本差异和调用成本。相比列很多工具，我更愿意拿一份原型、一段查询或一次问题分析来说明具体用法。Axure、Python 和 Tableau 如果是岗位必需，我会如实说明目前掌握程度，再针对实际任务补齐，不把它们都说成熟练。

追问1：我们不用 Figma，用 Axure，会有影响吗？

追问提纲：核心方法可迁移 → 补工具操作 → 用需求验证

答：工具操作需要适应，但流程、状态、异常和交互表达的方法可以迁移。我会拿团队的一条真实需求练习 Axure 的交互表达，再和设计、研发确认能否支持评审，不只以会点按钮作为学会的标准。

追问2：如果要求用 Python 分析一批模型结果，你怎么做？

追问提纲：先定口径 → 小样本实现 → 人工交叉检查

答：先明确数据结构和分析口径，再处理小样本，核对读取、清洗和指标计算是否正确。可以借助 AI 生成脚本，但要检查异常值、缺失记录和分母，用已知样本或 SQL 对照验证，再扩大到全量。复杂分析会请熟悉的同学协作。

备考备注：对应本次原题 12。已确认的工具是 Figma、Codex、Java/React 与数据库技术；Python、Axure、Tableau 未确认熟练，保留实际水平边界。本地 Eval 的维护经历不等于精通 Python 数据分析。

### 三个数字口径

年限：2023.11.14—2026.03.31 约两年四个半月，含实习；2024.07 毕业，正式转正日待确认。不要说三年正式产品经验。

耗时：180 分钟降至 40—60 分钟，耗时减少 66.7%—77.8%，来自本人一天自测。测试次数、原始计时和同质量复核尚需补齐，不能当作多人长期平均。

审核指标练习（假设数据，不是项目结果）：20 个实际风险，系统报出 18 个，其中 15 个成立，则精确率为 15/18≈83.3%，召回率为 15/20=75%。必须先定义单位是素材还是风险项，分母不能混用。
