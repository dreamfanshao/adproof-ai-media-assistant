### Q65｜从 0 到 1 的 AI 产品，怎么从场景挖掘推进到上线迭代？

考察点：能否把业务价值、技术可行性、上线质量和持续迭代接起来。

记忆提纲：① 选场景、定基线 ② 验数据、做验证 ③ 收范围、定分工 ④ 灰度上线、看效果

主回答：我会先跟业务走一遍真实任务，找出最耗时、最容易出错的环节，再结合使用频率、收益、数据条件和错误代价选场景，同时记录现有方式的质量、耗时和成本。接着用一小批真实样本验证，比较规则方案和模型方案，确认 AI 的收益值得投入。确定方向后，把 MVP 收到一条完整任务上，明确输入输出、人工确认、异常处理和验收指标。模型选型由我和算法一起评估，训练与调参由算法负责；如果成熟模型已经够用，就不必自研。上线前固定评测集，检查端到端质量、延迟和成本，再小范围放量并准备回退方案。上线后看用户是否完成任务、是否采用结果和再次使用，再按问题出在数据、检索、模型还是交互来安排迭代。

追问1：模型指标达标，但用户觉得不好用怎么办？

追问提纲：核对评测代表性 → 观察完整任务 → 改正确环节

答：先看评测样本是否覆盖真实任务，再观察用户完成工作的全过程。可能答案正确但等得太久、需要反复复制、人工复核负担太大。把这些成本算进去，再决定改模型还是改流程，不能只拿离线分数说服用户。

追问2：你的媒介助手完整做过这些阶段吗？

追问提纲：讲已做阶段 → 限定用户验证和训练经历

答：我已经做过需求梳理、原型、开发测试和本人计时自测，模型主要通过现有能力接入。我还没有独立负责过自研模型训练到规模化运营的完整过程，上线后的长期用户效果要按实际记录说明。上面的回答是我接手项目时的推进思路。

备考备注：对应本次原题 3。与 Q12 的 MVP 优先级、Q37 的选型和 Q40 的评测配合练习。MVP 关注用最小投入验证关键假设，不要求所有业务模块都做齐；上线是一项发布动作，不能单凭上线就判断需求已经验证成功。

### Q66｜数据治理和特征工程，产品经理应介入多深，怎么配合算法？

考察点：是否理解业务口径、数据质量与算法实现之间的责任边界。

记忆提纲：① 业务目标与标签 ② 字段口径与质量 ③ 算法实现与验证 ④ 线上线下一致

主回答：我会介入到能解释数据代表什么、为什么对业务有用，以及出了问题怎么验收的程度。比如先和业务、算法明确预测目标、标签定义、字段口径、更新时间、缺失值含义和数据使用范围。以达人筛选为例，“近 30 天互动”统计哪些内容、按哪个时间窗口，都会影响结果；用户愿意联系也不能直接当作合作成功的标签。特征上我会提出业务假设，与算法一起验证是否有效，具体编码、筛选和训练由算法负责。还要一起检查训练时是否混入预测时拿不到的信息、评测样本是否独立，以及线上线下处理是否一致。如果是 RAG 应用，重点更多在知识来源、切分、检索和上下文质量，不能把所有数据处理都叫传统特征工程。

追问1：算法说某个业务上很重要的特征没用，怎么办？

追问提纲：核对定义与时点 → 检查冗余和切片 → 对照实验

答：先看字段有没有按预期计算、预测时能否拿到，再看它是不是和其他特征重复，或只在某类用户上有效。请算法比较有无该特征的效果和成本；如果没有稳定收益，就接受移除，不因为业务上听起来重要而强留。

追问2：怎么发现数据泄漏？

追问提纲：预测时点 → 数据可得性 → 划分与预处理

答：沿预测时点逐个核对字段，不能把事后结果当输入，比如预测是否合作却用了最终合同状态。再检查同一对象的重复样本是否跨了训练和测试集，以及预处理是否错误使用了测试数据。具体切分还要匹配未来上线的使用方式。

备考备注：对应本次原题 4。这是协作方法，不代表已有模型训练项目经历。参考 scikit-learn 对数据泄漏和不一致预处理的说明；特征分布发生变化也不自动证明业务效果下降，需要结合结果标签验证。

### Q67｜业务方认为 AI 方案与直觉不符，你怎么验证和沟通？

考察点：能否把意见分歧转成有共同标准的验证。

记忆提纲：① 找具体分歧 ② 对齐标准和损失 ③ 同样本比较 ④ 小范围验证

主回答：我会先让业务方拿一个具体例子，说明哪里不合理，是结果不符合经验，还是流程增加了工作量。然后一起确定判断标准，尤其是错选和漏选分别会带来什么损失。比如系统推荐的达人，业务觉得不适合，我会拆开看是硬条件、内容风格还是商业合作经验没有体现。接着用包含普通案例和争议案例的同一批样本，按事先约定的标准比较人工与 AI，条件允许时先隐藏结果来源，减少先入为主。如果业务经验有效，就把它补成规则、特征或评测案例；如果 AI 有优势，也先小范围试用验证。最后沟通哪些结论已经有证据、哪些还不确定，以及下一步用什么结果决定是否扩大。

追问1：业务坚持不同意，也不愿意做测试怎么办？

追问提纲：明确顾虑 → 降低验证成本 → 对齐决策责任

答：先确认是风险、时间还是对目标不认同。可以提出只在历史数据上做离线比较，或旁路观察、不影响业务。如果仍无法推进，就把收益假设、风险和验证成本交给共同负责人决定，不直接强推上线。

追问2：AI 整体更准，是否就应该采用？

追问提纲：关键场景 → 错误代价 → 总成本

答：还要看重要场景有没有退步、错误代价能否接受，以及人工复核和等待是否抵消收益。比如整体准确率提高，但高风险内容漏报变多，就不能仅凭平均分上线。必要时只在可靠的场景使用。

备考备注：对应本次原题 5。与 Q50 区别：本题主要面对业务经验和使用流程的分歧，Q50 主要面对研发或算法方案分歧。

### Q68｜看调用成功率、留存等核心指标，还关注什么异常信号？

考察点：能否识别口径错误、平均数掩盖的问题及质量成本间的矛盾。

记忆提纲：① 先查口径与样本量 ② 拆人群和版本 ③ 看指标是否矛盾 ④ 按链路归因

主回答：我会先确认指标本身可信，包括分母、去重、重试、测试账号和数据延迟。调用成功也要区分接口正常返回、输出可解析和用户任务真正完成。然后按模型版本、场景、用户来源、新老用户和时间段拆开看，避免整体平均掩盖局部问题。我会特别留意几种信号：成功率提高但结果采用率下降，可能是把兜底或空结果算成功；平均延迟正常但 P95 升高，说明部分用户等待明显变长；成本突然下降却伴随质量下降，要查是否切了模型或少处理了输入。留存则按同一批用户的完整观察窗口比较，再结合业务发生频率判断。发现异常后，用发布记录、漏斗和样本定位原因，不直接认定是模型变差。

追问1：留存突然上涨，为什么还可能有问题？

追问提纲：用户组成 → 留存事件 → 观察窗口

答：可能这一批用户来源更精准，也可能埋点把自动刷新当成回访，或者比较了不同长度的观察窗口。我会确认留存事件代表主动、有价值的使用，再比较同类用户，而不是只看到上涨就宣布迭代有效。

追问2：调用成功率怎么避免被重试做高？

追问提纲：调用与任务分开 → 保留首试和重试成本

答：接口调用按实际请求统计，用户任务按去重任务标识统计，不能把两者混算。同时看首次成功率、最终任务成功率、重试次数与总耗时。任务最后做成了，也要暴露为了做成付出了多少额外成本。

备考备注：对应本次原题 6。P95 是约 95% 的请求延迟不超过的值；它用于观察长尾等待。指标异常先看绝对数量和历史正常波动，不能仅凭百分比大小判断严重性。

### Q69｜你会用 SQL 做一致性校验和异常排查，配合算法定位数据问题吗？

考察点：能否从业务约束出发查出可供进一步定位的异常样本。

记忆提纲：① 定粒度和约束 ② 查重复缺失关联 ③ 查时间分布与状态 ④ 交付可复现样本

主回答：会，我的开发背景可以支持这类 SQL 检查。开始前我会先确认一行数据代表一次调用、一个任务还是一个达人，以及表之间是一对一还是一对多，再查主键重复、关键字段缺失、关联不到的数据，以及关联后行数有没有意外放大。业务上还会检查状态和结果是否一致、时间顺序是否合理，并按日期、版本比较数量和缺失率。比如排查媒介助手，我会先聚合每个任务实际保存的去重达人数，再和任务汇总里的数量核对；发现差异后，保留任务标识、时间和查询条件交给相关同学。对于算法数据，再一起核对特征窗口和预测时点。我能承担数据排查，但不会把这说成已经主导过训练数据治理。

追问1：具体会怎么写，能举一个 SQL 思路吗？

追问提纲：先聚合到同一粒度 → 再关联 → 过滤差异

答：先按任务 ID 聚合结果表，计算去重达人数量，再左连接任务表，比较实际数量与记录数量。查询重复数据时按业务唯一键分组，用 HAVING COUNT(*) 大于 1 找候选异常。最后结合业务判断这些重复是否由合法历史版本或重试产生。

追问2：数据关联后数量翻倍，一定是重复脏数据吗？

追问提纲：检查关联基数 → 确认版本与粒度 → 再修查询

答：不一定，可能本来就是一对多，比如一个达人对应多条内容，或维表保留了多个历史版本。先确认指标要统计达人还是内容，再按对应粒度聚合或选择正确时点的版本，不能直接加 DISTINCT 掩盖问题。

备考备注：对应本次原题 7。上述表与字段为面试排查思路，非生产库已执行记录。未知值与 0 应分开处理，时间窗口和时区需要一致；异常值是否错误须由业务规则判断，不能一律删除。

### Q70｜模型效果突然下降又恢复了，你怎么排查？复现不了怎么办？

考察点：能否区分观测异常、质量退化与服务波动，做到证据保全和风险控制。

记忆提纲：① 确认下降与影响 ② 留存窗口和样本 ③ 对照数据配置链路 ④ 恢复后继续追踪

主回答：我会先确认掉的是业务效果、评测分数还是接口成功率，再看样本量、统计延迟和受影响范围。如果确实影响核心任务，先按预案降级、暂停放量，或在证据支持时回退。排查时保留异常前后的任务标识、输入输出和版本信息，把正常与异常样本对比，检查用户任务是不是变难了、数据是否缺失，模型、Prompt、知识库或路由有没有变化，以及限流、超时、重试和上下文截断等问题。恢复后也不会直接结案。复现不了，就保留未知根因，补充必要的脱敏日志、固定样本定时探测和告警，再约定复查时间。关键是下次出现时能定位，同时判断是否仍需要限制高风险场景。

追问1：重跑同一个输入正常，能排除模型问题吗？

追问提纲：请求环境可能变化 → 模型有随机性 → 重复对照

答：不能。模型版本、路由、外部检索结果和生成随机性都可能影响输出。需要尽量固定当时的配置和输入，多次比较正常与异常分布。一次重跑正常只能说明这次成功，不能证明此前没有质量问题。

追问2：日志不全，该向业务怎么交代？

追问提纲：已知影响 → 已采取措施 → 未知原因与复查计划

答：明确说明异常发生时间、已知影响、当前恢复情况和采取的措施，根因证据不足就不猜。同步补哪些监控、由谁跟进、什么时候复查。可以记录服务已恢复，但根因分析保持未关闭，不能写成“偶发，已解决”。

备考备注：对应本次原题 8。数据分布变化只是排查线索，不能直接等同于效果下降；脱敏日志只保留排障必要信息，并受权限和保存期限约束。参考 OpenTelemetry 的指标、日志和链路追踪方法。

### Q71｜入职后快速接手陌生 AI 业务线，你怎么切入？

考察点：能否在有限时间内理解业务、识别关键依赖并形成可交付改进。

记忆提纲：① 跟用户走任务 ② 看数据与系统链路 ③ 用失败样本补知识 ④ 选小范围改进

主回答：我会先和负责人对齐这条业务线的目标、当前阶段，以及希望我先解决什么问题，再跟业务或用户完整走一次任务，弄清输入是什么、结果交给谁、什么情况算做好。随后和算法、研发看数据来源、模型能力、评测集和线上问题，把业务流程与技术链路对上。新场景或新模态的知识，我会围绕真实失败案例补，比如语音场景先区分识别错、理解错还是执行错，避免一开始泛泛学所有技术。第一周争取形成一份业务与数据流程图、关键问题清单和待验证假设，再选一个范围小、结果能衡量的改进，和负责人确定优先级后推进。

追问1：业务和技术给你的说法互相矛盾怎么办？

追问提纲：用同一任务复盘 → 对照日志和交付标准

答：拿同一条真实任务一起看，从用户输入跟到最终结果，核对系统记录和业务实际操作。很多分歧来自观察环节不同，先确定在哪一步理解不一致，再形成共同口径，不能只选一边相信。

追问2：领导要求三天给方案，怎么办？

追问提纲：先交初步判断 → 标清假设 → 优先验证高影响项

答：三天内可以交问题界定、初步方案、关键依赖和验证安排，但会标清哪些已经确认、哪些是假设。优先验证会推翻方案的条件，比如数据拿不到或质量达不到要求，不把未经确认的判断包装成完整结论。

备考备注：对应本次原题 9。与 Q59 互补：Q59 讲前三个月的阶段产出，本题强调进入陌生业务的第一周如何建立理解和选题。

### Q72｜你了解我们公司的 AI 业务吗？最值得关注的 1—2 个问题是什么？

考察点：是否做过具体准备，能否区分公开事实、体验观察和待验证判断。

记忆提纲：① 一个具体观察 ② 任务完成与用户价值 ③ 单位经济与质量 ④ 用问题核实判断

主回答：我主要看了贵公司的［具体产品、官方案例或产品文档］。其中［一个可核实的功能或体验］让我理解，这项业务主要在帮助［目标用户］完成［核心任务］。基于这些公开信息，我会优先关注两件事：一是用户能否稳定完成这项任务，包括关键步骤的失败和返工，这会影响实际采用和复用；二是规模扩大后，每个成功任务的成本和交付质量能否保持，特别是重试和人工处理会不会明显增加。不过，我目前拿不到内部数据，这两点是待验证的问题，不能直接认定贵公司已经存在。也想了解一下，团队现阶段更看重用户增长、任务效果还是商业化？我会据此调整优先级。

追问1：说得太通用，能不能具体一点？

追问提纲：产品入口 → 真实观察 → 影响假设 → 验证指标

答：需要回到实际准备的证据，例如“在［产品入口］完成［具体任务］时，我观察到［可复核现象］，它可能影响［完成率或复核耗时］，希望了解团队是否已有相关数据”。如果没有这个观察，我会承认准备不足，不临场编造公司问题。

追问2：内部数据证明你的判断不成立呢？

追问提纲：接受新证据 → 更新判断 → 聚焦真正约束

答：那我会调整判断。外部观察只能帮助提出假设，内部数据和真实业务能让判断更准确。如果任务质量已经很好，而问题在获客或付费，我就把分析重点转过去，不为了维护面试中的观点坚持原结论。

备考备注：对应本次原题 10。尚未提供面试公司，本题为待填模板，不是公司研究结论。面试前至少填入一个真实产品事实和一个具体观察；没有试用就说“看过公开资料”，不能说“我体验后发现”。

### Q73｜严重的数据口径问题影响核心指标，明天交报告怎么办？

考察点：能否在期限压力下保证信息可信、管理影响并推动修正。

记忆提纲：① 立即同步影响 ② 留存版本并止用错误结论 ③ 复算或明确缺口 ④ 补校验防复发

主回答：我会当天就同步报告负责人和数据负责人，说明问题影响哪个指标、哪些时间段，以及是否可能改变结论。先保留当前数据、查询和报告版本，暂停传播有问题的数字，并按影响范围核对依赖它的图表和判断。同时把修正拆成最小可完成范围，优先重算核心指标，再由另一位同学交叉校验。如果明天能算清，就交修正版，并解释与原口径的差异；如果算不清，就交已验证的部分，受影响指标明确标注暂不可用，说明缺什么和补交时间，必要时申请延期。我不会为了按时交付，继续使用明知有问题的结果。之后再统一指标定义、版本和自动校验，防止同样的问题反复出现。

追问1：领导要求先用旧数字交出去呢？

追问提纲：说明决策风险 → 提供可交版本 → 留痕升级

答：我会解释旧数字可能导致的错误判断，并给出已验证部分先交、争议指标单独说明的方案。如果仍被要求把错误数据作为确定结论，应该记录风险并向更合适的负责人升级，不能私自配一个看起来合理的数字。

追问2：修正后核心指标大幅下降，怎么解释？

追问提纲：业务变化与统计变化分开 → 对照口径 → 重算历史

答：用同一批数据对照新旧口径，说明哪些差异来自去重、分母或事件定义，哪些才是业务变化。必要时重算历史，让趋势可比。口径修正导致的下降不能说成业务突然变差，也不能为了好看继续沿用旧值。

备考备注：对应本次原题 11。临时估算只有在有明确方法和足够证据时才提供，并标注范围与不确定性；不能把猜测填进正式结果。此题与 Q68 的日常异常识别区分，重点是截止期限下的交付和沟通。

### Q74｜你平时用哪些 AI 产品设计或数据分析工具？

考察点：是否把工具用在具体任务上，并能准确说明熟练程度。

记忆提纲：① Figma 表达方案 ② SQL 查业务数据 ③ Codex 加快验证 ④ 用产出证明熟练度

主回答：我常用的主要是 Figma、SQL 和 Codex。Figma 用来画原型和关键状态，帮助讨论用户流程；SQL 结合我熟悉的 MySQL、Oracle、PostgreSQL 等数据库，做业务查询和数据核对。Codex 用来辅助原型开发、代码排查和测试，我负责确认需求与结果。AI 项目里，我也会结合模型输出和本地 Eval 记录，检查失败案例、版本差异和调用成本。相比列很多工具，我更愿意拿一份原型、一段查询或一次问题分析来说明具体用法。Axure、Python 和 Tableau 如果是岗位必需，我会如实说明目前掌握程度，再针对实际任务补齐，不把它们都说成熟练。

追问1：我们不用 Figma，用 Axure，会有影响吗？

追问提纲：核心方法可迁移 → 补工具操作 → 用需求验证

答：工具操作需要适应，但流程、状态、异常和交互表达的方法可以迁移。我会拿团队的一条真实需求练习 Axure 的交互表达，再和设计、研发确认能否支持评审，不只以会点按钮作为学会的标准。

追问2：如果要求用 Python 分析一批模型结果，你怎么做？

追问提纲：先定口径 → 小样本实现 → 人工交叉检查

答：先明确数据结构和分析口径，再处理小样本，核对读取、清洗和指标计算是否正确。可以借助 AI 生成脚本，但要检查异常值、缺失记录和分母，用已知样本或 SQL 对照验证，再扩大到全量。复杂分析会请熟悉的同学协作。

备考备注：对应本次原题 12。已确认的工具是 Figma、Codex、Java/React 与数据库技术；Python、Axure、Tableau 未确认熟练，保留实际水平边界。本地 Eval 的维护经历不等于精通 Python 数据分析。

### Q75｜未来 3—5 年，你的职业规划是什么？

考察点：职业方向是否稳定，成长目标是否建立在岗位责任与实际成果上。

记忆提纲：① 先独立负责模块 ② 再做透业务场景 ③ 兼顾效果与商业 ④ 管理随责任发展

主回答：未来一年，我希望先完成从开发到 AI 应用产品的转变，能独立负责一个明确模块，把需求判断、研发推进和上线后的效果复盘做完整。两到三年，希望在一个业务领域持续积累，比如企业效率或营销工具，能够负责完整场景，既判断模型能力，也判断用户价值和投入产出。三到五年，希望有能力负责更完整的产品方向，做跨团队的优先级和资源取舍。如果有带团队的机会，我愿意承担，但会以已经做出的产品结果为基础。对我来说，这次转岗希望建立的是长期产品能力，而不是短期追一个 AI 头衔。

追问1：三年后没有带团队的机会，你会离开吗？

追问提纲：职责成长 → 业务积累 → 不以头衔单一判断

答：不会只因为没有管理头衔就离开。我会看负责的问题是否更复杂、决策范围是否扩大、是否持续积累产品成绩。如果能深入业务并承担更大的结果责任，资深个人贡献者也是有价值的发展路径。

追问2：AI 变化很快，怎么保证规划不失效？

追问提纲：稳定目标 → 灵活技术路径 → 周期复盘

答：我规划的是需求判断、数据分析、协作和结果验证能力，具体模型和工具会随业务更新。阶段性复盘岗位和技术变化，调整学习内容与项目选择，但不会因为出现一个新概念就频繁更换职业方向。

备考备注：对应本次原题 13。与 Q08 共用职业主线；本题展开到 3—5 年，面试时按对方要求选择长短版本，避免两道题给出不同方向。
