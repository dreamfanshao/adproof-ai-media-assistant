## 四｜AI 基础：回答选型、边界与验证（Q34—Q43）

本部分于 2026-09-14 重写：保留原 10 道主问题及 20 道追问，补齐技术机制、决策条件、指标口径和验证方法。先记提纲，再练主回答；“技术补充”供深入追问时展开。方法题中的“我会”表示方案思路，不表示个人项目已实现全部能力。

### Q34｜RAG、Workflow、Agent 分别是什么？

考察点：区分知识增强、流程编排和动态决策，能根据任务特性选择架构。

记忆提纲：① RAG：检索增强生成 ② Workflow：预设控制路径 ③ Agent：模型动态决策与执行 ④ 按不确定性和风险组合

主回答：RAG 是检索增强生成，在推理时从外部知识源检索与任务相关的信息，将其作为上下文交给模型生成答案。它主要解决私有知识、知识更新和证据追溯问题；通常不需要改变生成模型的参数，也不限定必须使用向量数据库。

Workflow 是流程编排，由代码或配置预先定义步骤、分支和执行条件，可以包含模型、检索和工具调用，适合路径相对稳定、需要控制时延和审计过程的任务。Agent 则让模型在目标和约束下，根据当前状态与工具反馈动态决定下一步行动。关键区别在于执行路径由谁决定，而不是有没有调用工具。

产品选型时，我会判断路径的不确定性、能否获得可验证的反馈，以及错误后果。比如图文初审，可以用固定 Workflow 保证必查项完整，在其中用 RAG 提供规则依据；开放式达人发现，则可让 Agent 在预算内决定补查方向。三者可以组合，但要通过任务完成质量和成本证明新增复杂度的价值。[A1]

技术补充：RAG 是知识增强机制，Workflow/Agent 是任务执行的组织方式。Agent 可以把 RAG 作为工具，也可以嵌入固定流程。自动重试、定时任务或大量条件分支本身不等于 Agent；模型选择一次工具也不必然构成完整的自主执行系统。

追问1：RAG 为什么不等于知识库问答？

追问提纲：机制与产品形态 → 检索结果参与生成 → 多种输出

答：知识库问答是产品形态，RAG 是底层机制。内容审核可以检索规则后生成风险分析，报告生成可以检索资料后输出带依据的结论，它们都可以使用 RAG。反过来，问答产品也可以只查数据库或直接使用完整文档，不一定采用 RAG。判断依据是是否存在“按任务检索外部信息，再基于检索信息生成”的过程，而不是有没有聊天窗口。

追问2：举一个适合 Agent 的任务？

追问提纲：路径不能预先穷举 → 反馈可验证 → 自主范围有限

答：例如围绕投放需求寻找达人。初始搜索可能返回大量品牌账号，也可能缺少近期内容证据，系统需要依据结果动态调整查询、补读主页，再决定是否继续。适合 Agent 的是搜索和补证路径；粉丝范围、去重、调用预算和停止条件仍由系统控制。如果只是依次执行固定关键词列表，就应称为 Workflow，不把普通循环包装成 Agent。

### Q35｜如何设计并评估 RAG？

考察点：完整描述离线入库与在线检索链路，用分层评测定位瓶颈。

记忆提纲：① 知识治理与切块 ② 召回、融合、重排 ③ 证据组织与生成 ④ 检索、回答、任务三层评测

主回答：我会把 RAG 分成离线知识处理和在线检索生成两条链路。离线先确定来源、更新频率和访问权限，再解析、去重和切块，保留标题、条款层级、来源、有效版本及权限元数据。使用向量检索时建立 Embedding 索引，查询与文档要采用兼容的同一模型空间。

在线先识别实体、时间和限制条件，必要时做查询改写或拆分。召回可结合关键词与向量检索，融合候选后重排；将相关且互补的证据在 Token 预算内组织为上下文，要求回答能对应具体来源。证据不足时补充检索、部分回答或转人工，不能把相似度直接当作答案正确概率。[A2、A3]

评估分三层：检索层看相关证据的 Recall@K、Precision@K 和排序质量；回答层看事实正确性、证据忠实度、问题覆盖和引用支持度；任务层看业务完成、人工复核耗时、延迟和成本。出现 Bad Case，先确认知识是否存在，再查召回、重排、上下文和生成各阶段。比如正确条款已经召回却未进入最终上下文，就不应优先修改生成 Prompt。[A4、A5]

技术补充：检索 Recall@K = 前 K 项命中的相关证据数 / 标注相关证据总数；固定 K 的 Precision@K = 前 K 项相关证据数 / K，不足 K 时的分母需预先约定。MRR 关注首个相关结果的位置，NDCG@K 适合评价带相关性等级的排序。审核可能需要多个条款共同支持，应增加“必要证据完整覆盖率”。ANN 索引近似召回率与业务相关证据召回率不同，不能混用；标注不完整时也不能声称测出了全库真实召回率。

追问1：Chunk 大小怎么定？

追问提纲：保证语义完整 → 检索与生成粒度可分离 → 同集对比

答：先按文档结构切，不直接套固定字数。法规条款要保留适用对象、条件和例外，表格要保留表头对应关系。小块更聚焦，但可能丢上下文；大块更完整，却可能引入噪声。我会测试不同粒度、适量重叠，以及“小块检索、回填父段落”。在同一问题集上比较必要证据覆盖率、答案正确性、重复片段占比和成本，再确定参数。重叠比例和 Token 数都不应当作行业通用标准。

追问2：什么时候混合检索？

追问提纲：精确与语义互补 → RRF 融合 → Reranker 精排 → 消融验证

答：当问题同时包含品牌名、条款编号等精确实体，以及同义词、口语表达时，值得验证混合检索。BM25 擅长词项匹配，向量检索补充语义相近结果。两类原始分数尺度不同，可以用 RRF 按排名融合，再用 Reranker 对查询与候选片段重新评分。重排只能处理已经召回的候选，无法挽救完全漏召回的证据。最后做单路、混合、加重排的消融对比，看有效覆盖提升是否值得新增延迟和成本。[A3]

### Q36｜怎么控制幻觉？

考察点：理解生成机制与证据约束的局限，建立可衡量的风险控制方案。

记忆提纲：① 区分事实错误与证据不忠实 ② 治理知识和检索 ③ 约束生成并校验 ④ 联合看错误、拒答和覆盖

主回答：大模型输出是基于上下文的概率性生成，并不是事实数据库。回答可能与外部事实不符，也可能与给定证据不一致，因此要分别评价事实正确性和证据忠实度。控制幻觉需要覆盖数据、检索、生成和结果处理整个链路。

首先保证资料权威、有效且适用，再检查是否检索到支撑当前判断的证据。生成时明确哪些结论必须有来源、哪些只能作为建议，并要求标出证据缺口。日期、金额、编号和结构化字段由程序或权威系统校验；语义结论则核对证据是否真正支持它，输出格式正确不代表事实正确。[A4、A5]

以图文初审为例，我会让结果分别呈现素材证据、适用规则和风险说明。资料不足、图片不清晰或存在解释分歧时转为待确认，再交人工复核。评测同时看无依据断言、严重漏报、误报、过度拒答和可答覆盖。降低 temperature 可以减少部分采样波动，但不能保证事实正确；加 RAG 也不能消除检索错误和错误推断。

技术补充：幻觉率没有统一分母，可以按“含无依据事实断言的回答数 / 含事实断言的被评回答数”计算，也可以逐条断言统计。需固定判定标准、核验来源和统计单位；拒答单独统计，避免靠增加拒答降低幻觉率。模型自报置信分数未经标注数据校准，不能作为真实正确概率。

追问1：有引用但不支持结论怎么办？

追问提纲：真实性 → 语义支持 → 适用条件 → 定位环节

答：检查引用是否真实存在且版本有效、原文是否支持断言，以及规则的适用对象、条件和例外是否与素材一致。真实引用也可能被误用，这类结果应判为依据不足或判断错误。修复时区分检索选错、上下文截断还是生成扩大解释。高风险结果先撤回确定性表达或转人工，再把样本加入回归集；第二个模型只能辅助核验，不能自动充当最终裁决者。

追问2：拒答率太高怎么办？

追问提纲：标注可答性 → 区分原因 → 分级处理 → 检查覆盖与风险

答：先建立可答与不可答问题集，统计可答问题被拒绝的比例，区分知识缺失、检索失败、输入不完整和门槛过严。前两类修复知识和检索，输入不完整则澄清，部分有依据时只回答可证实部分。阈值按风险等级调整，在验证集上观察覆盖提高时错误率如何变化。不能只看拒答率下降，审核场景还要检查严重漏报和人工承接能力。

### Q37｜怎么选模型？

考察点：在效果、服务性能、成本和部署约束之间作可验证的选择。

记忆提纲：① 任务与硬约束 ② 同任务评测 ③ 成功任务总成本 ④ 路由、灰度与替换

主回答：选型首先落到具体任务：需求解析看意图与约束提取，达人判断看语义匹配，图文初审看文字、图像和二者关系。同时明确结构化输出、工具调用、数据处理要求、并发及响应时间等硬约束，达不到必要条件的模型先排除。

我会建立覆盖常见、困难、边界和高风险场景的业务评测集。先在相同资料、工具条件和可比预算下比较，再给候选模型合理的 Prompt 适配机会，在独立测试集上盲评，记录模型版本及参数。重点看任务成功率、漏报误报、字段与工具参数正确性，以及重复运行稳定性；榜单用于初筛，最终选择由业务评测决定。[A6]

质量过线后比较成功任务总成本，计入输入输出、图片、外部工具、重试，以及可量化的人工复核成本；性能看端到端 P95 和目标负载下的稳定性。再判断统一模型还是按难度、风险路由。上线采用灰度和可回退配置，升级也重新回归，不能默认新版本更适合业务。

技术补充：上下文长度、参数规模和推理能力是不同维度，长上下文不等于复杂推理更强。首 Token 延迟影响交互反馈，完整任务延迟影响交付效率；流式显示不能缩短全部执行时间。私有部署还要计入算力利用率、运维、弹性与升级成本，不能只比 Token 单价。

追问1：贵模型只提升 2% 怎么办？

追问提纲：百分比或百分点 → 差异可信度 → 错误价值 → 增量收益

答：先确认是相对提升 2%，还是增加 2 个百分点，再看样本规模、重复试验和置信区间，判断差异是否稳定。若提升集中在严重漏报，可能比普通题多答对几道更有价值。我会估算业务量下减少的错误损失和人工时间，与新增费用、延迟比较。收益不足时不全量切换，可以只把高风险或难例路由给它，但路由误分流和升级比例也要评估，否则理论节省无法兑现。

追问2：模型升级怎么处理？

追问提纲：完整版本记录 → 回归和负载验证 → 灰度监测 → 真实可用的回退

答：先记录模型标识、Prompt、工具 Schema、知识索引和参数版本，跑固定回归集、历史 Bad Case 及新业务样本，检查格式、调用协议和负载表现。通过后按小流量灰度，监控关键质量切片、失败率、P95 和单任务成本；触发预设退化门槛就回退。如果供应商不支持固定版本或旧模型即将停用，就提前验证备选模型与降级流程，不能把回退建立在不可用的旧接口上。

### Q38｜怎么设计和管理 Prompt？

考察点：把业务标准转成可测试的输入输出契约，通过版本化评测迭代。

记忆提纲：① 任务、判据与边界 ② 输入分区和输出契约 ③ 示例与异常策略 ④ 版本、实验与回归

主回答：我会先定义业务判据和验收标准，再设计 Prompt，明确目标、输入字段、判断规则、证据要求、输出字段，以及信息缺失或无法判断时的处理方式。系统规则、用户需求和外部资料分区组织，避免将资料文本误当成执行指令。

对容易混淆的判断，用少量覆盖典型、反例和边界的 Few-shot 示例明确标准，例如提供祛痘服务的账号和分享本人祛痘经历的达人，语义相关但业务资格不同。需要结构化结果时定义 JSON Schema，再由服务端校验必填项、枚举、类型和跨字段约束；Schema 保证结构层面，业务事实仍需验证。

优化时针对 Bad Case 提出具体假设，如漏掉排除条件或把建议当事实，控制变量比较新旧版本。Prompt 与模型、示例、工具和评测集一起版本管理，经独立测试集回归再灰度。查询不到证据、工具失败和权限不足，应有明确输出状态，不能只补一句“请准确回答”。

技术补充：Prompt Engineering 主要设计指令和示例；Context Engineering 还管理检索证据、历史消息、工具说明与任务状态。temperature、top_p、输出长度等配置也需记录，避免把参数变化归因于 Prompt。输入分隔可以减少混淆，但不能独立解决提示词注入。[A7、A8]

追问1：Few-shot 过拟合怎么办？

追问提纲：示例偏置与测试泄漏 → 数据隔离 → 边界覆盖 → 未见样本验证

答：Few-shot 通常不更新参数，这里的过拟合主要指过度依赖示例模式，或反复针对同一批题调 Prompt 造成评测过拟合。我会隔离示例、开发和保留测试集，按文档或任务来源分组去重，避免近重复泄漏。示例覆盖决策边界，再用未见表达、反例和示例顺序扰动测试。对比零样本、少量示例和更多示例，确认新增示例是否真有泛化收益，而不是原题得分更好。

追问2：Prompt 泄露怎么办？

追问提纲：识别泄露内容 → 秘密不入 Prompt → 服务端授权 → 注入回归

答：先区分普通指令被看到，还是密钥、敏感数据或内部规则泄露。普通 Prompt 泄露与权限突破不是一回事；若包含凭据，就需要按凭据事件处理。设计上不把密钥放进 Prompt，也不靠“请勿泄露”承担权限控制；工具权限、数据范围和参数校验在服务端执行。网页、文件和知识库属于不可信输入，不能改变授权范围。发布前测试直接、间接提示词注入及越权读取、工具滥用场景。[A8、A9]

### Q39｜什么时候 RAG，什么时候微调？

考察点：理解上下文补充与参数训练的差异，按失败原因选择投入。

记忆提纲：① RAG 补外部知识 ② SFT 训练任务行为 ③ LoRA 是微调方式 ④ 用基线与独立评测决定组合

主回答：先判断瓶颈在知识供给还是任务行为。私有资料经常更新、答案需要出处、权限随用户变化时，优先考虑 RAG：知识保存在外部，按任务检索进入上下文，更新知识通常不需要重训生成模型。

微调通过训练数据和优化目标更新模型的部分或全部参数。SFT 使用高质量输入输出示范训练特定行为，适合稳定的领域表达、分类抽取或指令遵循需求。LoRA 是参数高效微调方法，通常冻结基础权重、训练低秩增量矩阵，以减少可训练参数和部分训练资源开销。SFT 是训练范式，LoRA 是参数更新方式，两者可以同时使用。[A10、A11]

决策前先建立基础模型加 Prompt/Few-shot 的基线。如果补齐证据后仍持续出现同类行为错误，而且有足够高质量、具代表性的数据和维护预算，再评估微调收益。知识更新与行为适配同时存在，可以 RAG 加微调。对媒介助手这类规则更新、判断要追溯的场景，我会优先验证知识质量和检索链路，不因领域垂直就直接训练模型。

技术补充：微调能吸收部分领域知识，但不保证完整记忆、实时更新或可靠出处。需要隔离训练、验证、测试数据，评估业务收益、通用能力回归、过拟合和全生命周期成本。LoRA 降低部分训练开销，不等于不需要训练资源，也不保证任何任务都能用少量数据提升。

追问1：微调后知识过期怎么办？

追问提纲：可变事实外置 → 冲突专项评测 → 行为改变再训练

答：经常变化的事实放在版本化知识库或权威 API 中，推理时读取。如果参数中的旧知识与检索到的新资料冲突，用专门样本验证模型是否遵循新证据，不能只靠“以新资料为准”一句话保证效果。若变化的是判断规则或目标行为，再更新标注和训练数据、重新训练并回归。撤销的资料也要同步处理索引和缓存。

追问2：什么时候直接用长上下文？

追问提纲：材料范围 → 全文基线 → 信息定位能力 → 成本与维护

答：一次任务只涉及少量、范围明确且权限一致的材料，需要跨章节综合理解时，可以先把完整资料送给长上下文模型，减少检索漏证据。但装得下不等于用得好，要测试多处证据组合、中间位置内容、冲突版本和长文干扰。知识规模大、更新频繁、权限复杂或重复查询多时，RAG 通常更便于按需取数。用同一任务集比较质量、延迟、Token 和维护成本，也可以先检索文档再读取相关全文。[A7]

### Q40｜怎么建立 AI 产品评测体系？

考察点：覆盖真实任务和系统行为，形成可信的迭代、发布与回归机制。

记忆提纲：① 成功与严重错误定义 ② 分层样本和独立测试 ③ 规则、人工和模型评分 ④ 离线门槛接线上验证

主回答：先把业务目标转成可判定的成功标准，并明确不可接受错误。达人发现看候选是否满足条件且可用；图文初审看风险识别、依据适用和复核价值，不能用同一个准确率概括全部能力。

数据集分两类：按真实流量结构抽样的代表集，用来估计整体表现；高风险、边界和历史 Bad Case 构成挑战集，用来暴露薄弱点，两者分别报告。标注记录评分单位、期望结果或准则、证据和风险等级。保留不参与调优的测试集，对模型、Prompt、工具、知识索引和数据集做版本记录。

评分采用分工：结构和数值用程序判定，复杂语义由业务专家制定 Rubric，LLM-as-a-Judge 辅助扩展但须与人工标注校准。Agent 除最终结果，还要检查工具轨迹、重复执行、越权、重试与恢复。非确定性任务重复运行并报告波动，一次演示成功不能代表稳定成功。[A12]

发布同时看主要质量指标、关键场景退化、安全护栏、延迟和成本。离线通过后灰度，条件合适时做 A/B 测试，验证任务完成、采用和复用。线上失败回流开发集，但不能无限重复用保留测试集指导调优。评测最终要支持“能否发布”和“优先改哪里”这两个决策。

技术补充：分类题看 Precision/Recall/F1；开放生成看事实、覆盖及依据支持；Agent 检验最终状态是否达到任务目标，并诊断中间行动。单次成功概率为 p，在独立同分布假设下，k 次至少成功一次为 1-(1-p)^k，k 次全部成功为 p^k。真实试验可能相关，应报告实际重复运行结果，不把多次尝试里选一次成功当成生产可靠性。

追问1：没有标准答案怎么办？

追问提纲：无唯一措辞仍有准则 → 评分锚点 → 评审一致性 → 校准裁判

答：开放任务可以没有唯一措辞，但应明确必须覆盖的信息、事实正确性、证据支持、可用性和一票否决项，为评分档位配锚点样例。独立评审并复核分歧，检查评审一致性。比较两个版本可做匿名成对评价，随机交换答案位置并允许平局。模型裁判需要检查位置、长度和风格偏置，持续抽样对照人工；高风险结论不能只依赖模型互评。[A6]

追问2：离线变好，业务没变好呢？

追问提纲：检查实验与口径 → 样本代表性 → 代理指标与体验 → 业务增量

答：先核对统计口径、分流、埋点和样本量，再看评测集是否代表线上用户及新场景。接着检查离线指标是否是有效代理，例如措辞评分提高并不一定减少返工。拆任务漏斗，判断延迟、入口、失败重试或复核负担是否抵消收益；按用户和任务类型分析，再结合访谈定位原因。如果可信实验显示无业务增益，就调整评测标准或方案，不以离线涨分单独证明上线价值。

### Q41｜Agent 有哪些核心部分和常见失败？

考察点：理解执行循环、环境反馈及可靠性设计，能解释失败落在哪一层。

记忆提纲：① 目标、状态与规划 ② 模型、工具与执行器 ③ 观察、验证与终止 ④ 权限、预算和恢复

主回答：Agent 的核心包括目标与约束、模型决策、工具接口及执行器、任务状态与记忆、观察反馈和结果验证，外围还需要权限、预算、日志与人工介入。模型生成工具名和参数不代表操作成功，执行器要校验参数和权限、实际调用工具，再把真实结果交回决策循环。

ReAct 强调推理与行动交替：根据当前信息决定行动，通过工具获得观察，再更新判断。工程上应关注可记录的行动、观察和状态变化，不把模型展示完整思维链当作可靠性证明。结束任务也应依据外部结果或业务验收条件，例如候选确实入库且符合规则，而不是模型说“已完成”。[A13]

常见失败包括目标理解错、规划偏离、工具选择或参数错、环境失败、状态丢失，以及伪造成功。对应采用结构化约束、工具契约、参数校验、有限重试、幂等、检查点恢复和结果验证。产品经理需要确定自主执行范围、失败后的用户路径和验收线；高风险写操作设置明确授权环节。[A1]

技术补充：重试要区分限流、暂时故障、参数错误和权限错误；前两类可有限退避，后两类需修正或停止。写操作超时先核对实际状态，防止重复执行。Tool 是可调用能力，Skill 通常封装任务指引、资源或脚本；MCP 是连接工具和资源的协议，三者不能单独替代 Agent 的决策执行闭环。

追问1：什么时候需要长期记忆？

追问提纲：跨会话收益 → 与业务状态分工 → 写入可信度 → 生命周期

答：用户确认的稳定偏好或有效经验会影响未来任务时才考虑，例如长期偏好的内容风格。已选达人、支付状态和任务游标需要精确一致，应以业务数据库为准。记忆记录用户范围、来源、确认状态、更新时间和失效条件，支持纠正和删除。取回旧记忆后仍需检查是否适用于当前任务，不能用旧偏好覆盖本次明确要求。

追问2：怎么避免无限循环？

追问提纲：系统硬预算 → 重复与无进展检测 → 有限恢复 → 保存结果并交接

答：执行层设置最大步骤、累计耗时、费用和工具调用次数，不只把限制写进 Prompt。再记录动作、参数和返回结果，识别相同状态下重复调用、连续没有新证据或反复切换计划。可恢复故障有限重试，无法恢复则停止或交人工。退出时返回已有结果、缺口及原因，保存检查点；恢复前重验权限和时效。步数上限是兜底，无进展检测用于提前止损。

### Q42｜上下文和记忆怎么设计？

考察点：区分输入窗口、运行时状态和跨任务记忆，兼顾一致性与成本。

记忆提纲：① 上下文是本次输入 ② 状态与历史分层存储 ③ 按需取回与预算分配 ④ 冲突、失效和权限治理

主回答：上下文是模型本次推理看到的输入，包括指令、问题、历史消息、检索证据和工具结果；记忆是跨轮次或跨会话保存、需要时取回的信息。外部保存了信息，不代表本次模型已经读取。

我会将信息分为任务状态、可检索知识、历史记录和长期偏好。当前目标、硬约束、关键证据、待办和已执行动作优先进入上下文，大量历史与文档按需取回。长工具输出保留摘要和原文指针；金额、排除条件、任务状态保留结构化原值。还要为输出及后续工具反馈预留 Token 空间，不能让输入占满窗口。[A7]

更新时按来源、确认状态和时间处理冲突，明确本次需求与旧偏好的优先级。存储及检索按用户、项目权限隔离，记忆有失效和纠正机制。验证覆盖长会话、跨会话恢复、条件变更、旧知识冲突和摘要遗漏，看条件遵循率、任务连续性、敏感信息误用和成本。

技术补充：会话摘要是有损压缩，检索也可能漏信息，都不能替代关键业务状态的权威存储。KV Cache 是推理时复用计算的缓存机制，不等于用户长期记忆；扩大上下文窗口也不能自动解决历史冲突与信息过期。

追问1：摘要丢细节怎么办？

追问提纲：关键字段不依赖摘要 → 保留来源 → 决策前回查 → 专项验证

答：先定义必须无损保存的信息，如粉丝上限、排除对象和已执行动作，单独保存结构化状态，摘要主要压缩叙述。摘要带来源、覆盖范围和版本，关键决策需要细节时回查原记录。用“长会话后是否仍遵守约束”“恢复后是否重复动作”验证，而不只评价摘要文笔。发现遗漏则调整保留策略和输入选择，必要时减少压缩或补读原文，不在不完整摘要上继续猜测。

追问2：用户前后矛盾怎么办？

追问提纲：识别明确变更 → 更新生效版本 → 检查执行影响 → 含糊处澄清

答：先区分明确修改、临时偏好和表达含糊。用户明确改预算，就更新对应字段及需求版本，检查旧结果是否需要重算；已执行的操作不会因需求改变自动撤销。若要求无法同时满足，或变化影响高成本、不可逆动作，先澄清再执行。保留变更记录，当前只使用生效版本，不能简单按最后一句话覆盖所有已确认约束。

### Q43｜AI 产品核心指标怎么设计？

考察点：把用户价值转成可计算、可诊断、可用于决策的指标体系。

记忆提纲：① 价值指标与阶段目标 ② 过程转化和使用 ③ 质量、性能及成本护栏 ④ 分母、时间与版本口径

主回答：先明确用户获得什么价值，再设置主指标、过程指标和质量成本护栏。调用量不直接等于价值，接口成功也不等于用户任务成功。

结合媒介助手，最新确认的北极星指标是“已选达人转化率”：当前被用户选中的达人数量，除以真实检索后进入候选池的达人数量。按项目和达人去重，累计计算，分母为零显示暂无数据。它反映候选转化为用户选择的情况，但已选不代表已合作或产生投放收益，也不能只靠比例判断规模。[项目记录 D025，2026-09-13]

因此还要看有效候选数、产生有效选择的任务数、名单完成耗时及用户复用；审核模块单独看风险项精确率、召回率、严重漏报和人工复核耗时。工程层关注调用成功率、端到端 P95、超时与重试；经济性看成功任务总成本。按场景、用户和模型版本拆分，才能判断变化来自能力、数据、体验还是流量结构。

技术补充：TP 是正确检出的风险，FP 是误报，FN 是漏报；Precision = TP/(TP+FP)，Recall = TP/(TP+FN)，F1 = 2PR/(P+R)。需约定零分母处理。低风险样本占多数时，总准确率可能掩盖严重漏报。[A14] 单成功任务成本 = 同范围内全部任务相关成本 / 成功任务数，失败和重试成本不能剔除。成功标准、窗口、去重键和数据版本都要写入指标字典。

追问1：指标冲突怎么办？

追问提纲：质量约束 → 错误成本 → 分级策略 → 防止数字失真

答：先明确不可突破的业务底线，再优化主指标。审核降低阈值可能提高召回，同时增加误报及复核量，要按错误代价和处理容量选工作点；Precision 与 Recall 也不总是只能此消彼长，提升数据和模型质量可能同时改善。达人转化率还可能因只展示少数容易选中的人而虚高，因此同时看满足需求的数量、覆盖和耗时。无法消除冲突时说明取舍和受影响用户，不用随意加权掩盖问题。

追问2：第一版阈值怎么定？

追问提纲：人工基线与样本 → 风险及资源约束 → 验证集选点 → 独立测试与灰度

答：先测现有人工流程的质量、耗时和错误分布，再与业务确定漏报代价、误报容忍度及复核容量。若有可比较的评分，在验证集上画 Precision-Recall 曲线，对比阈值对应的严重漏报和复核量，选满足约束的工作点；模型自报分数要先检查有效性，不能直接当概率。然后独立测试、灰度校正。高风险切片单独看样本量和不确定性，少量样本零漏报不等于上线零风险，不凭空承诺 95% 或 99%。

备考备注：Q43 依据 2026-09-13 的 D025 更新；其他章节如 Q11、Q18 保留旧版准备记录，若主指标表述不同，以本题引用的最新决定为准。D025 是累计“当前状态”指标，取消已选会改变分子；分析历史趋势需记录状态事件或定期快照，不能将今天的累计比例当上周同期群转化率。真实用户量、留存及审核提效仍需实际数据支持。
